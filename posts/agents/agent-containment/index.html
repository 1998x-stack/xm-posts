ANTHROPIC ENGINEERING / AGENT SECURITY

Understanding Agent Containment

当 Agent 获得文件、Shell、网络和工具权限时，安全问题不再只是“模型会不会听错指令”，而是一次失败最多能触及哪些资源、能否越过边界、外部内容能否改变 Agent 的行动。

官方工程文章 · 2026-05-25主分类：Agents / Agent Security约 27 分钟状态：研究草稿

01 · Agent 风险有三种来源

Anthropic 把 Agent 的安全风险分为：用户误用（user misuse）、模型自身行为偏离（model misbehavior）和外部攻击者（external attackers）。它们可能产生相似后果，却需要不同防线。

风险来源典型情况不能只依赖什么
用户误用用户让 Agent 执行破坏性命令，或误解后果只假设用户每次都能正确审查权限弹窗
模型行为偏离模型为完成目标寻找未预料到的路径只依赖 system prompt 或 classifier
外部攻击者恶意文件、工具输出、网页或运行时组件影响 Agent只做传统依赖扫描，不检查 prompt injection

能力越强，模型可能越少犯明显错误，但也越有能力找到设计者没有写下来的边界漏洞。安全设计因此要关注“失败概率”和“失败后果”两个维度；限制 blast radius 可以让某些高效用能力在可控范围内部署。

02 · 三个防御组件：环境、模型与外部内容

2.1 环境边界：决定 Agent 实际能够做什么

文件系统边界、进程沙箱、虚拟机、网络出口控制等机制能限制 Agent 可触达的资源。凭证如果根本不进入沙箱，就不必指望模型每次都正确拒绝读取它。环境防御是确定性的硬边界，应优先于纯行为引导。

2.2 模型边界：改变行为倾向，而不是物理能力

System prompt、分类器、探针和训练修改可以改变模型倾向，但模型是概率系统，不能保证 100% 不越界。Anthropic 将 Claude Code auto mode 定位为降低权限审批疲劳的一层防线，而不是沙箱替代品。

2.3 外部内容边界：可信工具不等于可信数据

GitHub README、网页、MCP 返回值和第三方 connector 都可能把恶意指令带入上下文。即使 connector 本身通过代码安全审查，它加载的数据仍可能被投毒。应对工具权限做最小化，并在内容进入上下文之前考虑实时检查。

03 · 三种隔离模式：按用户监督能力匹配

Pattern A：短生命周期容器（claude.ai）

代码执行在服务端隔离基础设施中的 gVisor 容器内；文件系统按会话临时存在，代码不运行在用户本机。它缩小了对用户设备的影响范围，但不提供持久工作区或用户本机文件访问。对应威胁模型更偏向保护平台基础设施和租户隔离。

Pattern B：人类监督 + OS 沙箱（Claude Code）

开发者 Agent 需要访问本机仓库、Shell 和网络，因此单靠远端容器会削弱产品能力。早期方案允许读取、对写入 / bash / 网络请求审批；但 Anthropic 发现用户大约批准了 93% 的权限提示，审批疲劳会削弱监督。后来增加 macOS Seatbelt 或 Linux bubblewrap 沙箱：允许读取，允许工作区内写入，默认禁止网络。文章报告权限提示减少约 84%。

Pattern C：本地 VM（Claude Cowork）

通用知识工作者未必能判断复杂 Shell 命令，因此不能把风险判断全部交给用户。Cowork 采用 VM 隔离：独立 guest kernel、文件系统和进程表，只挂载用户选择的工作区；凭证留在 host keychain，不进入 guest。后续将 Agent loop 移到 VM 外、代码执行留在 VM 内，以改善 VM 启动失败时的可用性，同时保留代码执行隔离。

04 · 失败案例说明：边界要覆盖“用户点击之前”和“允许访问之后”

4.1 信任弹窗之前的项目配置

Anthropic 报告过项目目录中的配置或 hook 在用户确认信任之前就被解析或执行的问题。修复原则是：在用户接受信任之前，不解析、不执行项目本地配置。项目打开、配置加载和 localhost listener 都应按外部输入处理，而不是因为“来自本机文件夹”就默认可信。

4.2 用户也可能成为 prompt injection 的载体

内部 red-team 测试展示：恶意指令可能由用户复制粘贴进入任务，而不是来自网页或工具输出。模型层分类器未必能识别这种情况，因为指令表面上来自用户。环境层文件边界和 egress control 才能阻止敏感文件离开工作区。

4.3 域名 allowlist 不等于能力安全

允许访问一个 API 域名，可能同时允许它提供的文件上传、代理抓取等能力。Anthropic 描述过一个 Cowork 案例：请求目的域名在 allowlist 中，但请求使用了攻击者控制的凭证，仍导致工作区文件被上传。修复方向是在代理中验证 VM 自己的 session token、限制请求能力和来源，而不是只判断目的域名。

隔离也有可观测性成本：VM 可能让 host EDR 看不到 guest 内部事件。Anthropic 提到通过 OTLP 拉取事件日志作为当前缓解方式，但这不等于实时监控。安全边界设计应把审计与企业可见性一起纳入。

05 · 工具与外部内容：代码供应链安全和上下文安全是两件事

传统依赖审查主要处理代码供应链风险：工具代码是否可信、版本是否固定、签名是否正确。Agent 还多出上下文安全风险：工具返回的数据可能包含操纵模型的指令。Anthropic 建议先用假数据在受控环境中试运行工具，并在工具输出进入上下文前考虑扫描和策略检查。

长期运行 Agent 还带来持久记忆投毒：产品 memory、CLAUDE.md、工作区和调度任务状态会跨会话重新加载；一旦恶意内容进入持久状态，就可能重复影响未来会话。多 Agent 系统也有信任升级风险：主 Agent 可能错误地把 sub-agent 输出当作比原始工具结果更可信的内容。

07 · 最小策略：先解析真实路径，再做工作区授权

from pathlib import Path

def inside_workspace(workspace, candidate):
    root = Path(workspace).resolve()
    target = Path(candidate).resolve()
    try:
        target.relative_to(root)
        return True
    except ValueError:
        return False

这个片段演示一个常见边界原则：先解析符号链接，再判断最终路径是否仍在授权目录中。它只是路径检查教学示例；生产沙箱还需要处理竞态、挂载、硬链接、进程权限、网络和内核边界。

08 · 适用边界与结论

  • 模型层防御是概率性的；不能取代环境层硬边界。
  • 人类审批适合有能力判断风险的用户，但提示疲劳会降低有效监督。
  • VM 隔离可以缩小 blast radius，却可能牺牲 host 可观测性和启动可靠性。
  • 域名 allowlist 只是目的地策略；API 端点本身暴露的能力也必须纳入威胁模型。
  • 本地和远程工具都可能提供恶意内容；代码可信度与数据可信度必须分开处理。
核心原则：把最坏情况下 Agent 能触及的资源限制在最小范围；让模型层帮助减少误操作，但不要让系统安全依赖模型每一次都判断正确。
