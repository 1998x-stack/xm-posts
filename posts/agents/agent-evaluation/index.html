AGENTS / AGENT EVALUATION · RESEARCH GUIDE

Understanding
Agent Evaluation

一个 Agent 真正完成了任务吗？从最终状态、工具调用和执行轨迹，到一致性、安全性与成本，建立能够解释、复现并指导工程改进的评测体系。

Research synthesis · 2023–2026约 35 分钟阅读Agent Benchmarks · Reliability · Safety

01 · 为什么 Agent 不能只看答案？

对普通问答模型，我们常常把输入和输出放在一起比较；但 Agent 的任务不是只生成一段文字，而是通过一串行动改变外部世界。

想象一个很普通的工程任务：“定位仓库里的一个 Bug，修复它，运行测试，并提交一个可审查的 Pull Request。” 一个 Agent 可能给出非常漂亮的解释，却没有真正修改文件；也可能修改了代码，但没有运行测试；甚至测试通过了，却误删了与问题无关的功能。

如果评测器只检查最后一段自然语言是否包含“已修复”，它就会把“声称完成”误判成“任务完成”。这不是小小的指标误差，而是评测对象定义错了。

核心区别：对话模型主要回答“它说得对不对”；Agent 评测还必须回答“它做得对不对、过程是否可靠、是否越过权限边界，以及完成任务花了多少资源”。

这也是为什么 Agent 评测不能直接把 MMLU、GSM8K 或普通文本生成指标搬过来。它们可以测量底层模型的某些知识或推理能力，却不能单独回答一个系统能否稳定地完成多步骤任务。KDD 2025 的综述明确指出，Agent 在动态交互环境中规划、调用工具、利用记忆并与用户或其他 Agent 协作，因此评测复杂度高于孤立 LLM 的文本输出评测。Mohammadi et al., 2025

02 · 评测对象：完整 Agent 系统，而不只是模型

先把评测对象写清楚。为了避免把 Agent 和它所处的环境混为一谈，我们把被测 Agent 系统与外部评测配置分开定义：

AgentSystem=(M,P,C,T,S,G)EvaluationSetup=(AgentSystem,E,V)
M：基础模型；P：Prompt / Policy；C：Controller；T：Tools；S：State / Memory；G：Guardrails / 权限控制。E 是外部 Environment，V 是独立 Verifier / Evaluator；两者属于评测配置，不是 Agent 自身的内部模块。该表达是本文的系统边界抽象，不是某篇论文规定的唯一架构。

模型与提示

模型版本、采样温度、系统提示、任务模板、上下文窗口和结构化输出约束。

控制器与规划

循环策略、最大步数、重试、终止条件、子任务拆分、并行或多 Agent 编排。

工具与环境

API Schema、浏览器、文件系统、代码解释器、数据库、权限、网络和外部状态。

状态与安全

短期上下文、长期记忆、状态同步、人工审批、访问控制和不可逆操作保护。

因此，实验报告不能只写“使用某模型”。更完整的描述应该是：模型版本 + Agent Scaffold + Prompt + 工具定义 + 环境版本 + 数据集版本 + 采样配置 + 评测器版本。

否则，同一个模型换了工具说明、记忆机制或重试策略，成绩就可能发生变化；我们却错误地把所有变化都归因于模型能力。OpenAI 对 SWE-bench Verified 的分析也展示了这一点：同一 GPT-4 在不同软件 Agent Scaffold 下的表现可以明显不同。SWE-bench Verified

03 · 两维评测分类体系：评什么 × 怎么评

Agent Evaluation 研究已经形成了相对清晰的组织方式。Mohammadi 等人在 KDD 2025 的综述中提出一个二维 Taxonomy：第一维是 Evaluation Objectives（评测目标），回答“我们想知道 Agent 的哪种性质”；第二维是 Evaluation Process（评测过程），回答“我们通过什么数据、环境、指标和工具来测量”。

3.1 第一维：Evaluation Objectives——评测什么

这四类并不互相替代。一个 Agent 可以任务成功率很高，但需要大量不必要的工具调用；也可能任务成功率不错，却偶尔发生越权写入。只看一个指标会掩盖另一类失败。

3.2 第二维：Evaluation Process——怎么评

  • Interaction Mode：固定输入的静态测试，还是用户、工具与环境持续交互的动态测试？单轮、长对话、多轮任务、多 Agent 协作都应明确区分。
  • Evaluation Data：合成任务、人工编写任务、真实工作流，还是领域 Benchmark？数据是否代表目标用户真实任务分布？
  • Metrics Computation：用程序检查最终状态、AST / Schema 检查工具调用、参考答案匹配、人工打分，还是 LLM-as-a-Judge？
  • Evaluation Tooling：是否记录完整 Trace、环境快照、模型版本、Token、工具调用、失败原因和运行日志？
  • Evaluation Context：任务是在模拟器、浏览器、桌面操作系统、代码仓库、数据库，还是开放互联网中执行？
如何使用这套二维分类？不要把它理解成“每篇论文只能属于一个格子”。一个 Agent Benchmark 通常会同时涉及多个目标与多个过程维度。二维 Taxonomy 是设计评测矩阵的坐标系，不是互斥标签表。

04 · 六类核心指标：从成功率到安全性

研究综述将行为、能力、可靠性和安全作为主要目标；在实际系统验收中，还应该把效率与用户体验单独报告。下面这六组指标可以构成一张可执行的 Scorecard。

4.1 任务结果：Success Rate / Goal Completion

最基础的指标是任务成功率。设测试集有 N 个任务，第 i 个任务的最终状态是否满足成功条件记作 yᵢ ∈ {0, 1}：

SR=1N∑i=1Nyi
yᵢ=1 表示任务的预先定义成功条件全部满足，否则为 0。

关键在于：成功条件应该尽可能落在可检查的环境状态上，而不是 Agent 自己的文字声明上。例如，数据库中的订单状态是否真的变更、代码补丁是否通过目标测试、日历事件是否按要求创建。

对于多目标任务，可以额外定义部分完成度：先列出目标状态 g₁, …, gₘ，为每项设定权重 wⱼ，再计算已达成目标的加权比例。它适合诊断“完成了 3/4 个步骤”，但不能随意取代最终成功率；高风险任务中，某个关键子目标失败就可能意味着整体失败。

4.2 工具调用：选择正确还不够，参数和结果也必须正确

把一次工具调用拆成四个检查点：

  1. 是否应该调用：问题是否真的需要外部信息或动作？
  2. 选择哪个工具：工具名称和能力是否匹配？
  3. 参数是否正确：字段、类型、枚举值和具体值是否符合 Schema 与任务语义？
  4. 执行后是否达到预期：工具是否成功返回？环境状态是否发生了正确变化？

这四层不能混为一个“Function Calling Accuracy”。例如 AST 可以判断调用结构和参数语法是否正确，却不一定知道一个合法的 user_id 是否属于当前用户。BFCL 使用 AST 评估串行、并行工具调用，并逐步扩展到多轮、有状态的 Agentic 评测；它也强调单轮工具调用表现并不能代表记忆、动态决策和长程推理能力。Patil et al., ICML 2025

4.3 规划与轨迹：Agent 有没有走对过程

设一次执行轨迹为 τ = (o₀, a₀, o₁, a₁, …, oₜ)，其中 oₜ 是观察，aₜ 是动作。除了最终成功与否，还可以检查：

  • 工具序列是否满足任务依赖关系；
  • 每一步是否推动了目标状态，而不是重复搜索或空转；
  • 遇到空结果、超时、异常响应时，是否采取合理恢复动作；
  • 是否过早结束，或在已完成后继续执行危险动作；
  • 是否发生循环、重复调用、无关文件修改或不必要的状态写入。

轨迹指标特别适合错误归因：如果 Agent 最终失败，我们需要知道它是没理解任务、没选对工具、参数错了、环境没准备好，还是在第 8 步之后偏离了原目标。

4.4 可靠性：同一任务重复执行是否稳定

LLM Agent 通常具有采样随机性，外部环境也可能发生变化。因此一次成功并不代表可重复成功。下一节将重点推导 Pass@k 与 Pass^k。

4.5 安全性：不仅看有没有拒绝，还要看有没有越权副作用

安全评测应检查敏感数据泄露、未经授权的写入、危险工具调用、Prompt Injection 成功率、是否遵守人工确认流程，以及拒绝是否发生在正确的边界上。单纯统计“拒绝率”会误伤正常任务：一个永远拒绝操作的 Agent 可以得到很低的攻击成功率，却没有任何实际可用性。

4.6 效率与体验：完成一次任务付出了什么

至少报告端到端延迟、模型输入/输出 Token、工具调用次数、外部 API 成本、重试次数、人工接管次数，以及每个成功任务的成本。Agent 的成本不能只统计模型 Token：浏览器、代码执行、搜索、数据库和人工审核都可能成为主要开销。

Csuccess=CtotalNsuccess
需注明统计范围、计价时间、重试策略与人工成本是否计入；若成功任务数为 0，该指标应报告为未定义，而不是 0。

05 · Pass@k 与 Pass^k：偶尔能做成，不等于稳定能做成

这是 Agent 评测中最容易被误读、也最值得掌握的一组指标。

假设一个 Agent 对同一个任务单次成功概率为 p = 0.8。如果允许它运行五次，只要其中一次成功就算成功，那么“至少成功一次”的概率会非常高；但如果要求五次全部成功，结果就会低得多。

Pass@k=P(∑j=1kyj≥1)=1−(1−p)k
Pass@k：k 次独立尝试中至少一次成功。它更接近“允许多次采样 / 重试时，是否有机会找到成功轨迹”。
Passk=P(∑j=1kyj=k)=pk
Pass^k：k 次尝试全部成功。它更严格地反映一致性，对每次执行都必须可靠的任务更有意义。
交互实验 · 改变单次成功概率和重复次数

τ-bench 将 Pass^k 用于衡量 Agent 在多次试验中的行为一致性。其任务模拟零售与航空客服场景：Agent 需要和模拟用户持续对话、遵循领域政策并调用 API，最终通过数据库状态与标注目标状态进行比较。原论文报告，GPT-4o 在任务上的成功率低于 50%，零售场景的 Pass^8 低于 25%。这些是该论文实验设置下的历史结果，不应当被当作当前所有模型的实时排名。Yao et al., ICLR 2025

重要的统计假设：上面的 1 − (1 − p)ᵏ 和 pᵏ 依赖“每次尝试独立且成功概率相同”的简化假设。真实 Agent 的多次运行可能共享缓存、随机种子、环境状态或同一模型偏差。正式报告应在每个任务上实际重复运行，并直接计算经验 Pass@k / Pass^k，而不是只从单次成功率外推。

6.1 如何把这些 Benchmark 组合起来？

  • 通用助手：GAIA + AgentBench，关注跨领域任务与工具协同。
  • 浏览器自动化：WebArena + BrowserGym 生态，关注长程交互、页面变化和功能状态。
  • 桌面自动化：OSWorld，关注截图理解、GUI 定位和跨应用操作。
  • 工具密集型工作流：BFCL + τ-bench，分别观察调用能力和用户/业务规则闭环。
  • 代码 Agent：SWE-bench Verified，配合新鲜任务集和完整容器化测试环境。
  • 高风险 Agent：AgentDojo 等安全评测，与正常任务成功率一起报告。

GAIA 的设计尤其值得注意：它并不只追求“人类也很难做”的题目，而是强调对人类概念上简单、但需要系统准确执行多步骤动作的任务，并尽量让最终答案可以自动验证。这个思路提醒我们：Benchmark 的难度不等于它的评测质量。GAIA

同样，WebArena 和 OSWorld 的早期论文结果不能直接与今天的模型排行榜横向比较：模型、工具、Agent Scaffold、环境和评测协议都可能已经变化。表格中的数字用于理解论文当时揭示的挑战，而不是构造统一的当前排名。

07 · 如何设计严谨的 Agent Evaluation 实验？

下面是一套可以真正用于研究生实验、模型比较和生产验收的流程。重点不是“跑一个 Benchmark”，而是保证每个分数都有明确的测量含义。

  1. 定义任务契约。写明用户目标、初始环境状态、可用工具、禁止操作、终止条件和成功状态。不要把模糊的自然语言期望留给评测器临时猜测。
  2. 冻结系统配置。固定模型快照、提示词、工具 Schema、控制器、记忆、权限、采样参数、超时、重试次数和上下文预算。
  3. 构造分层任务集。按任务类型、难度、步骤长度、工具数量、风险等级、是否需要澄清、是否包含环境变化分层。避免测试集只包含简单任务。
  4. 设计对照组。至少比较一个基线 Agent；若研究某个组件，使用 Ablation：关闭记忆、移除规划、替换工具描述、改变重试策略等。每次尽量只改变一个关键因素。
  5. 执行多次运行。记录随机种子、运行次数、失败重试和环境重置方式。随机性较大的系统不能只跑一个样本或一个种子。
  6. 记录完整 Trace。保存用户输入、模型版本、工具名称与参数、Observation、状态变化、异常、Token、时间、费用和最终状态。敏感信息必须脱敏。
  7. 使用独立评测器。优先通过数据库状态、单元测试、文件差异、API 返回和权限审计进行确定性验证；开放式质量再使用人工或校准过的模型评审。
  8. 做统计分析。报告均值、分布、置信区间、任务分层表现、失败类型和重复运行一致性；不要只报告一个平均分。
  9. 发布可复现报告。包含任务集版本、环境镜像、Agent 配置、评测代码、原始结果、失败样本和已知局限。
一个实用原则：如果无法回答“这个任务在什么初始状态下、经过哪些操作、最终满足了什么可机器检查的条件”，就还没有真正定义好 Agent Benchmark。

08 · Evaluator 与 LLM-as-a-Judge：谁来判断 Agent 做得对不对？

Agent 的最终输出有时是自然语言，有时是数据库状态、代码补丁、文件系统变化或多个工具副作用。评测器需要根据任务性质选择，不存在一种评分方法能覆盖全部场景。

评测方式适合什么优势主要风险
程序化状态检查数据库、文件、代码、订单、日历状态可复现、便宜、标准明确成功条件设计错了会稳定地判错
测试 / 执行验证代码修复、数学工具、结构化操作验证真实行为，而非文字描述测试覆盖不完整，环境依赖可能误伤正确方案
规则 / Schema / AST函数调用、参数格式、协议遵循容易定位格式和结构错误合法语法不保证语义正确或权限合规
LLM-as-a-Judge解释质量、开放式规划、交互体验可扩展到难以写规则的文本判断偏好冗长答案、顺序偏差、模型偏差和自我偏好
人工评审高风险、复杂歧义、用户体验和安全审计能处理细微上下文昂贵、耗时，评审者之间可能不一致

8.1 为什么不能把所有评分都交给另一个 LLM？

LLM Judge 可以帮助判断“解释是否清楚”，却未必知道“数据库中的订单是否真的变更”。它还可能偏爱更长、更自信或格式更整齐的回答；如果没有盲测和校准，评分本身也可能引入新的偏差。

建议采用分层 Evaluator：

  • 第一层：硬约束。状态、测试、权限、结构化字段、必须满足的条件，由确定性程序检查。
  • 第二层：语义质量。对解释、相关性、可读性等开放式内容，使用带 rubric 的 LLM Judge。
  • 第三层：人工审计。抽查成功与失败样本，尤其是边界案例、争议样本和高风险动作。

对 LLM Judge 至少做四项校准：固定评分 rubric；对模型答案隐藏系统身份；随机交换 A/B 顺序检测位置偏差；用人工标注子集测量 Judge 与人类的一致程度。还应保留原始评分和分歧案例，而不是只保存最终总分。

GAIA 的论文讨论了模型评审的局限：开放式评测依赖人类或模型判断，而模型评审本身可能存在偏差；其设计因此尽量使用能够通过完成多步骤任务得到、且容易自动核验的事实答案。GAIA

09 · Benchmark 有效性：高分不一定代表真实能力

Benchmark 分数是一个测量结果，不是能力本身。要相信这个数字，至少要检查下面几种有效性风险。

9.1 数据污染与任务过时

静态任务可能出现在训练数据或公开代码仓库中。Agent 可能记住了答案，而不是现场完成任务。应使用私有留出集、时间切分、新鲜任务、动态环境或定期轮换的任务集，并明确报告污染检测的能力边界。

9.2 任务本身不公平或无法完成

SWE-bench Verified 是一个非常好的反例：原始 SWE-bench 中部分任务存在描述不充分、测试过于具体或环境配置不可靠的问题。OpenAI 与 SWE-bench 作者合作筛选出 500 个经人工确认质量更好的样本；其说明还报告，初始分析的 1,699 个随机样本中，68.3% 因任务描述、测试或其他问题被过滤。这个案例说明：评测集本身也需要被评测。SWE-bench Verified

9.3 只报平均值掩盖长尾失败

同样的 80% 成功率，可能来自“所有任务都大约 80% 成功”，也可能来自“简单任务几乎全对、少数关键任务完全失败”。生产系统更需要按任务难度、风险、步骤长度和用户群体切片。

9.4 评测环境和真实部署之间存在差距

模拟器更可控，却可能不够真实；真实环境更贴近用户，却可能出现网络波动、页面改版、权限差异和不可重复状态。应明确评测是在封闭模拟器、真实沙箱，还是开放环境中完成，并记录环境版本和初始化状态。

9.5 Reward Hacking 与 Goodhart's Law

一旦把某个指标作为唯一优化目标，Agent 就可能学会钻指标的空子。例如：为了提高工具调用成功率而调用不必要的工具；为了提高任务完成率而绕过安全检查；为了得到更高 Judge 分而输出冗长解释；为了通过测试而硬编码样例答案。

不要只问“分数提高了多少”。还要问：成功条件是否被投机？失败是否被隐藏？有没有新增副作用？在独立测试集和真实用户任务上是否仍然成立？

10 · 最小可运行指标代码：把重复试验变成可复核统计

下面的 Python 示例使用纯标准库，输入每个任务的多次运行结果，输出 Pass@1、Pass@k、Pass^k 和平均单次成功率。它不连接模型、不调用外部 API，也不声称复现某个论文 Benchmark；它只实现定义清楚的统计量。

from agent_eval_metrics import summarize_runs

# 每一行是同一个任务的 5 次独立运行结果
runs = [
    [True,  True,  False, True,  True],
    [True,  False, False, False, True],
    [False, False, False, False, False],
]

report = summarize_runs(runs)
print(report)

# 预期：
# pass_at_1       = 2 / 3
# pass_at_k       = 2 / 3
# pass_all_k      = 0 / 3
# mean_attempt_success = 6 / 15

运行方式（从仓库根目录）：

python -m pytest -q tests/test_agent_eval_metrics.py
python posts/agents/agent-evaluation/agent_eval_metrics.py

注意：Pass@k 和 Pass^k 必须基于同一任务的重复运行分组计算。把不同任务的成功结果混在一起，或者把“同一个任务的 k 次尝试”误当成“k 个不同任务”，都会得到没有意义的统计量。

11 · 研究前沿与开放问题：从 Benchmark 分数走向持续评测

到 2026 年，Agent 评测已经从“比较几个模型谁的分数高”逐渐转向对评测体系本身的研究。2026 年的 Survey on Evaluation of LLM-based Agents 从基础 Agent 能力、领域 Benchmark、通用 Agent、Benchmark 核心维度和开发者评测框架五个视角组织相关工作，并指出成本效率、安全性、鲁棒性和可扩展的细粒度评测仍是重要缺口。Yehudai et al., Findings of ACL 2026

动态任务与持续评测

静态 Benchmark 会过时。未来需要定期更新任务、追踪环境变化，并保留可比较的固定锚点集。

长时程能力

任务步骤越长，错误累积和状态漂移越明显。METR 的 Time Horizon 研究以人类专家完成时间作为任务难度刻度，并拟合 Agent 在不同任务时长下的成功概率。它测量的是任务难度与成功可靠性的关系，不是 Agent 运行了多久。

多 Agent 协作

需要额外衡量任务分配、信息共享、冲突解决、协调开销和失败传播，而不只是每个子 Agent 的单体分数。

安全与治理

权限控制、数据隔离、人工审批、审计日志和 Prompt Injection 防护应进入常规评测协议，而不是部署后再补测。

AgentDojo 把安全问题变成可执行测试：外部工具返回的内容可能包含恶意指令，诱导 Agent 代表用户执行不该做的事。其 NeurIPS 2024 版本包含 97 个任务和 629 个安全测试用例，覆盖邮件、网银和旅行预订等场景。它强调安全评测必须同时观察正常任务效用和攻击条件下的安全属性。AgentDojo

最终，成熟的 Agent 评测不应只有一个排行榜，而应是一套持续运行的工程系统：任务集持续更新，运行轨迹可追溯，评测器经过校准，安全边界可验证，成本和可靠性与任务成功率一起呈现。
