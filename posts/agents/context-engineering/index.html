01 · 一个反直觉的问题：为什么给 Agent 更多信息，反而可能让它更差？

设想你正在让一个代码 Agent 修复一个线上 Bug。它已经读取了 80 个文件、执行了 14 次命令、收到 30 多段工具输出，并且经历了多轮方案修改。此时你再把整个仓库、所有日志和完整聊天记录都塞进模型，真的会让它更聪明吗？

不一定。模型可能忘记最初的验收条件，混淆已经废弃的方案与当前方案，在冗长日志中漏掉关键错误，或者把旧版本文档当成最新事实。问题并不一定是模型“没有读到”，而可能是重要信息被低价值信息淹没，或者信息之间缺少明确的关系与可信度标记。

核心问题：在有限的上下文窗口、延迟和成本预算下，怎样让模型在当前这一步获得足够、相关、可信、不过时的信息，同时避免被历史噪声和不必要的细节干扰？

Anthropic 在 2025 年的 Engineering 文章中把上下文视为有限的注意力资源，并讨论了随着输入变长，模型在信息召回与长程推理方面可能出现的性能退化。这类现象常被称为 context rot。需要注意，它不是一个所有模型、所有任务都遵循同一曲线的定律：不同模型、位置、任务和检索方式会有不同表现；更准确的理解是，窗口容量增大并不自动保证有效利用率同步增长。

因此，Context Engineering 的优化目标不是“塞得更多”，而是“在当前任务中放对信息”。

02 · Prompt Engineering、Context Engineering、RAG、Memory 与 Harness

这些术语经常被放在一起讨论，但它们处在不同的抽象层次。把它们混为一谈，会导致工程设计只盯着 Prompt 文案，却忽略工具、检索、状态与持久化。

概念核心问题典型对象边界
Prompt Engineering怎样表达任务与行为要求？System prompt、指令、few-shot 示例主要关注指令设计，不负责管理全部动态状态
Context Engineering本次推理应该获得哪些信息？指令、工具、历史、检索结果、记忆、外部状态负责信息选择、组织、更新和预算管理
RAG如何从外部知识源找到相关内容？索引、Embedding、检索、重排序、引用是上下文获取的一类重要机制，不等于整个上下文工程
Agent Memory什么经验值得在未来会话继续使用？日志、笔记、知识图谱、索引、持久化状态关注跨任务或跨会话的保留与再利用
Harness EngineeringAgent 在什么环境中运行、观察和完成工作？工具、沙箱、文件系统、执行计划、评测、权限提供运行时与治理结构；上下文工程是其中的关键组成

一个容易记住的关系是：Prompt 是上下文中的一部分；RAG 是上下文的一个来源；Memory 是可跨时间复用的状态；Harness 则提供工具和执行环境，让 Agent 能够读取、修改并验证外部世界。

Anthropic 将 Context Engineering 描述为对推理时全部信息的持续策划；OpenAI 的 Agents SDK Cookbook 则从 Session 层面给出了历史裁剪与摘要压缩的具体方法。两者关注点不同，但都指向同一件事：模型每一步获得的信息状态，需要被主动管理，而不是无限累积。

03 · 上下文窗口：容量不等于质量

3.1 先理解 Token Budget

上下文窗口通常同时容纳输入与输出。工程上不能把全部容量都分配给历史消息：模型还需要输出空间，工具调用也可能产生下一轮输入。因此可以先用一个简单的预算账本来理解：

EQUATION 1 · CONTEXT BUDGET
B=Bsystem+Btools+Bgoal+Bretrieval+Bhistory+Boutput+Bmargin
这是工程预算模型，不是模型内部固定的 token 分区。实际 API 还可能有模型特定的输入/输出上限、缓存规则与工具消息开销。

各项的含义：

  • System：身份、任务边界、稳定规则和安全约束。
  • Tools：当前可用工具的名称、用途、参数和返回结构。
  • Goal：用户当前目标、验收标准、不可违反的约束。
  • Retrieval：本轮真正需要的文档、证据和外部状态。
  • History：近期对话、关键决策、未完成事项。
  • Output：为模型最终回答或下一步工具调用预留的空间。
  • Margin：工具结果膨胀、额外元数据和不可预测开销的缓冲。

3.2 为什么“大窗口”不等于“无限工作记忆”？

Transformer 的自注意力允许 Token 之间建立关系。对标准稠密全注意力，长度为 n 的序列涉及约 n² 量级的 token-pair 关系；高效注意力、稀疏注意力和其他架构会改变实际计算与访存成本，因此不能把这个数量级直接当作所有模型的推理延迟公式。

更重要的是，模型的召回能力并非只由窗口上限决定。信息的位置、干扰项、指令冲突、工具输出格式、训练分布和任务难度都会影响模型能否利用这些信息。一个 100 页的文件全部进入窗口，不代表模型能够稳定地定位其中每一个细节。

工程启示：把外部存储视为容量，把上下文窗口视为工作集。数据库可以很大，CPU Cache 不会因此变成整个数据库；同样，Agent 的外部知识库可以很大，但每次推理的上下文仍然需要筛选。

3.3 一个优化视角：相关性、成本和风险之间的权衡

令 It 表示时刻 t 所有可访问的信息候选集合，Ct 表示本次真正装入模型的信息。我们可以把上下文选择写成一个教学用的优化目标：

EQUATION 2 · CONTEXT SELECTION OBJECTIVE
Ct*=arg maxCt⊆It[U(Y|Ct,gt)−λCost(Ct)−μRisk(Ct)] subject to Tokens(Ct)≤Bt
这是用于组织工程决策的抽象目标，并非 Anthropic 或 OpenAI 公布的训练损失函数。U 表示任务效用，Cost 包含 Token、延迟和检索开销，Risk 包含过时、错误、注入和隐私风险。

这个模型帮助我们避免两个极端：一味追求最短 Prompt，可能删掉必要约束；一味追求最全历史，又可能带来噪声、成本与错误传播。真正要最大化的是单位上下文预算带来的任务效用。

04 · Context Engineering 的技术分类：从基础操作到系统架构

Mei 等人的《A Survey of Context Engineering for Large Language Models》提出了一个适合研究者使用的视角：基础组件可以分为 Context Retrieval & Generation、Context Processing 和 Context Management；在此之上，再观察 RAG、Memory、工具集成推理和 Multi-Agent 等系统形态。

结合 Anthropic 与 OpenAI 的工程实践，可以形成以下教学分类。它是对多种来源的综合归纳，而不是某个厂商的官方产品目录。

L1 · INFORMATION ACQUISITION

信息获取与生成

检索、搜索、文件读取、数据库查询、工具 Schema、计划和状态摘要。

L1 · INFORMATION PROCESSING

信息处理

过滤、重排序、去重、分块、结构化、摘要、压缩、格式规范化。

L1 · CONTEXT MANAGEMENT

上下文管理

Token 预算、窗口裁剪、Compaction、会话状态、缓存、持久化与隔离。

L2 · SYSTEM INTEGRATION

系统集成模式

RAG、Agent Memory、Tool-integrated Reasoning、Multi-Agent 与 Harness。

4.1 不要把“检索”当作全部上下文工程

RAG 主要回答“外部资料在哪里、哪段内容相关”；但即使检索命中正确，仍然需要决定：取多少段？如何处理冲突？是否保留来源？是否压缩？怎样与用户最新约束一起传给模型？工具结果是否可信？这些问题已经超出了向量检索本身。

4.2 不要把“记忆”当作“把聊天记录存下来”

原始日志适合审计和重新检索，但通常不适合每轮全部加载。记忆系统需要从经历中抽取稳定事实、决策、规则和可验证证据，再建立索引或知识表示。更关键的是，记忆必须可以被纠错、更新和降级，而不是一旦写入就永久可信。

4.3 不要把“Context Window”当作系统边界

OpenAI 的 Harness Engineering 经验强调：让 Agent 能够理解大型代码仓库，关键不在于把一份巨大的说明书全部放进 Prompt，而是给它一张地图，指向结构化、可验证、可持续维护的仓库知识。这个思路把上下文工程从 Token 管理扩展到了知识的可发现性。

05 · 六阶段上下文生命周期：把抽象概念变成工程流程

下面这套六阶段流程是本文的综合模型。它强调每个阶段都有输入、输出和质量检查点，因此可以被记录、评测和迭代。

阶段关键问题典型操作输出质量检查
1. Define本轮要完成什么？解析目标、约束、验收标准、风险等级Task State目标是否可判定？约束是否冲突？
2. Retrieve需要哪些外部信息？RAG、JIT 搜索、文件读取、数据库和工具调用Evidence Candidates相关性、来源、时效、权限
3. Process如何把候选信息变成高信号输入？过滤、排序、去重、摘要、结构化、压缩Context Pack关键事实是否丢失？冲突是否标记？
4. Assemble模型本次具体看到什么？组织系统指令、工具、示例、状态和证据Inference ContextToken 预算、优先级、边界、版本
5. Execute模型采取了什么行动？推理、调用工具、执行代码、接收观察Action & Observation输出是否受限？工具是否成功？
6. Persist什么应该留给下一轮或下一会话？写日志、更新状态、生成摘要、维护记忆Durable State是否有证据？是否过期？能否回滚？

这个循环有两个重要的设计原则。第一，不是所有阶段都必须由 LLM 完成：权限检查、去重、Token 计数、Schema 校验和文件索引，通常可以交给确定性程序。第二，上下文不是越动态越好：稳定的规则与当前任务目标可以预先注入，大体量、易变化的数据则更适合按需获取。

06 · 检索：预加载、Just-in-Time Retrieval 与混合策略

6.1 预加载：快，但容易把噪声提前带进来

传统 RAG 常在模型推理前完成检索：把用户问题转成向量，召回 Top-K 文档，再把片段放入 Prompt。优点是路径短、容易控制延迟，也适合知识范围明确、查询模式稳定的任务。缺点是 Top-K 不一定等于当前真正需要的信息；预取过多会增加噪声，索引也可能落后于真实数据。

6.2 JIT：先拿到地图，需要时再读取细节

Anthropic 的 Context Engineering 文章强调 Just-in-Time Context：Agent 不必预先加载全部数据，可以先持有轻量级标识符，例如文件路径、查询、URL 或索引；当任务推进到某一步，再通过工具读取最相关的内容。这样既能减少初始 Token 消耗，也能使用文件名、目录结构、时间戳和 Schema 等元数据辅助判断。

6.3 混合策略：固定核心 + 按需发现

对复杂 Agent，通常更合理的做法不是“全部预加载”或“全部现场搜索”，而是：

  • 固定核心：系统身份、不可违反的安全规则、当前目标、验收标准。
  • 轻量地图：文件目录、文档索引、可用工具列表、数据库 Schema、项目状态摘要。
  • 动态证据：只在当前子问题需要时读取具体文件、日志、网页或数据库记录。
  • 回写状态：将验证后的关键结果保存到外部状态，而不是每次重放完整工具输出。
什么时候选 JIT？ 当数据规模很大、信息更新频繁、任务路径不确定，而且 Agent 有可靠工具可以探索时，JIT 的价值更明显。若数据规模小、查询固定、延迟极敏感，预计算检索可能更合适。Anthropic 也明确指出，运行时探索会带来额外延迟和工具使用成本。

07 · 处理：过滤、排序、去重与压缩

检索到的内容只是候选集，不应直接全部进入模型。上下文处理的目标是把原始资料变成有结构、有来源、可比较的证据。

7.1 为每个候选片段建立可解释的评分

可以为每个信息片段记录六类属性：与当前目标的相关性、时间新鲜度、来源可信度、对下一步行动的价值、Token 成本和安全风险。一个教学用评分式如下：

EQUATION 3 · CANDIDATE PRIORITY
Score(di)=αrRi+αfFi+αpPi+αaAi−λTi−μSi
R：相关性；F：新鲜度；P：来源可信度；A：行动价值；T：Token 成本；S：安全风险。权重应由任务与评测决定，不存在适用于所有系统的固定数值。

7.2 去重与冲突处理

重复内容会浪费预算，还可能造成“多个副本看起来像多个独立证据”的错觉。去重不只看字符串相同，还要识别同一事实的不同表达、相同文档的多个切片，以及来自同一上游来源的转述。

如果两个可信来源发生冲突，不要简单把它们压成一个“平均事实”。应保留来源、时间、版本和冲突状态；必要时将“尚未确认”显式传递给模型。对于快速变化的数据，时间戳通常比语义相似度更重要。

7.3 摘要不是无损压缩

摘要能够缩短上下文，但会改变信息的表达形式，也可能丢失边界条件、数字、否定词和来源关系。工程上应区分：

  • 原文保留：法律条款、精确参数、用户明确约束、未验证的关键证据。
  • 结构化提取：当前目标、决策、已完成步骤、待办、文件路径、实体 ID、证据引用。
  • 可丢弃信息：重复工具输出、过期调试日志、与当前目标无关的闲聊。
  • 仅保留指针：大文件、数据集、代码仓库、长网页和完整运行日志。

08 · 组装：究竟哪些信息应该进入模型窗口？

完成筛选之后，还需要明确上下文的层次和边界。一个可维护的上下文包通常包括以下部分：

01 · System / Policy：身份、行为边界、输出规范与安全约束。

02 · Task Contract：本轮目标、验收条件、当前优先级、不能破坏的状态。

03 · Tool Interface：工具名称、参数、返回 Schema、失败语义与权限边界。

04 · Canonical Examples：少量有代表性的正确行为与边界案例。

05 · Retrieved Evidence：按需读取的证据片段，带来源、时间与可信度。

06 · Recent State：最近行动、工具观察、当前计划、未完成事项。

07 · Output Reserve：为最终答案、结构化结果或下一步动作预留容量。

Anthropic 建议 System Prompt 清楚、直接，并保持适当的抽象层次：太具体会变得脆弱，太宽泛又无法指导行为。工具则应该边界清晰、功能重叠少、输入参数明确、输出尽量节省 Token。Few-shot 示例应优先选择少量典型案例，而不是把所有边缘情况都堆进 Prompt。

09 · 长任务：Trim、Summary、Compaction 与 Sub-agents

当 Agent 连续工作几十分钟、数小时，甚至跨越多个上下文窗口时，历史消息会不断增长。此时必须决定哪些内容继续保留、哪些内容可以压缩、哪些任务应该隔离到独立上下文。

策略做法优点主要风险适用场景
Trimming删除旧轮次，只保留最近 N 轮确定性强、低延迟、不会引入摘要改写旧约束、ID 和决策可能突然丢失短流程、近期信息最重要的操作型任务
Summarization把旧消息压缩成结构化摘要保留长期目标与决策，缩短历史细节丢失、摘要偏差、错误传播长对话、分析与多阶段协作
Compaction将接近窗口上限的上下文压缩并继续新窗口支持长时间连续执行压缩后的状态必须经过保真与恢复评测长程工具循环、代码迁移、持续研究
Persistent Memory把经验写入会话外存储，未来按需读取跨会话复用、可积累知识陈旧记忆、错误事实、隐私和权限问题重复任务、个性化、长期项目
Sub-agent Isolation将子任务交给独立上下文的专门 Agent隔离噪声、并行探索、降低主上下文压力摘要交接丢失细节，协调与验证成本增加复杂研究、多文件分析、并行代码审查

9.1 Trimming：保留最近 N 轮

OpenAI Agents SDK Cookbook 的一个实现把“一轮”定义为一条用户消息及其后续助手回复、工具调用和工具结果，直到下一条用户消息。系统从历史尾部向前寻找最后 N 个用户轮次，并保留这些轮次之后的全部项目。这样能避免把一次工具调用的结果从它所属的任务中间拆开。

这种方法的优点是简单、容易复现；缺点也很直接：较早的任务约束、用户偏好或关键实体 ID 可能被整体删除。只保留最近 N 轮，并不意味着最近 N 轮就一定包含所有重要信息。

9.2 Summarization：把长历史压成状态摘要

摘要更适合长期连续任务，但不能只写“我们讨论了什么”。更有用的结构是：

current_goal: 当前目标
hard_constraints: 不可违反的约束
decisions: 已确认的决策及理由
verified_facts: 已验证事实与证据位置
open_questions: 尚未解决的问题
completed_steps: 已完成工作
next_actions: 下一步动作
stale_or_rejected: 已废弃方案与原因

这里尤其需要保留“已拒绝的方案”和“未验证的假设”，否则后续 Agent 可能重新提出旧方案，或者把猜测误认为事实。

9.3 Compaction：跨窗口继续同一项工作

Anthropic 将 Compaction 描述为：在上下文接近上限时，高保真地总结当前状态，并在新的上下文窗口中继续任务。OpenAI 在 2026 年介绍 Responses API 的计算环境时，说明其原生 Compaction 可以生成 Token 高效的状态表示，并在后续上下文中保留关键状态与高价值的早期内容。

要特别区分：Compaction 主要解决当前长任务如何跨越窗口边界继续；Persistent Memory 解决当前会话结束之后，未来任务如何重用经验。前者不自动等于长期记忆，后者也不应该只是压缩后的聊天记录。

9.4 Sub-agents：用隔离换取清晰的工作上下文

当一个主 Agent 同时承担文献检索、代码审查、数据分析和报告写作时，所有细节都会争夺同一个窗口。可以把不同工作交给独立的子 Agent：每个子 Agent 负责局部问题，保留自己的检索与推理细节，最后只向协调者返回经过整理的结论、证据和未解决事项。

隔离并不会自动提升质量。主 Agent 必须验证子 Agent 的结论，交接摘要也应携带来源和不确定性；否则，系统只是把上下文污染从一个窗口转移到了另一个窗口。

10 · Agent Memory：跨会话知识如何形成？

Anthropic 在 2026 年 11 月发布的《The components of agent memory》中给出了一个更细的层次结构：会话记录、记忆笔记、记忆表示（例如 Wiki）和预先注入到新会话的上下文。它还讨论了 Dreaming：Agent 在任务间隙回看日志、验证笔记、修正错误、合并重复信息，并把更稳定的知识整理成可导航的表示。

10.1 四层记忆结构

  • Transcript / Event Log：原始事件、用户消息、工具调用和观察结果。优点是保留事实来源，缺点是体积大、噪声多。
  • Memory Notes：从经历中抽取的事实、规则、用户偏好、任务经验和失败教训。每条笔记都应该能够追溯到原始证据。
  • Memory Representations：把大量笔记组织成 Wiki、主题索引、关系图或可搜索的知识结构，让 Agent 可以沿着链接逐层发现信息。
  • Injected Context：每个新会话预先注入的极小核心，包括当前目标、重要约束和知识入口。它应当足够小，避免长期占据窗口。

10.2 Dreaming：为什么记忆需要离线整理？

在会话中即时写入记忆，可以让经验快速留存，但 Agent 当时并不知道未来哪些信息最重要；如果每一步都花大量精力写笔记，又会分散当前任务的注意力。Dreaming 提供了另一种思路：在任务间隙回顾多轮记录，检查事实是否正确、合并重复知识、修正过时笔记，并建立更好的知识导航。

Anthropic 的文章展示了 Dreaming 用原始会话记录纠正错误记忆、构建 Wiki 表示以及控制注入层规模的案例。它也强调了风险：被注入的错误笔记可能在后续会话中反复影响决策；知识表示需要持续维护，不能把“写进 Memory”当成“已经验证”。

关键原则：记忆不是“越多越好”，而是对未来有用、能够追溯、可以纠错、适合在正确时机被检索的信息。

10.3 Memory、Session State 和 Compaction 的边界

Session State 是当前任务的运行状态；Compaction 是为了跨窗口继续任务而做的上下文压缩；Memory 是为了未来会话可复用而保存的经验。一个项目可以同时使用三者，但必须分别定义写入时机、保留期限、更新策略和权限。

11 · Harness Engineering：让知识可发现、可验证、可执行

如果说 Context Engineering 关心“哪些信息进入模型”，那么 Harness Engineering 还要回答“模型如何找到这些信息、如何在安全环境中操作、如何知道自己做对了”。

OpenAI 在 2026 年 2 月的 Harness Engineering 文章中，总结了一个很有代表性的经验：不要把一个超长 AGENTS.md 当作整个知识库，而应该让它成为目录或地图，指向结构化的文档、架构说明、执行计划、质量标准和参考资料。文章还强调通过 Lint、结构测试和文档维护任务，验证这些知识是否仍然有效。

KNOWLEDGE LAYER

可发现的知识

短入口文件、文档索引、架构地图、可搜索的事实库、执行计划和决策日志。

EXECUTION LAYER

可验证的环境

文件系统、沙箱、测试、日志、指标、工具权限、可重复执行和失败恢复。

OpenAI 在 2026 年 3 月的 Responses API 计算环境文章中，还介绍了如何通过 Shell、持久化容器工作区、文件系统、结构化存储和受限网络，让 Agent 执行复杂任务；工具输出可以设置上限，避免把完整日志无差别地塞回模型。

11.1 一个好的仓库知识入口应该长什么样？

repository/
├── AGENTS.md                 # 短入口：规则、地图、下一步去哪里
├── ARCHITECTURE.md           # 系统结构与依赖边界
├── docs/
│   ├── index.md              # 文档索引
│   ├── design/               # 设计决策与核心原则
│   ├── plans/                # 当前计划、进度、决策日志
│   ├── references/           # 外部规范与技术参考
│   └── quality/              # 质量标准、已知缺口
├── src/
├── tests/
└── scripts/                  # 可验证的自动化检查

这是一种知识组织示例，不是要求每个仓库照搬目录名。关键在于：入口短、索引清楚、事实有来源、计划有状态、规则能自动检查。Agent 应该先读取地图，再按当前任务逐步加载细节。

11.2 Harness 与 Context Engineering 的互补关系

仅靠上下文拼接无法弥补一个不可观察、不可测试、权限混乱的执行环境；反过来，再好的沙箱和工具，如果没有清晰的上下文管理，也会因为错误状态和大量无关输出而失效。可靠 Agent 需要同时具备信息组织、工具执行、状态持久化、验证反馈和权限治理。

12 · 安全：上下文也是攻击面

上下文越丰富，模型接触到的外部内容也越多。网页、PDF、Issue、代码注释、邮件和工具返回值都可能包含恶意指令或错误信息。检索系统如果把这些内容不加区分地拼接进上下文，就可能让不可信数据伪装成系统指令。

风险发生方式缓解措施
Prompt Injection外部文档包含要求忽略原指令、泄露秘密或调用工具的文本标记不可信来源；数据与指令分层；工具执行前做策略检查
Context Poisoning错误工具结果或错误摘要被反复带入后续轮次保留来源、时间、验证状态；关键事实回查原文
Stale Context旧配置、过期计划或已废弃 API 被误当作当前事实记录版本与更新时间；设置过期策略；读取权威来源
Data Leakage不必要的个人信息、凭据或内部文件进入模型或子 Agent最小权限、字段脱敏、按任务隔离、敏感信息不进入持久记忆
Tool Confusion工具名称重叠、Schema 模糊、参数缺少约束减少工具重叠；使用严格 Schema；校验参数与副作用

一个实用做法是给每条上下文数据附加元信息：source、timestamp、trust_level、verification_status、scope。模型可以看到必要的证据内容，但不能因为某段文档写着“忽略系统指令”就把它提升为高优先级指令。

还要注意，摘要与 Memory 都可能成为持久化攻击面。错误信息一旦被压缩成简洁、肯定的陈述，未来的模型可能更难意识到它最初只是一个不可信的工具输出。因此，压缩时必须保留来源和不确定性。

13 · 如何评估 Context Engineering 是否真的有效？

不能只比较 Prompt 长短或 Token 使用量。一个上下文方案可能更省 Token，却丢失关键约束；也可能召回率很高，但把无关文档塞进模型后降低了最终任务成功率。评估应该从上下文层和任务层同时进行。

指标维度可测量指标想回答的问题
信息质量Recall@K、Evidence Precision、来源覆盖率、冲突识别率真正需要的信息有没有被找回来？
上下文效率输入 Token、重复率、压缩率、有效信息密度每单位预算保留了多少有用信息？
任务表现任务成功率、约束遵循率、答案准确率、完成时间上下文优化是否改善了真实结果？
工具表现工具选择准确率、参数正确率、重试率、无效调用数上下文是否帮助模型正确行动？
长程稳定性状态恢复成功率、跨窗口事实保留率、摘要漂移率长任务是否还能保持一致？
安全与治理注入成功率、越权调用率、敏感信息暴露率、过期记忆比例上下文是否引入新的安全风险？

13.1 做消融，而不是只看一个总分

建议构建至少四个基线：完整历史、最近 N 轮裁剪、结构化摘要、固定核心加 JIT 检索。保持模型、任务、工具和评测集一致，比较任务成功率、Token、延迟、错误类型和证据保留情况。再分别关闭记忆、工具 Schema、检索、压缩和来源标记，观察各组件的独立贡献。

13.2 用失败案例驱动上下文改进

每次失败都应该回答：信息没有检索到？检索到了但排序太低？摘要把否定条件丢掉了？工具输出太长？旧状态覆盖了新目标？子 Agent 交接时丢失了证据？这些失败属于不同阶段，不能全部归因于“Prompt 写得不好”。

评测闭环：任务轨迹 → 失败归因 → 上下文策略调整 → 固定回归集 → 再次评测。只有在任务表现和风险指标上都得到改善，才能认为上下文工程真正有效。

14 · 一个可落地的工程蓝图

下面给出一个与具体模型厂商无关的参考控制流程。它强调确定性组件负责筛选和边界检查，模型负责理解任务、选择下一步动作以及处理需要语义判断的内容。

def run_agent_turn(task, durable_state, tools, token_budget):
    # 1. Define: 固定本轮目标与不可丢失的约束
    goal = parse_goal(task)
    invariants = load_policy_and_project_constraints(goal)

    # 2. Retrieve: 先读轻量索引，再按需取回证据
    pointers = search_index(goal, durable_state.index)
    candidates = fetch_relevant_items(pointers, goal)

    # 3. Process: 去重、标记来源、排序并压缩
    candidates = deduplicate(candidates)
    candidates = attach_provenance_and_freshness(candidates)
    candidates = filter_untrusted_or_out_of_scope(candidates)
    candidates = rank_by_relevance_value_cost_and_risk(candidates)

    # 4. Assemble: 保留输出空间，按预算组装上下文
    context = pack_context(
        invariants=invariants,
        goal=goal,
        tool_schemas=tools.minimal_schemas(),
        evidence=candidates,
        recent_state=durable_state.recent_state,
        token_budget=token_budget,
    )

    # 5. Execute: 模型提出行动，Harness 执行并限制返回
    action = model_step(context)
    observation = execute_with_permissions_and_output_caps(action)

    # 6. Persist: 保存事件，更新状态；记忆写入需经过验证
    durable_state.append_event(action, observation)
    durable_state.update_task_state(goal, action, observation)
    maybe_consolidate_verified_memory(durable_state)

    return observation, durable_state

这段伪代码的价值不在于某个函数名，而在于责任边界：

  • 检索系统负责找候选，不直接决定哪些内容一定可信。
  • 上下文组装器负责预算和结构，不负责伪造事实。
  • 工具执行层负责权限、Schema、超时和输出上限。
  • 状态存储层负责可追溯记录；长期记忆需要单独验证。
  • 评测层负责判断优化是否改善真实任务，而不是只看 Prompt 是否更短。

14.1 建议的最小可用版本

PHASE A

先建立状态结构

明确 goal、constraints、decisions、evidence、open questions、next actions。

PHASE B

再建立检索边界

使用轻量索引与按需读取，避免每轮加载完整文件或历史。

PHASE C

最后加入长期记忆

保存已验证经验，记录来源与版本，并定期清理过期信息。

不要一开始就搭建复杂的多 Agent 记忆平台。先用一个结构化状态文件、可检索的外部文档和确定性 Token 预算器，验证它能否解决真实失败案例；只有在单 Agent 的上下文管理已经成为瓶颈时，再引入更复杂的分工与持久化架构。

15 · 失败模式与设计边界：没有一种策略适合所有任务

任务特征优先考虑需要警惕
短流程、每轮相对独立确定性裁剪、最小工具集最近 N 轮仍可能包含大体量工具输出
长对话、约束需要持续保留结构化摘要 + 近期原文摘要遗漏精确 ID、否定条件和来源
大型代码仓库或文档集仓库地图 + JIT 搜索 + 文件读取工具探索成本、陈旧索引、权限越界
重复任务、跨会话工作分层 Memory + 检索 + 纠错机制记忆过期、错误固化和隐私泄漏
复杂并行研究子 Agent 隔离 + 证据化交接协调成本、重复工作和交接失真
严格时延或 Token 成本限制预计算检索、缓存、工具输出裁剪过度压缩可能降低准确率

还需要明确几个常见误区：

  1. 把所有信息都塞进 System Prompt：导致指令过长、维护困难、重要约束不突出。
  2. 把所有历史都保存为原文并每轮重放：把持久化存储与工作上下文混为一谈。
  3. 把摘要当成事实：摘要是一个新的信息表示，需要来源、验证和更新。
  4. 把 RAG Top-K 当作最终上下文：召回结果还需要过滤、去重、冲突处理和预算控制。
  5. 把更大的窗口当成架构升级：更大容量不能自动修复工具、记忆、状态和安全设计问题。
  6. 只优化 Token 成本：如果任务成功率、可靠性或安全性下降，Token 更少并不是工程进步。
最终判断：Context Engineering 不是一套固定的 Prompt 模板，而是一套围绕任务状态、信息来源、有限预算、执行反馈与长期知识组织的系统设计方法。最好的系统不是拥有最多上下文的系统，而是在正确的时间把正确的信息交给正确的 Agent。
