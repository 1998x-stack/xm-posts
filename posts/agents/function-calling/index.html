Understanding Function Calling

模型如何把一句自然语言，变成一个可验证、可授权、可执行的外部动作？从 JSON Schema、工具调用协议到 Agent Runtime，理解 LLM 与真实软件系统之间的接口。

研究专题 · Tool Use & Function Calling约 35 分钟OpenAI · Anthropic · Toolformer · MCP

01 · 为什么模型需要工具？

一个语言模型可以解释“如何查询天气”，但如果它没有访问天气服务的能力，它就不能知道东京此刻的真实天气；它可以写出一封邮件，却不能仅凭文字生成就证明邮件已经发送。

这不是简单的知识缺失，而是模型内部计算与外部世界状态之间存在边界。模型参数保存的是训练形成的统计规律，不是一个持续更新的数据库；模型输出的是 token 序列，不会自动变成数据库查询、支付请求或文件修改。

先建立正确直觉：Function Calling 不是“让模型直接运行 Python”，而是让模型用一种约定好的结构，向宿主应用提出工具调用请求。真正访问网络、读写文件或修改业务状态的，是应用侧的执行环境。

读取信息

“查一下东京今天的天气。”

需要外部数据源；模型不能凭训练记忆保证实时性。

执行动作

“把周五下午三点的会议改到四点。”

需要身份验证、日历权限、冲突检查和实际写入。

这两类任务都可以通过工具接口连接外部系统，但风险完全不同：读取天气通常是低风险查询；修改日历已经产生副作用，必须检查调用者身份、授权范围和时间冲突。

因此，真正的问题不是“模型能否输出一个 JSON”，而是：模型能否选对工具、填对参数，应用能否安全执行，并且双方能否正确传递结果？

02 · Function Calling 究竟是什么？

Function Calling（也常称 Tool Calling）是一种模型—应用协作机制：开发者向模型声明一组可用工具及其输入契约，模型根据当前任务选择是否调用，并生成结构化的工具名称和参数；应用接收请求、执行真实函数，再把结果返回模型。

它至少包含四个不同对象：

  1. Tool definition：工具名称、用途说明、输入 Schema，有时还有输出 Schema。
  2. Tool call：模型提出的调用意图，通常包含调用 ID、工具名称和参数。
  3. Tool execution：应用或工具运行时执行的真实代码。
  4. Tool result：执行结果，以与调用 ID 对应的消息返回模型。

把它写成一个抽象调用记录：

q=(callid,toolname,arguments)
式 1 · 这是本文用于解释协议的抽象表示，不是某一家厂商的原始消息类型定义。

这里的 call_id 不是装饰字段。一次模型回复可能包含多个工具调用，执行器必须把每个结果准确地关联回对应请求；否则在并发或多轮执行中，模型可能把 A 工具的结果误认为 B 工具的结果。

OpenAI 将函数定义为一种特定类型的工具：它通过 JSON Schema 描述参数，由模型把调用数据交给应用；平台还提供内置工具和其他自定义工具形式。Anthropic 的 Tool Use 采用相近的协作思想，但消息块与执行边界有自己的协议定义。参见 OpenAI Function Calling 文档与 Anthropic Tool Use 文档。

03 · 一次完整调用：模型只负责提出，运行时负责执行

最重要的心智模型是一个闭环，而不是一次性“问答”。模型收到工具定义后，可能选择普通回答，也可能输出一个或多个工具调用；应用执行后把结果送回模型，模型再决定回答、继续调用，或者报告失败。

OpenAI 官方文档把标准流程概括为五步：向模型提供工具定义、接收工具调用、在应用侧执行、将工具输出再次提交模型、接收最终回答或更多调用。注意第 3 步明确发生在应用侧，而不是模型输出 token 的瞬间。[OpenAI Function Calling · Tool calling flow]

  1. 声明能力：应用把可用工具、参数结构和说明传给模型。
  2. 选择与生成：模型根据用户目标决定是否调用，并给出工具名称和参数。
  3. 校验与执行：应用解析调用，验证结构、业务规则和权限，再调用真实函数。
  4. 结果关联：执行器用原调用 ID 回传成功数据或结构化错误。
  5. 继续决策：模型读取结果，生成答案，或提出下一次调用。
边界提醒：模型说“我已经帮你取消订单”，只有在执行器确认取消操作成功、并返回可核验结果后，才有事实依据。模型生成的自然语言不是外部系统的执行回执。

04 · 调用消息长什么样？

以一个只读天气查询为例。应用声明 get_weather，模型返回一个结构化调用。下面是便于理解的 Responses API 风格示意，重点是字段关系，而不是要求所有 SDK 都使用完全相同的封装方式。

{
  "type": "function_call",
  "call_id": "call_7f31",
  "name": "get_weather",
  "arguments": "{\"location\":\"Tokyo\",\"unit\":\"celsius\"}"
}

这里有三个关键点：name 必须匹配已声明且当前可用的工具；arguments 在某些 API 响应中是 JSON 编码的字符串，应用必须解析并校验；call_id 用于关联后续工具结果，不能丢失或由执行器随意替换。

应用执行后，向模型回传与该调用 ID 对应的输出。Responses API 中可使用 function_call_output 项：

{
  "type": "function_call_output",
  "call_id": "call_7f31",
  "output": "{\"temperature_c\":18,\"condition\":\"cloudy\"}"
}

模型收到结果后才有依据生成最终说明。如果工具返回超时、权限拒绝或业务错误，也应回传可辨识的错误状态；不要把错误文本包装成成功数据。

协议差异：较早的 Chat Completions 使用 tool_calls 数组与 tool 角色消息；Responses 使用类型化的 output items，并用 call_id 关联输入输出。迁移时应按当前 API 文档处理，不要把两套消息外形混写。[OpenAI Responses API migration guide]

05 · Schema：它是结构化契约，不是安全边界

工具定义不是给模型看的随意备注，而是一份接口契约。好的定义至少回答四个问题：工具做什么、何时使用、参数如何组织、结果代表什么。

下面是一个 OpenAI Responses API 风格的函数定义。这里把 location 和 unit 都设为必填，并关闭额外字段，以便演示严格的结构契约：

{
  "type": "function",
  "name": "get_weather",
  "description": "Get current weather for a city. Use only for current conditions.",
  "parameters": {
    "type": "object",
    "properties": {
      "location": {"type": "string", "description": "City name, e.g. Tokyo"},
      "unit": {"type": "string", "enum": ["celsius", "fahrenheit"]}
    },
    "required": ["location", "unit"],
    "additionalProperties": false
  },
  "strict": true
}

Strict Mode 到底保证什么？

OpenAI 文档建议对 function tools 使用 strict: true。其严格模式基于 Structured Outputs，并要求对象的 additionalProperties 为 false，且 properties 中的字段都出现在 required 中。若要表达“可选”，通常要把字段类型设计为可空，而不是简单地从 required 删掉。[OpenAI · Strict mode]

这能显著降低结构错误，却不能证明参数真实、操作合法或用户已授权。模型可以生成一个结构完全合规、但业务上错误的订单 ID；也可以在 Schema 合规的情况下，提出用户从未授权的删除操作。

安全原则：不要把“模型输出符合 JSON Schema”当成“可以直接执行”。Schema 是第一道门，不是授权系统。

可以把应用侧的最低验证条件写成一个逻辑合取：

Valid(q)=J(q)∧S(q)∧B(q)∧P(q)
式 2 · J = JSON 可解析，S = Schema 合法，B = 业务规则通过，P = 调用者权限允许。

这里的四个条件是工程检查清单，不是模型训练目标。即使使用 Strict Mode，应用也必须在真实执行边界重新验证。

06 · JSON Mode、Structured Outputs 与 Function Calling 有什么区别？

这三个概念经常被放在一起讨论，因为它们都可能输出 JSON；但它们解决的是不同问题。

机制核心问题是否选择工具是否执行外部动作
JSON Mode尽量保证输出是合法 JSON不负责不负责
Structured Outputs让输出符合指定结构 Schema不必然不负责
Function Calling从可用工具中选择，并生成调用参数是由应用或托管工具运行时负责

举例：如果你希望模型把一段简历解析成固定字段，Structured Outputs 可能已经足够；如果你希望模型查找某个候选人的日历空档，并创建会议，就需要工具调用以及真正的日历执行逻辑。

它们也可以组合使用：Function Calling 使用 JSON Schema 描述工具参数；某些平台的严格模式会借助结构化输出约束参数格式。但“输出格式受约束”仍然不等于“业务动作被授权”。

07 · 一次调用还是多次调用？顺序与并行

用户的一句话可能对应多个工具动作。比如“查一下东京和大阪的天气，再比较哪个更冷”：两个城市的天气查询互不依赖，可以并行；但“先查询库存，再按库存结果创建订单”有数据依赖，必须先后执行。

若每次模型往返耗时为 t，工具执行耗时分别为 e₁, e₂, …, eₙ，忽略调度和聚合开销时：

Tseq≈nt+∑i=1nei
Tparallel≈t+max1≤i≤nei
式 3 · 这是解释延迟结构的简化模型，不是平台性能承诺；真实系统还受排队、限流、重试和模型调度影响。

并行调用不是越多越好。需要确认调用之间没有写入冲突、资源竞争、速率限制或顺序依赖。即使模型能在一个回复里提出多个工具调用，执行器也必须逐个检查其权限和副作用。OpenAI 文档说明可通过 parallel_tool_calls 控制并行工具调用行为；不同模型和 API 的支持范围应以当前文档为准。[OpenAI · Parallel function calling]

08 · OpenAI 与 Anthropic：相同思想，不同消息协议

两家平台都把工具使用视为模型与外部执行环境之间的结构化交互，但具体字段、消息角色、工具定义方式和执行位置并不完全相同。阅读 SDK 代码时，应该区分“共同的系统概念”和“某家 API 的消息格式”。

维度OpenAI Responses APIAnthropic Messages API
工具定义type: function、name、description、parametersname、description、input_schema
模型调用表示output item 中的 function_callassistant 内容中的 tool_use block
调用停止信号检查响应中的工具调用项和状态客户端工具通常以 stop_reason: tool_use 表示

执行位置自定义函数通常由应用执行；内置工具可由平台执行客户端工具由应用执行；Anthropic 托管工具可由 Anthropic 执行
核心工程责任执行前验证参数、权限和副作用执行前验证参数、权限和副作用

Anthropic 的 Tool Use 文档明确区分 client tools 和 server tools：对于用户自定义的客户端工具，Claude 返回 tool_use block，应用执行操作后再提交 tool_result；托管工具则可以在 Anthropic 基础设施上运行。[Anthropic · Tool use with Claude]

因此，不能只凭“模型输出了一个 tool call”就假设执行位置相同。集成前要回答：谁拥有凭据？谁执行函数？谁保存状态？工具输出如何回到模型？错误和拒绝如何表达？

跨平台抽象建议：在自己的应用内部定义统一的 ToolCall / ToolResult 类型，再由 OpenAI、Anthropic 或 MCP adapter 负责协议转换。业务执行器不应被某一家供应商的消息字段绑死。

09 · 从 Toolformer 到 ToolLLM：模型怎样学会使用工具？

API 协议解决的是“怎样表达调用”。但模型为什么会在合适的时候选对工具、填对参数？这属于模型能力与训练数据问题。Function Calling 并不等于某一种训练算法；它既可以通过提示和 Schema 驱动，也可以通过 SFT、偏好优化、工具轨迹训练等方式提升。

Toolformer：让模型自监督地学习何时调用

Schick 等人在 2023 年提出 Toolformer。其核心问题是：语言模型擅长生成文本，却可能不擅长精确计算、查询最新事实或调用外部服务。Toolformer 让模型学习何时调用 API、调用时传入什么参数，以及如何把工具结果纳入后续 token 预测。论文使用少量工具示例，通过候选调用和损失变化筛选有用调用，而不是把所有工具调用都视为有益。[Toolformer, NeurIPS 2023]

这揭示了工具使用的三个可学习子问题：是否调用、调用哪个工具、如何组织参数。工具结果还必须以适当方式融入后续生成，否则“调用成功”并不保证“任务完成”。

Gorilla：API 文档变化时，不能只靠记忆

Gorilla 研究大规模 API 调用生成，并结合检索系统让模型在测试时参考更新的 API 文档。其动机之一是 API 版本、参数和用法会变化，模型仅凭参数记忆容易幻觉出错误的调用形式。论文使用 Hugging Face、TorchHub、TensorHub API 相关数据构建 APIBench。[Gorilla, 2023]

工程启示是：当工具库频繁变化时，工具说明和文档检索可能比继续堆叠旧提示词更可靠；模型必须看到当前版本的真实契约。

ToolLLM / ToolBench：工具使用需要规模化数据和评测

ToolLLM 提出由数据构造、模型训练和评估组成的工具使用框架。论文报告其 ToolBench 收集了 16,464 个真实 RESTful API，覆盖 49 个类别，并构造单工具和多工具指令及调用路径，再以 ToolEval 评估任务完成情况。[ToolLLM / ToolBench, 2023]

这个数字说明工具空间本身就可能非常庞大，但不能据此推断“工具越多，Agent 越强”。大量相似、描述含糊或低质量的工具会增加选择难度、提示 token 和错误机会；工具检索、命名空间、分层暴露与评测因此变得重要。

10 · MCP、工具发现与程序化调用：从单个函数走向工具生态

当一个 Agent 只有两三个工具时，把所有 Schema 一起放进上下文可能很简单；当它需要连接 GitHub、数据库、搜索、文件系统、监控平台和企业内部服务时，问题就从“能否调用一个函数”变成“如何发现、管理和编排一整个工具生态”。

MCP：标准化工具如何被发现和调用

Model Context Protocol（MCP）把工具能力放在客户端与服务器之间的协议层。服务器可以通过 tools/list 暴露工具列表，客户端通过 tools/call 请求执行。MCP 解决的是工具发现和互操作问题；它不是 Function Calling 的同义词，也不会替应用自动解决模型决策、权限验证和审批策略。[MCP Tools Specification]

Tool Search：不要一开始就把几百个 Schema 全塞进上下文

Anthropic 在 2025 年的 Advanced Tool Use 工程文章中介绍了按需工具发现：把不常用工具延迟加载，模型先搜索相关工具，再把匹配的工具定义加入上下文。其动机是大量工具定义会占用上下文预算，并可能让真正相关的工具更难被模型关注。文中还介绍 Tool Use Examples，让工具定义不仅包含字段结构，也包含正确使用方式。[Anthropic · Advanced Tool Use]

Programmatic Tool Calling：让代码承担确定性的编排

当任务需要几十次重复调用、循环、条件判断、数据过滤或聚合时，每一步都让模型重新推理，可能产生大量往返和中间结果。Anthropic 与 OpenAI 的程序化工具调用方案都在探索：让模型生成一段受控代码，在执行环境中组合工具调用，只把必要的最终结果交回模型。[Anthropic Advanced Tool Use] [OpenAI Programmatic Tool Calling]

OpenAI 的 Programmatic Tool Calling 指南强调：代码适合确定性的循环、条件和数据处理；直接工具调用则适合单次操作或需要模型重新判断的步骤。无论调用来自模型还是程序，应用仍需检查参数、权限，并在高影响操作前执行审批；尽可能设计幂等操作，避免重试导致重复副作用。[OpenAI · Programmatic Tool Calling]

11 · 如何设计模型真正会用的工具？

Anthropic Engineering 在《Writing effective tools for agents》中提出一个重要视角：传统函数主要面向确定性程序员；Agent 工具则要面对非确定性的模型。模型可能误解用途、漏掉可选参数、选择错误工具，或把工具返回中的无关文本当成指令。因此，工具的“可用性”不仅由代码实现决定，也由接口和上下文设计决定。[Anthropic · Writing effective tools for agents]

  • 名字具体：search_customer_orders 比 search 更能说明对象与动作。
  • 说明何时用：写清适用场景、数据范围和不适用情况。
  • 参数有语义：不仅说明 date 是字符串，还要说明时区、格式、是否包含边界。
  • 返回可行动：给出稳定字段、状态码、分页游标和明确错误，不返回大段无法解析的自然语言。
  • 工具职责单一：避免一个工具同时承担查询、删除、付款和发通知等不同权限。

工具数量与上下文预算

工具定义本身会消耗上下文。名称、描述、参数 Schema、示例和历史调用都会成为模型可见信息。工具过多时，可以按领域命名空间分组，或用检索按需加载；工具太少、过于宽泛时，模型又可能需要在一个工具中组合大量不相关参数。

Anthropic 的工程建议包括：选择真正需要的工具、通过命名空间表达边界、返回有意义且节省 token 的上下文，并通过 Agent 评测反复改进工具描述。工具设计不能只凭开发者感觉，应使用真实任务集验证模型是否能正确选择和完成操作。

一个工具接口的审查清单

  • 输入字段是否最少且足够？
  • 枚举、范围、单位、时区是否明确？
  • 空值、缺失值、默认值是否有清楚语义？
  • 返回是否包含机器可读状态和可诊断错误？
  • 是否能通过工具名和描述区分相似能力？
  • 权限和副作用是否可以在执行器侧单独控制？
  • 调用结果是否足够小，能支持下一步决策？

12 · 安全边界：工具调用会把语言错误变成真实副作用

普通聊天中的错误回答可能只是信息质量问题；接入工具后，错误可能变成错误付款、错误删文件、越权查询或敏感信息外泄。工具调用因此必须把模型输出视为不可信输入，即使模型来自可信供应商、Schema 使用严格模式也不例外。

  • 最小权限：只授予工具完成当前任务所需的最小 API scope、文件目录和数据访问权。
  • 服务端重新验证：检查调用者身份、资源归属、参数范围、速率限制和当前状态，不能依赖模型自己判断。
  • 人工确认：付款、删除、外发邮件、生产变更等高影响动作，应在执行前展示具体对象和参数并取得批准。
  • 幂等与重试：为写操作设计幂等键，区分超时、可重试错误和不可重试错误，防止重复扣款或重复创建。
  • 隔离与审计：限制网络、文件系统和凭据暴露范围；记录调用者、参数摘要、审批、执行结果和追踪 ID。
  • 不可信内容隔离：网页、邮件、文档和工具输出都可能包含间接提示注入。把外部内容当数据而非系统指令，并在动作前重新检查原始用户意图。

OpenAI 的 Agent 安全文档强调对高影响工具调用设置审批和工具级检查；OWASP 的 Prompt Injection 指南也建议在应用侧执行权限验证、参数验证和最小权限控制。结构化调用可以减少自由文本命令带来的歧义，但不能单独消除提示注入。[OpenAI · Guardrails and human review] [OWASP · Prompt Injection Prevention]

14 · Python 最小执行器：Allowlist、参数校验与 call_id

最小执行器不需要复杂 Agent 框架。它至少应该做四件事：只允许调用已注册工具、解析参数、验证字段和类型、把执行结果绑定回原始调用 ID。

from __future__ import annotations

import json
from dataclasses import dataclass
from typing import Any, Callable


@dataclass(frozen=True)
class ToolResult:
    call_id: str
    output: dict[str, Any]


def get_weather(location: str) -> dict[str, Any]:
    # 固定教学数据：不访问网络，不代表真实天气。
    return {
        "location": location,
        "temperature_c": 18,
        "condition": "cloudy",
    }


TOOLS: dict[str, Callable[[str], dict[str, Any]]] = {
    "get_weather": get_weather,
}


def execute_function_call(call: dict[str, Any]) -> ToolResult:
    if not isinstance(call, dict) or set(call) != {"call_id", "name", "arguments"}:
        raise ValueError("invalid call envelope")

    call_id = call["call_id"]
    name = call["name"]
    raw_arguments = call["arguments"]

    if not isinstance(call_id, str) or not call_id:
        raise ValueError("missing call_id")
    if not isinstance(name, str) or name not in TOOLS:
        raise ValueError("tool is not allowlisted")
    if not isinstance(raw_arguments, str):
        raise ValueError("arguments must be a JSON string")

    try:
        arguments = json.loads(raw_arguments)
    except json.JSONDecodeError as exc:
        raise ValueError("arguments are not valid JSON") from exc

    if not isinstance(arguments, dict):
        raise ValueError("arguments must be an object")
    if set(arguments) != {"location"}:
        raise ValueError("expected exactly one field: location")

    location = arguments["location"]
    if not isinstance(location, str) or not location.strip():
        raise ValueError("location must be a non-empty string")
    if len(location) > 80:
        raise ValueError("location is too long")

    output = TOOLS[name](location.strip())
    return ToolResult(call_id=call_id, output=output)


if __name__ == "__main__":
    request = {
        "call_id": "call_demo_001",
        "name": "get_weather",
        "arguments": "{\"location\":\"Tokyo\"}",
    }
    result = execute_function_call(request)
    print(json.dumps({
        "call_id": result.call_id,
        "output": result.output,
    }, ensure_ascii=False, indent=2))

完整示例与测试可以在文章目录中运行：

python posts/agents/function-calling/tool_call_demo.py
python -m pytest -q posts/agents/function-calling/test_tool_call_demo.py

这个例子只演示一个只读、确定性的本地工具。它没有实现真实用户认证、数据库事务、网络超时、速率限制或人工审批。生产系统必须把这些能力放在真实执行器边界，而不是从这个教学例子推断“已经安全”。

15 · 如何评测工具调用？不要只看 JSON 能不能解析

一个调用的 JSON 格式正确，不等于模型选对了工具；工具执行成功，也不等于最终任务已经完成。评测应该沿着完整闭环拆开，而不是只统计 Schema pass rate。

评测层建议指标典型失败
工具选择Precision / Recall、无必要调用率工具选错或不该调用却调用
参数生成Schema pass rate、字段准确率、语义匹配参数格式正确但目标 ID 错误
执行可靠性执行成功率、超时率、重试成功率工具不可用、限流、事务失败
结果理解结果引用正确率、错误解释率把失败结果当成功、忽略关键字段
任务完成End-to-end success、完成时间、成本调用都成功但用户目标没有完成
安全性越权率、审批绕过率、注入成功率模型被外部内容诱导执行未授权动作

一个实用的可靠性分解可以从条件概率链式法则出发。把任务成功分为工具选择、参数正确、执行成功和结果正确整合几个阶段：

P(success)=P(T)·P(A|T)·P(E|T,A)·P(I|E,T,A)
式 4 · T = 工具选择正确，A = 参数有效，E = 执行成功，I = 结果被正确整合。这是链式分解，不假设各阶段相互独立。

这个分解能帮助定位问题：如果 Schema pass rate 很高但任务成功率低，问题可能在工具选择、业务参数、外部服务或结果解释，而不是 JSON 格式。评测集还应包含不该调用工具的任务、相似工具之间的选择、缺失参数需要追问的任务、工具报错和恶意工具输出等边界案例。

Anthropic 的工具工程文章建议先建立真实任务评测，再迭代工具原型和描述；OpenAI 的程序化调用指南也建议同时衡量最终正确性、token、延迟、工具调用次数、重试和安全结果，而不是只看执行效率。[Anthropic tool design] [OpenAI programmatic tool calling]

16 · 局限与总结：Function Calling 不是 Agent 的全部

它擅长解决

  • 把模型意图转成结构化调用。
  • 通过 Schema 限定参数形状。
  • 连接外部 API、数据和执行能力。
  • 让调用结果进入后续模型推理。

它本身不保证

  • 工具选择一定正确。
  • 参数在业务上一定真实。
  • 调用者拥有执行权限。
  • 外部系统一定成功。
  • Agent 最终完成用户目标。

把 Function Calling 放回 Agent 系统中，可以得到一个清晰的分工：

  1. ReAct / Planning 讨论模型如何在推理、行动和观察之间组织步骤。
  2. Function Calling 定义模型如何把一个行动意图表达成结构化调用。
  3. MCP / Tool Search 解决工具如何被发现、连接和按需加载。
  4. Runtime / Guardrails 负责真实执行、权限、审批、隔离和失败恢复。
  5. Agent Evaluation 衡量完整任务是否可靠完成，而不只是调用格式是否正确。
最终心智模型：Function Calling 是 LLM 与软件世界之间的“动作接口”。模型负责提出有上下文的调用建议；Schema 负责描述结构；Runtime 负责验证和执行；工具结果负责提供新证据；评测负责确认整条链路是否真正完成任务。

继续学习可以沿着这条路线阅读：先看 ReAct 理解 Thought–Action–Observation，再看本文理解调用协议，然后阅读 SWE-agent 理解工具接口如何影响真实任务执行，最后连接 Agent Memory 研究长期任务中的上下文管理。
