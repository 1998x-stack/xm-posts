Understanding
Harness Engineering

为什么同一个大模型，接入不同的工具、上下文、验证机制与执行环境后，会表现出完全不同的软件工程能力？从 OpenAI Codex 与 Anthropic Claude 的工程实践，拆解 Agent Runtime 的设计原理。

01 · 一个模型会写代码，为什么仍然不会交付软件？

假设你给一个能力很强的模型一个看似简单的任务：“给这个网站增加分页，并确保手机端可用。”模型可能几秒钟就能写出一个分页组件。但真正完成任务，还要回答更多问题：应该改哪个页面？项目有没有现成的分页规范？数据是否应该在构建期切片？URL 是否需要独立？旧页面会不会回归？移动端是否溢出？最终部署是否成功？

这说明“生成一段正确代码”与“完成一项真实的软件工程任务”不是同一个能力。后者是一个有状态、跨多步、依赖外部工具并且必须验证结果的过程。模型需要读仓库、运行命令、观察输出、理解错误、恢复现场、保留进度，还要知道什么时候应该停止并交付。

核心问题：模型的潜在能力不会自动变成可靠的任务完成能力。它需要一个运行时系统，把目标、上下文、工具、状态、反馈、安全与验收连接起来。

可以把系统的研究对象写成：

Agent System = Model + Harness + Environment这是一个概念分解，不是数值相加。系统能力取决于三者之间的接口与协同。

Model 提供语言理解、推理和代码生成能力；Environment 提供真实的仓库、文件、浏览器、测试、日志与运行时状态；Harness 决定模型能看到什么、能做什么、如何保存状态、如何解释反馈，以及什么证据足以判定完成。2026 年一篇 AI Harness Engineering 研究预印本也将软件工程能力的分析单位从“模型单体”扩展为 model–harness–environment 系统，并提出 autonomy gap：模型看起来会写补丁，但整个系统仍无法独立、可验证地完成任务。[5]

这也改变了调试问题的方式。当 Agent 失败时，不应立刻归因于“模型不够聪明”。它可能根本没有看到相关文件、没有可用的浏览器、没有正确的测试命令、没有跨会话进度，或者缺少一个能够阻止它过早宣布完成的验证协议。

02 · Harness Engineering 的定义，以及它不是什么

本文采用一个工程化定义：Harness 是包裹基础模型、使其能够在特定环境中持续行动的运行时系统；Harness Engineering 则是设计、验证和演进这个运行时系统的工程实践。 它管理的不只是 prompt，而是一次 Agent episode 从开始到结束的完整生命周期。

Anthropic 在 2026 年《Demystifying evals for AI agents》中给出了一个很有用的术语区分：Agent harness 包装模型，让它能够调用工具和执行任务；Evaluation harness 则包装一次评测，用来运行任务、记录轨迹并打分。两者都叫 harness，但方向不同。[4]

概念主要解决的问题与 Harness 的关系
Prompt Engineering一次模型调用应该如何理解指令？是输入设计的一部分，不负责完整运行生命周期。
Agent Framework如何用库和抽象构建 Agent 应用？可用于实现 Harness，但框架本身不等于运行中的 Harness。
Agent–Computer Interface（ACI）Agent 通过什么接口查看、修改和操作计算机？是工具与动作子系统的重要部分，SWE-agent 是典型研究案例。
Agent Harness如何让模型在真实环境里持续观察、行动、恢复与验证？本文的核心研究对象。
Evaluation Harness如何系统地运行测试任务、记录轨迹并评分？测量 Agent 的基础设施，不应与生产运行时混淆。
Orchestrator如何调度多个 Agent 或多个 Harness？可以位于 Harness 之上；单纯协调不等于实现 Agent 执行循环。
DevOps / CI如何构建、测试、发布和运维软件？提供大量底层能力；Harness 还需要把这些能力变成模型可理解、可调用的接口。

一个很容易混淆的边界是：ACI 关注“动作接口”，Harness 关注“完整运行时”。 文件搜索、代码编辑、终端命令、浏览器操作属于 ACI 或工具层；任务状态、上下文选择、权限、恢复策略、验证协议和跨会话持久化，则把这些动作组织成可靠流程。

研究边界：Harness Engineering 是 2026 年快速形成的工程领域，目前还没有被所有研究者统一接受的唯一组件标准。下文的七大子系统来自 2026 年 7 月的一项代码级系统比较预印本；十一项职责来自另一项运行时框架预印本。本文会明确区分原作者提出的分类与本文为了教学所做的综合归纳。[5][6]

03 · 七大核心子系统：一个 Harness 究竟由什么构成？

如果只看一个 ReAct 循环，Agent 似乎只有三步：思考、行动、观察。但一个能够稳定运行数小时、操作大型仓库、调用多个工具并在失败后恢复的系统，必须把更多职责显式化。

2026 年 7 月的《Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents》对 11 个代码 Agent 系统进行源码层分析，将 Harness 归纳为七个子系统，并指出界面层与会话持久化是跨越多个子系统的支撑面。[6]

3.1 Agent Loop：决定何时行动、何时观察、何时停止

Agent Loop 是整个 Harness 的控制骨架。它反复执行：接收当前状态 → 请求模型决策 → 解析动作 → 执行工具 → 收集观察结果 → 更新状态。它还必须定义停止条件、最大步数、超时、失败重试和中断恢复。

state = initialize(task, environment)

while not terminal(state):
    context = select_context(state)
    decision = model(context, available_tools(state))
    action = validate_and_parse(decision)
    observation = execute(action, environment)
    state = update(state, action, observation)
    persist(state)

return verify_and_report(state)

这段伪代码刻意省略了模型 API、工具协议与存储实现，但揭示了一个重要事实：Agent 的行为不是一次文本生成，而是一系列会改变外部状态的决策。 如果没有 stop condition，Agent 可能无限循环；如果没有 failure recovery，一次超时就可能终止整个任务；如果没有持久化，进程重启就会丢失关键状态。

这里 xₜ 表示当前环境状态，cₜ 表示本轮选择的上下文，mₜ 表示可检索的持久记忆。公式是对 Agent 决策条件的抽象表达，并非某一篇论文的专属算法。

3.2 LLM Integration：模型接口不只是发一个 HTTP 请求

这一层负责模型供应商协议、消息格式、工具调用 schema、模型路由、缓存、推理参数、流式响应以及不同模型能力的兼容。不同模型可能在工具调用格式、上下文长度、并行调用和结构化输出上存在差异。若把这些差异散落在业务代码里，Harness 会变得难以升级。

更深一层的问题是 model–agent co-design：模型升级后，哪些能力已经内化到模型本身？哪些能力仍需要外部 scaffold？这决定了 Harness 应该保留什么、移除什么。

3.3 Tools & Actions：工具数量不是越多越好

工具是模型改变环境的接口。一个工具至少要有明确名称、用途、输入 schema、输出格式、错误语义、超时与权限。对于代码 Agent，常见工具包括文件读取、符号搜索、补丁编辑、终端命令、测试执行、浏览器导航和日志查询。

工具设计的关键不在于把所有命令都暴露给模型，而在于让模型能低成本地完成正确动作。过长的 shell 输出会挤占上下文；模糊的工具参数会增加调用错误；不稳定的返回格式会让模型误判成功。SWE-agent 的 ACI 研究正是通过重新设计文件查看、搜索、编辑和 lint 接口，改善模型与软件环境的交互。[7]

3.4 Memory & Context：当前上下文、任务状态与长期记忆必须分开

上下文窗口是有限的工作空间，不是无限知识库。一个成熟的 Harness 至少需要区分三种东西：

  • 当前上下文：本轮任务中马上需要模型看到的文件、日志、约束和工具结果。
  • 任务状态：已经检查过什么、当前假设是什么、哪些问题尚未解决、下一步是什么。
  • 项目记忆：跨任务稳定存在的架构约束、代码规范、已知陷阱、运行方式和历史决策。

将所有历史都塞进 prompt，既浪费 token，也会把过期信息带进当前决策。更好的做法是按需检索、分层存储、保留来源，并且允许记忆被修正。

3.5 Safety & Permissions：能力必须有边界

Harness 决定模型可以读取哪些文件、运行哪些命令、访问哪些网络资源、修改哪些分支，以及哪些动作必须得到人工批准。Sandbox 负责隔离文件系统、进程和网络；permission policy 负责表达允许、拒绝与审批规则。二者不能混为一谈：沙箱提供执行隔离，权限策略表达任务授权。

3.6 Orchestration：多 Agent 不是默认答案

Orchestration 负责拆分任务、分配角色、传递结构化工件、管理并行执行与冲突。Planner、Generator、Evaluator 是一种常见模式，但每增加一个 Agent，就增加上下文同步、工具权限、协调延迟和成本。只有当角色分离带来的收益超过协调成本时，多 Agent 才值得采用。

3.7 Extensibility：Skills、Hooks、MCP 与插件扩展

扩展层让用户能够添加新工具、新工作流和领域知识。Anthropic 对 Agent Skills 的工程介绍将 Skill 描述为包含 SKILL.md、脚本和资源的目录，并通过渐进式披露按需加载更深层说明；这使通用 Agent 可以在不把所有领域知识塞进初始上下文的前提下获得专门能力。[9] Hooks 可在特定事件前后执行确定性逻辑；MCP 提供标准化的工具或资源连接。扩展机制必须同时考虑来源可信度、版本、权限、审计和回滚。

七个子系统之外，研究还特别强调两个横切面：Interface Layer（CLI、TUI、IDE、SDK、HTTP 等入口）与 Session Substrate（对话轨迹、状态持久化、恢复、分叉和回放）。它们不一定是独立模块，却会影响几乎所有子系统。[6]

04 · 从架构到可检查的责任：十一项运行时职责

七大子系统回答“架构有哪些部分”；另一种更适合排查问题的视角，是问“每次 Agent episode 必须履行哪些责任”。2026 年 5 月的《AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents》提出了十一项职责，并为每一项配上典型失败模式和可留下的证据。[5]

运行时职责没有它时的典型失败应该留下什么证据
Task Interface目标模糊、验收范围漂移任务记录、需求清单
Context Manager看错文件、遗漏约束上下文选择轨迹
Tool Registry工具不可用、参数错误工具调用记录
Project Memory重复探索、修错架构层记忆来源与引用
Task State重复劳动、长任务漂移状态文件、下一步
Observability不知道发生了什么日志、指标、运行轨迹
Failure Attribution失败后盲目再改一次现象、预期、根因记录
Verification Protocol只凭口头声称完成需求级测试与验证报告
Permission Boundary越权、破坏性操作权限决策与审批记录
Entropy Auditor文档过期、依赖混乱、残留文件维护质量审计
Intervention Logger人类不断补位但系统看不见人工介入及其原因

这里有一个非常重要的研究转变：失败不再只是一个 pass/fail 布尔值，而是一个可以归因的运行时事件。例如，Agent 修复失败，可能不是模型不会写代码，而是 Harness 没有暴露相关测试；人类告诉它应该打开哪个文件，说明 Context Manager 可能不足；人类替它解释错误日志，说明 Observability 或 Failure Attribution 可能不足。

实用原则：不要只记录 Agent 最后输出了什么。还要记录它看到了什么、调用了什么、环境返回了什么、为什么认为任务完成，以及人类在哪一步不得不接手。

05 · OpenAI：把仓库知识变成 Agent 的系统记录

OpenAI 于 2026 年 2 月发布的《Harness engineering: leveraging Codex in an agent-first world》，讲述了一个从空 Git 仓库出发、以 Codex Agent 为主要执行者构建内部软件产品的工程实验。[1]

文章描述：项目在五个月左右发展到约一百万行代码，累计打开并合并约 1,500 个 Pull Request；团队最初为三名工程师，文中报告的平均吞吐量约为每位工程师每天 3.5 个 PR。作者还估计，整个产品的构建时间约为手工编写代码所需时间的十分之一。这些是 OpenAI 对其内部项目的工程自述，不是独立控制实验，也不应直接外推为其他团队的生产率承诺。

原文还明确说明，产品逻辑、测试、CI 配置、文档、可观测性和内部开发工具都由 Codex 生成；团队成员没有直接手工编写代码。人类并未退出工程流程，而是把工作重心转移到目标设定、环境设计、反馈回路和结果验收。[1]

5.1 人类的角色从“写代码”转向“设计环境”

文章中有一句很值得记住的话：Humans steer. Agents execute. 这并不是说人类不再负责工程，而是工程师的主要工作从逐行实现，转向描述意图、设计工具、暴露上下文、定义架构边界和构建反馈闭环。

团队早期遇到的瓶颈，并不只是模型写代码能力不足，而是环境没有被充分定义。模型不知道去哪里找信息，不知道哪些抽象可以复用，也没有足够清晰的工具和验证流程。因此，工程师遇到失败时不只是让模型“再试一次”，而是追问：缺失了什么能力？怎样让这项能力对 Agent 可见，并且能被机械执行？

5.2 AGENTS.md 应该是一张地图，而不是一本百科全书

OpenAI 文章明确指出，把所有规则都塞进一个超长 AGENTS.md 并不可取：上下文预算有限；过多规则会让重点消失；文档很快过时；单个大文件也难以自动检查覆盖率、时效性和链接关系。

他们最终采用的思路是：AGENTS.md 负责告诉 Agent 从哪里开始，真正的知识库由结构化 docs/ 承载。 仓库包含架构说明、设计文档、产品规格、执行计划、质量评分、安全规范和可靠性规则。Agent 从一个简短入口出发，再按任务需要逐步读取相关文档，这就是 Progressive Disclosure（渐进式披露）。

这对真实项目的启发是：AGENTS.md 不应重复 README、架构文档和所有开发规范。它应该回答四个问题：项目入口在哪里？遇到什么任务应先读哪些文档？哪些规则是硬约束？如何验证修改？具体实现细节应该放在更靠近代码或主题的文件里。

5.3 Agent Legibility：让应用本身可以被 Agent 观察

当代码生成吞吐量提高后，瓶颈会转移到人工 QA。OpenAI 的工程实践是为每个 Git worktree 启动隔离应用实例，并将 Chrome DevTools Protocol、DOM 快照、截图、页面导航和本地 observability 工具接入 Agent。每个 worktree 还拥有独立的日志、指标和 trace 环境。

这会改变 Agent 能完成的任务类型。以前，“修复登录流程在第二次重试时失败”需要人类手动复现；现在 Agent 可以启动应用、操作浏览器、查看日志、查询指标、重现问题、修复代码并验证结果。所谓 Agent Legibility，不是让 Agent 拥有更多文字，而是让系统状态可以被它直接观察和检验。

5.4 Enforce Invariants：约束边界，而不是规定每一行代码

OpenAI 还强调，文档不能单独保证架构一致性。团队为领域分层和依赖方向建立机械规则，例如 Types → Config → Repo → Service → Runtime → UI 的单向层级；跨领域能力通过明确接口进入。自定义 linter 和结构测试会阻止不合规依赖、无结构日志、命名偏差和过大的文件。

关键不是要求 Agent 必须使用某个具体库，而是定义哪些结构绝对不能被破坏。边界由机器强制，边界内部允许 Agent 自主选择实现。 这比在 prompt 中重复“请保持架构整洁”可靠得多。

5.5 Entropy Management：生成速度越快，清理越要自动化

Agent 会复制仓库中已经存在的模式，即使这些模式本身并不理想。错误抽象、重复 helper、过期文档、临时文件和脆弱测试可能不断积累。OpenAI 将这种持续累积的维护负担描述为类似垃圾回收的问题：把团队的工程原则写进仓库和工具，再通过定期后台任务扫描偏差、更新质量评分并提交小型清理 PR。

这意味着 Harness 的目标不能只是提高短期代码产出。它还要维护未来 Agent 能继续理解和修改的代码环境。否则，今天节省的时间可能变成明天更高的上下文成本和维护成本。

06 · Anthropic：让 Agent 能跨越上下文窗口持续工作

Anthropic 的工程文章提供了另一条重要研究主线：如何让 Agent 在数小时、多个会话甚至多轮任务中保持连贯。它不是简单地延长上下文窗口，而是把任务拆解、进度持久化、会话交接与独立评估纳入 Harness。

6.1 2025：Initializer + Coding Agent

2025 年 11 月《Effective harnesses for long-running agents》指出，长任务的两个典型失败是：Agent 一开始试图一次性实现太多功能，导致上下文耗尽时留下半成品；以及后续会话看到已有进展后，误以为整个项目已经完成。[2]

Anthropic 的解决方案分成两种角色：

  • Initializer Agent：首次运行时建立项目环境，生成 init.sh、功能清单、进度文件和初始 Git commit。
  • Coding Agent：后续每个会话先恢复项目状态，再挑选一个尚未完成的功能，逐步实现、测试、提交，并写下结构化进度。

这里的 clean state 很重要：新会话开始时，项目应当可以运行，已经完成的功能应有清楚的记录，未完成的功能应能被明确识别。Agent 需要先检查项目是否仍然正常，再继续增加功能。

为什么不能只依赖对话摘要？因为摘要可能丢失执行状态、未提交修改和关键错误。Git commit 提供可恢复的代码状态，功能清单提供可检查的完成标准，进度文件提供下一步线索，初始化脚本提供可重复的启动方式。它们合在一起，才构成可靠的跨会话交接协议。

6.2 Compaction 与 Context Reset：压缩不等于重新开始

Anthropic 在 2026 年 3 月的文章中进一步讨论了 Context Compaction 与 Context Reset 的区别。[3]

策略做法优势风险 / 成本
Compaction压缩历史对话，继续使用同一个上下文窗口。保留一定的连续性，交接成本较低。可能保留旧的思维路径和错误假设；摘要不一定保留足够精确的任务状态。
Context Reset结束旧上下文，启动新 Agent，并从结构化交接材料恢复。获得干净上下文，减少历史噪声和过早收尾倾向。需要更好的 handoff artifact；增加编排、token 和延迟成本。

Anthropic 报告，在他们早期的 Sonnet 4.5 长任务实验中，单纯 compaction 不足以消除明显的 context anxiety，因此 context reset 成为必要设计。到了 Opus 4.5 / 4.6，模型持续规划和处理长上下文的能力提升，部分场景可以减少甚至取消 reset。这说明 Harness 不是固定模板，而是需要随模型能力重新校准的运行时系统。

6.3 2026：Planner–Generator–Evaluator

2026 年 3 月《Harness design for long-running application development》进一步把“独立评估”加入架构，形成三个角色：[3]

Planner 从一到四句话的需求中扩展出产品规格，重点描述交付物和产品目标，而不把实现细节过早锁死。这样可以避免规划阶段的错误技术假设向后传播。

Generator 按功能或 sprint 增量实现应用。对于每个 sprint，它需要和 Evaluator 协商一个 sprint contract：本轮做什么、哪些行为应该可见、如何验证“完成”。

Evaluator 不应只阅读代码，而是使用 Playwright 操作正在运行的应用，点击按钮、检查 API、观察数据库状态，并依据功能完整性、代码质量、视觉设计和产品深度等标准给出反馈。

这项实验很有启发性：Anthropic 报告，在一个复古游戏制作工具的对比实验中，单 Agent 方案约 20 分钟、成本约 9 美元；完整 Harness 方案约 6 小时、成本约 200 美元。后者产出更完整、可实际操作的应用，但并不是免费获得的提升。后续他们使用 Opus 4.6 简化 sprint 机制，在 DAW 实验中报告约 3 小时 50 分钟、124.70 美元的运行成本。这些数字是特定模型、任务和内部实验的成本记录，不是通用的成本倍率或质量保证。

更重要的是，Evaluator 自己也会犯错：它可能发现问题后又说服自己“问题不严重”，也可能只做浅层测试。因此，独立评估并不等于绝对正确；它需要通过人类校准、失败案例复盘、明确的 rubric 和可重复测试不断改进。

07 · OpenAI 与 Anthropic：两种路径的共同点和差异

两家工程文章关注的场景并不完全相同。OpenAI 更强调 Agent-first repository 的组织方式、知识可见性、架构约束、可观测性和持续清理；Anthropic 更强调长任务的上下文交接、增量执行、角色分离与独立评估。但两条路径指向同一个结论：模型能力必须通过一个可观察、可约束、可验证的运行环境才能转化为可靠交付。

维度OpenAI Codex 实践Anthropic Claude 实践
核心问题如何让 Agent 理解并持续维护大型代码仓库？如何让 Agent 跨越长任务和多个上下文窗口持续推进？
上下文策略仓库作为系统记录；短 AGENTS.md + 结构化 docs。功能清单、Git 历史、进度文件、结构化 handoff。
执行方式Agent 使用标准开发工具、worktree 与仓库内 skills。Initializer、Coding Agent，进一步演进为 Planner、Generator、Evaluator。
反馈机制浏览器、DOM、日志、指标、trace、lint 和结构测试。端到端浏览器 QA、sprint contract、独立 rubric 和多轮修复。
质量治理架构不变量、机械 lint、文档治理、周期性垃圾回收。验收标准、外部评估、失败案例校准、按模型能力简化 Harness。
主要风险吞吐量提升后，架构漂移和维护熵会迅速积累。多 Agent 协调成本高；Evaluator 也会漏测或误判。

如果把它们组合成一套通用系统，可以得到以下原则：

  1. 把仓库知识和任务状态放在 Agent 可访问、可版本化的位置。
  2. 把运行中的应用、日志、测试和指标暴露给 Agent，而不是只给它源码。
  3. 把“完成”写成可以执行的验收标准，不允许只凭模型自述。
  4. 让评估者尽量独立于实现者，并用确定性测试约束主观判断。
  5. 把人工反馈转化为文档、测试、工具或架构规则，避免同一个问题反复发生。
  6. 模型升级后重新做消融：删掉已经不再需要的支架，也补上模型仍无法可靠完成的部分。

08 · 评测：怎样证明 Agent 真的完成了任务？

Harness 如果只让 Agent “跑得更久”，却不能证明结果正确，那么它只是在放大行动数量。真正的关键是把自然语言目标转成可以检查的结果。

Anthropic 在 2026 年《Demystifying evals for AI agents》中把一次评测拆成几个基本概念：[4]

  • Task：一个输入明确、成功条件清楚的测试任务。
  • Trial：Agent 对某个任务的一次运行。由于模型存在随机性，同一个任务通常要重复多次。
  • Grader：负责检查某个方面的评分器，一个任务可以组合多个 grader。
  • Transcript / Trace：完整记录一次运行，包括模型消息、工具调用、观察结果和中间交互。
  • Outcome：运行结束后环境中的真实状态，而不只是 Agent 最后的文字回复。

例如，订票 Agent 最后说“已经预订成功”并不构成成功证据；真正的 outcome 应该是数据库中确实存在符合条件的订单。对代码 Agent 也是如此：它说“修复完成”并不够，需要代码通过相关测试、没有破坏既有行为，并且在真实运行环境中达到验收条件。

8.1 三类 Grader 应该如何配合？

Grader适合检查什么主要缺陷
Code-based单元测试、静态分析、状态检查、工具参数、性能阈值。容易对合理但不同的实现方式过于僵硬。
Model-based代码质量、需求理解、开放式任务质量、交互体验。非确定、成本更高，需要人类校准。
Human专业判断、审美、复杂用户体验、风险决策。成本高、速度慢，难以对所有运行逐一检查。

三类评估器不应互相替代。确定性测试负责“能否证明某个条件成立”；模型评估器负责处理更复杂的开放式质量标准；人类则负责校准评估标准和处理高风险判断。

8.2 Capability Eval 与 Regression Eval

Capability Eval 问的是：这个 Agent 能否解决以前不擅长的任务？初始通过率可以比较低，因为它测量的是能力边界。Regression Eval 问的是：Agent 是否仍然能稳定完成过去已经通过的任务？它应该维持接近完整的通过率，用来防止模型、prompt 或工具升级引入回归。

当某项能力成熟后，原来的能力评测可以毕业为持续运行的回归测试。这样，Harness 不只是一次性交付流程，而是持续观察系统质量的基础设施。

8.3 从“测试通过”走向“证据闭环”

一个较完整的验证协议应当把每条需求映射到证据：

Requirement: 用户可以在移动端打开第 2 页
Evidence:
  - URL: /archive/page/2/
  - Browser: 390px viewport
  - Assertion: page title and 16 article links visible
  - Regression: page 1 remains reachable
  - Accessibility: pager controls have names and focus states
  - Build: static site validation passed
  - Deployment: public URL returns the expected page

这段是本文构造的教学示例，不是 OpenAI 或 Anthropic 的内部格式。它体现了一个通用原则：每一条“完成”都应能追溯到具体证据。

09 · 交互实验：Harness 的短板会怎样限制整体可靠性？

现在用一个简化模型观察五类运行时能力的共同作用：上下文质量、工具可靠性、验证覆盖率、安全边界和维护质量。你可以拖动参数，或点击预设场景，观察教学指数如何变化。

38.3

Harness 教学指数 / 100
不是实际成功概率，也不是论文拟合指标；它只用于演示多个环节同时存在短板时，系统综合能力可能受到怎样的限制。

当前瓶颈：验证覆盖率最低。系统可能完成了代码修改，却没有充分检查真实行为。

H_demo = C × T × V × S × (1 − E)C：上下文相关性；T：工具可靠性；V：验证覆盖率；S：安全边界质量；E：维护熵负担。各变量归一化到 0–1。

为什么用乘法而不是加法？这是一个教学上的瓶颈模型：如果某个关键环节接近零，其他环节即使很好，也很难补偿它。例如工具可靠性为零，Agent 就无法执行必要操作；验证覆盖率为零，系统就无法可靠区分“真的完成”与“看起来完成”。

模型限制：真实 Harness 的各维度并不独立，也不一定能被压缩成一个分数。这个公式不是 OpenAI、Anthropic 或 arXiv 论文中的经验模型，更不能用来预测生产系统的成功率。实际研究应使用固定任务、固定环境、多个 trial 和可复核的 outcome 做 controlled ablation。

10 · 如何从零设计一个可用的 Harness？

不建议一开始就构建多 Agent 平台。先围绕一个清晰任务，把最小闭环跑通，再根据真实失败增加组件。一个实用的建设顺序如下：

Step 1：把用户意图变成任务契约

任务契约需要包含目标、约束、允许修改范围、验收条件和停止条件。不要把所有实现细节都写死，但必须让“完成”有可检查的定义。

{
  "goal": "Add pagination to the article archive",
  "constraints": ["preserve existing URLs", "mobile friendly"],
  "acceptance": [
    "each page contains at most 16 posts",
    "page 2 has a canonical URL",
    "no duplicate or missing published posts",
    "390px and 360px viewports have no page overflow"
  ],
  "allowed_actions": ["read", "edit", "run_tests", "browser"],
  "approval_required": ["delete_data", "change_permissions", "deploy"]
}

这是一份教学任务契约。真正项目中还应增加仓库版本、运行环境、依赖版本和证据链接。

Step 2：先给地图，再按需给上下文

建立简短入口文档，指向架构、目录、测试、部署、代码风格和常见故障。Agent 先读取与任务直接相关的文档，再根据搜索结果打开具体文件。不要一开始把整个仓库或所有历史记录塞进上下文。

Step 3：设计最小、稳定的工具面

优先提供少数高价值工具：文件搜索、带行号查看、受控编辑、测试运行、日志读取和浏览器操作。工具输出要短、结构稳定、错误可识别。对破坏性动作设置明确审批门槛。

Step 4：把任务状态保存为结构化工件

至少记录已完成事项、未完成事项、当前假设、失败原因、下一步和最近一次成功验证。Git commit 是代码状态的恢复点；progress 文件是跨会话交接点；测试报告是质量证据。三者不能互相替代。

Step 5：把可观测性接入 Agent 工作流

除了终端输出，还应尽可能暴露运行日志、测试报告、浏览器截图、页面 DOM、指标和 trace。只有当 Agent 能够观察到失败，才有机会准确定位并恢复。

Step 6：用独立验证器定义“完成”

对于确定性要求，优先使用单元测试、集成测试、静态分析和浏览器断言；对于开放式质量，使用清晰 rubric 和人类抽查校准。实现者可以自测，但不应该成为唯一的验收者。

Step 7：建立权限、回滚和维护治理

限制 Agent 的工作目录和可执行命令；敏感操作必须审批；每次修改都要保留 diff 和可恢复的 Git 状态；定期检查过期文档、重复代码、依赖漂移、测试弱化和临时残留。

从最小系统开始：一个模型、一个 Agent Loop、一组受控工具、一份任务状态文件、一套确定性测试和一条明确的人工升级路径。只有观察到具体失败，再增加多 Agent、自动记忆、复杂编排或高级评分器。

11 · 失败归因：不要把所有问题都叫作“模型不够聪明”

Harness 的价值之一，是让不同类型的失败能被分开处理。以下诊断矩阵把常见现象映射到应该检查的运行时能力。

可观察现象可能缺失的 Harness 能力更合理的修复方向
Agent 总是打开错误文件Context Manager / Project Memory补充目录地图、相关文档索引和检索证据。
命令频繁失败或输出难以解析Tool Registry / Tool Interface稳定参数 schema、错误格式、超时和输出截断。
失败后只会继续随机修改Observability / Failure Attribution先复现、记录预期与实际，再分类根因。
功能未实现却声称完成Verification Protocol把需求映射到测试、浏览器行为和状态检查。
Agent 执行了未授权命令Permission Boundary在执行层强制权限，不只依赖 prompt。
长任务重复探索或忘记进度Task State / Session Substrate保存结构化状态、Git checkpoint 和交接记录。
代码越来越重复、文档过期Entropy Auditor加入结构 lint、文档治理和周期性清理。
所有支持都正确但仍无法完成可能是 Model Capability检查是否超出当前模型能力边界，调整任务或更换模型。

五个常见反模式

  1. Prompt-only Engineering：把工具、状态、安全和验证问题都写成更长的提示词。
  2. Context Dumping：把整个仓库、所有历史和所有规范一次性放进上下文。
  3. Multi-Agent by Default：用更多角色掩盖工具接口和任务契约设计不清的问题。
  4. Self-Approval：让实现者只凭自己的自然语言判断决定是否完成。
  5. Throughput without Garbage Collection：只追求代码与 PR 数量，不治理架构漂移、过期文档和维护负担。

12 · 局限与研究前沿

12.1 Harness 的贡献如何与模型能力分离？

如果换了模型、换了工具、换了提示词，结果同时变好，我们很难知道是哪一项起了作用。研究者需要固定模型、任务、仓库初始状态和验收规则，对 Harness 的某些组件做 controlled ablation。2026 年 5 月的预印本提出 H0–H3 阶梯：从只有任务与仓库的基线开始，逐步增加工具、项目记忆、任务状态、可观测性和验证协议，以区分各层支持的贡献。[5]

12.2 Harness 会不会变成另一个复杂系统？

会。每增加一个 Agent、一个评分器或一层中间件，都增加新的失败点、延迟、成本和维护负担。Anthropic 的工程文章明确强调，模型升级后应该重新审查哪些组件仍然必要；某个组件曾经有用，不代表它永远有用。[3]

12.3 评估者也可能被欺骗或产生偏差

模型评分器可能偏爱表面完整的输出；Agent 可能找到测试漏洞；静态检查也无法覆盖所有用户行为。评测系统需要隐藏测试、独立 outcome 检查、重复 trial、人工校准和真实用户反馈。安全敏感任务还需要独立的威胁建模与权限审计。

12.4 长期维护比单次任务成功更难

Harness 的成功不能只看一次任务是否通过。还要关注跨版本回归、文档是否陈旧、工具 schema 是否兼容、记忆是否过时、生成代码是否引入隐性复杂度，以及系统在模型升级后是否仍然稳定。

12.5 未来值得研究的方向

  • Harness 自动演进：根据 trace 与失败归因，自动调整工具、上下文策略和验证机制。
  • 跨模型迁移：同一 Harness 是否能在不同模型家族间复用？哪些规则需要模型特定化？
  • 可审计自主性：如何量化 Agent 完成任务时需要多少人工介入？
  • 记忆可信度：如何追踪记忆来源、时效性、冲突与修正？
  • 安全与可恢复性：如何在沙箱、最小权限、审批和回滚之间取得合理平衡？
  • 长期质量：如何衡量代码仓库的维护熵，而不是只衡量短期任务通过率？
阅读研究预印本时要注意：本文引用的两篇 2026 年 arXiv 研究用于展示正在形成的术语、架构框架与研究方法，不代表已经形成行业标准。七大子系统和十一项职责是两组研究者提出的分析框架，本文将其并置，是为了帮助读者理解“架构视角”和“责任视角”的差异。

13 · 总结：Harness Engineering 的真正目标是什么？

Harness Engineering 的核心不是让模型拥有更多工具，也不是让 Agent 永远运行下去。它的目标是：让模型在一个结构清楚、权限明确、反馈充分、状态可恢复、结果可验证的环境中，持续完成有价值的任务。

五个可以带走的 mental models

  1. Agent = Model + Harness：不要把模型能力和系统能力混为一谈。
  2. AGENTS.md 是地图，不是百科：用渐进式披露组织上下文。
  3. Long-running ≠ Long-context：跨会话交接依赖状态工件、Git 和可恢复环境。
  4. Completion is Evidence：完成不是一句话，而是需求对应的可复核证据。
  5. Harness must evolve with the model：组件要通过真实任务和消融证明价值，不能永远堆叠。

如果你已经理解 ReAct 的 Thought–Action–Observation，再读 SWE-agent 的 ACI，下一步就可以把视角提升到 Harness：不再只问“Agent 下一步做什么”，而是问“整个系统如何确保 Agent 看对信息、采取正确动作、从失败中恢复，并用证据证明它真的完成了任务”。

  2. Justin Young. Effective harnesses for long-running agents. Anthropic Engineering, 2025-11-26. 重点：Initializer/Coding Agent、feature list、progress file、增量工作与浏览器验证。
  3. Prithvi Rajasekaran. Harness design for long-running application development. Anthropic Engineering, 2026-03-24. 重点：Planner/Generator/Evaluator、Context Reset、sprint contract 与独立 QA。
  4. Anthropic Engineering. Demystifying evals for AI agents. 2026-01-09. 重点：Task、Trial、Grader、Transcript、Outcome，以及 code/model/human graders。
  5. Hailin Zhong & Shengxin Zhu. AI Harness Engineering: A Runtime Substrate for Foundation-Model Software Agents. arXiv:2605.13357, 2026-05-13. 研究预印本：十一项职责、H0–H3 harness ladder 与 trace-based evaluation。
  6. Paul Barbaste, Tristan Darrigol, Germain Vu & Tom Wiltberger. Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents. arXiv:2609.00006, 2026-07-15. 研究预印本：十一套系统的源码分析、七大子系统与扩展机制。
  7. Yang et al. SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering. NeurIPS 2024. 重点：ACI 如何改善模型与软件环境的交互。
  8. Yao et al. ReAct: Synergizing Reasoning and Acting in Language Models. ICLR 2023. 重点：推理、行动与环境观察的交替循环。
  9. Anthropic Engineering. Equipping agents for the real world with Agent Skills. 2025-10-16. 重点：SKILL.md、脚本与资源的渐进式披露和可组合扩展。
