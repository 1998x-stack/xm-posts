AGENT SYSTEMS / LOOP ENGINEERING / 2026

Understanding Loop Engineering

如何把一次 Agent 调用，变成一个能够自动发现任务、持续执行、独立验证、跨会话恢复，并且知道何时停止的工程系统？

研究主题：Agent Systems建议阅读 28 分钟适合本科高年级 / 研究生 / Agent 工程实践者

01 · 为什么一个很强的 Agent，仍然不能自动完成长期工作？

假设你让一个编码 Agent 修复仓库中的一个 Bug。它可以读取文件、修改代码、运行测试，甚至在测试失败后再修改一次。单看这一轮，它已经相当聪明。但明天仓库里又出现了新 Issue，或者 CI 又失败了，谁会发现这件事？谁来启动下一轮？谁来记住上一次已经验证过什么？

这暴露了一个容易被忽略的区别：能在一次运行中反复行动，不等于能长期负责一个目标。单次 Agent 的输入通常来自人；长期系统还需要自动产生下一次输入、判断工作是否值得做、保存可恢复状态，并在证据不足或权限不足时停止。

单次 Agent 任务

人给出一个目标；Agent 在当前上下文中规划、调用工具、观察结果；最终返回答案或交付物。

主要问题：这一轮能否做好？

持续运行的 Agent 系统

事件或日程触发运行；系统发现任务、恢复状态、分配工作、验收结果，再决定是否继续或升级。

主要问题：系统能否长期、可靠、受控地推进目标？

可以把它类比成两种软件：一个函数能正确处理一次输入，不代表整个服务已经具备队列、重试、持久化、监控和故障恢复能力。Agent 的推理能力只是系统的一部分；长期任务还需要控制平面和工程约束。

本文的核心问题：不要只优化“让 Agent 这一次做得更好”，还要设计“什么条件下再次启动 Agent、给它什么状态、如何判断结果可信，以及何时必须停止”。

02 · Loop Engineering 到底是什么？

Loop Engineering 是 2026 年逐渐出现的实践术语。Lulla 等人的探索性研究将其描述为：开发者不再每次亲自向 Agent 发出下一条提示，而是设计一个系统，由系统在日程或仓库事件发生时启动 Agent，并通过机器可检查的条件决定何时停止。[1]

这不是一个已经拥有统一标准、成熟理论体系和充分因果证据的学科名称。更准确的说法是：它正在成为一组工程实践的统称，关注如何把 Agent 的执行组织成可触发、可验证、可恢复、可治理的重复工作循环。

注意三个常见误解：

  • 它不等于 while True：无限重启 Agent 只是循环调用，不代表系统知道任务是否完成、是否重复、是否安全。
  • 它不等于 ReAct：ReAct 描述一次 Agent 运行内部如何交替思考、行动和观察；Loop Engineering 还要解决运行之间的触发、状态、验收和治理。
  • 它不等于 Self-Refine：Self-Refine 主要研究同一个模型如何对当前候选输出进行反馈和改写；Loop Engineering 的对象可以是跨任务、跨会话、跨工具的长期流程。

一个好记的定义是：Agent loop 让模型在一次运行中继续行动；Loop Engineering 让系统在多次运行之间持续、受控地推进目标。

03 · 从 Prompt、Context、Harness 到 Loop：四层工程关注点

这四个概念不是互相淘汰的技术流派，而是逐层扩大的系统边界。每一层都回答一个不同的问题。

层次核心问题典型设计对象不负责解决什么
Prompt Engineering这一轮应该怎样表达任务？指令、示例、输出格式、约束不会自动发现明天的新任务
Context Engineering模型本轮应该看到哪些信息？检索、状态摘要、文件、历史、排序与压缩不会自动决定何时再次启动
Harness Engineering模型能调用什么、如何运行？工具、沙箱、权限、测试、执行环境、观测不会自动形成完整的长期工作计划
Loop Engineering系统何时启动、处理什么、如何验证并继续？触发器、任务队列、状态、验证器、预算、升级策略不能替代底层模型、上下文和执行环境

OpenAI 对 Codex agent loop 的工程说明，展示了模型推理、工具调用、工具执行和反馈重新进入上下文的内层循环。[2] Anthropic 对 long-running agent harness 的研究，则进一步讨论跨 Context Window 的持续工作：使用 initializer agent 建立环境，再由 coding agent 在每次会话中增量推进，并留下进度文件供下一次恢复。[3]

因此，Loop Engineering 可以被理解为更高一层的协调设计：它调用 Prompt、Context 和 Harness 的能力，但新增了时间维度、任务生命周期和系统级控制。

04 · 外层循环的完整架构：不是只有一个 Agent

把一个可运行的 Loop 拆成七个阶段，可以得到一张更容易落地的系统图。

4.1 Trigger：触发器

触发器回答“什么时候值得运行”。常见类型包括：

  • 时间触发：每小时、每天、每周执行一次巡检。
  • 事件触发：GitHub Issue 创建、Pull Request 更新、CI 失败、文件变化、部署完成。
  • 状态触发：任务队列中出现待处理任务、失败次数达到阈值、审批状态发生变化。
  • 人工触发：用户主动要求继续，或批准一个此前被暂停的高风险操作。

触发器只负责启动候选流程，不应该直接等同于“让 Agent 修改东西”。触发后仍然需要任务发现、去重和权限检查。

4.2 Discover：任务发现与去重

一个仓库可能同时有 20 个 Issue、3 个失败的 CI、若干过期文档和多个未合并 PR。Agent 不应把所有事情塞进一个上下文。系统首先要把外部事件转换成任务记录：任务 ID、来源、优先级、依赖、截止时间、当前状态和负责角色。

这里最重要的是 idempotency（幂等性）。同一个 Webhook 可能重复送达；定时任务可能重叠运行。如果每次触发都创建一个新任务，就会重复修改同一份文件或重复发出外部请求。可以使用稳定的事件 ID、资源 ID 与版本号构造幂等键，并在领取任务时使用原子状态转换。

4.3 Context Projection：上下文投影

任务记录通常远小于完整对话历史。系统应根据当前任务，选择必要的上下文：相关文件、Issue 描述、历史决策、最新提交、上一次验证报告、尚未解决的风险。把所有历史都塞回 Prompt，不一定能帮助模型；更重要的是保留当前事实、来源和版本。

4.4 Execute：隔离执行

Worker 在受限环境中执行：读取文件、提出补丁、运行测试、生成文档或调用业务 API。执行环境要明确工作目录、网络策略、凭证范围、可写文件、最大运行时长，以及哪些副作用必须等待审批。

4.5 Verify：独立验证

Agent 提交的是候选结果，不是已经被证明正确的结果。系统应该运行测试、静态检查、Schema 验证、领域评测，必要时再交给人审查。验证器输出结构化结果，至少包含 pass/fail、证据、失败原因和是否需要人工介入。

4.6 Persist：持久化

将任务状态、产物版本、验证结果、失败反馈、下一步动作和运行成本写入持久化存储。下一次运行不能依赖“模型应该记得上次说过什么”。

4.7 Decide：决策与终止

根据证据选择四类结果：通过并完成；有明确可修复反馈时重试；遇到歧义或高风险时升级给人；达到预算或停止条件时终止。一个健康的循环必须允许停止，并且能解释为什么停止。

05 · Loop Specification：先写契约，再写自动化脚本

为了避免把 Loop 设计成一个含糊的“Agent 不断努力直到成功”，可以用一个工程规格描述它：

ℒ=(T,G,D,C,Π,A,V,S,M,B,H)

各符号分别代表：

  • T — Trigger：启动事件、周期或状态条件。
  • G — Goal：目标及可观察的成功标准。
  • D — Discover：任务发现、筛选、分解与去重。
  • C — Context：本轮所需的上下文投影。
  • Π — Policy：Worker 的执行策略、角色和工具选择。
  • A — Authority：权限边界、可访问资源和允许的副作用。
  • V — Verifier：独立验收规则及证据格式。
  • S — Stop：完成、超限、无进展、冲突和风险终止条件。
  • M — Memory：持久状态、决策记录、版本与交接内容。
  • B — Budget：尝试次数、Token、时间、费用和并发上限。
  • H — Human escalation：何时暂停并请求人工判断或授权。

这不是唯一标准化公式，而是一份设计清单。漏掉任何一项，都可能在运行时暴露出系统性问题：没有 T 就无法自动启动；没有 V 就无法判断结果；没有 M 就无法跨会话恢复；没有 B 和 S 就可能无限消耗；没有 A 和 H 就可能越权执行。

每次运行可以抽象成状态转移：

sk+1=F(sk,Δk,ek,B,A)

其中 sk 是第 k 轮开始时的任务状态，Δk 是 Agent 产生的候选变更，ek 是验证器收集到的证据。F 不是“模型自由发挥”，而是由显式策略决定下一状态。

Verifier / Policy 结果下一状态系统动作
全部验收条件通过completed保存产物与证据，关闭任务
可修复的确定性失败retrying将失败日志作为下一轮反馈
权限不足、歧义或高风险needs_human暂停自动执行，提交证据等待审批
预算耗尽、无进展或冲突stopped保存状态、原因和恢复条件

06 · 为什么验证器必须成为一等公民？

一个常见设计是让 Agent 先写代码，再问同一个 Agent：“你觉得自己写对了吗？”这可以作为初步自检，但不能作为唯一验收依据。生成器擅长提出候选方案；验证器的工作是根据独立证据判断候选方案是否满足约束。

验证器不一定是另一个 LLM。根据任务的可判定性，优先使用最可靠、成本最低的证据：

验证类型例子可靠性边界
确定性测试单元测试、集成测试、编译、类型检查只能证明被覆盖的行为，不能证明所有需求都满足
结构约束JSON Schema、API 契约、链接检查、文件清单结构正确不代表语义正确
领域评测Benchmark、回归集、规则校验、检索命中率评测集可能不覆盖真实分布，也可能被过拟合
模型评审LLM-as-judge、独立审查 Agent可能存在偏好偏差、提示敏感和共同盲点
人工审批生产发布、资金操作、权限变更、破坏性迁移成本较高，但对高后果操作不可随意省略

最重要的原则是：验证证据应尽量独立于生成过程。如果 Worker 和 Verifier 使用同一套提示、同一模型、同一份未经核实的上下文，它们可能共享同一个错误假设。增加一个“Reviewer Agent”标签，并不会自动带来独立性。

OpenAI 的 Codex iterative repair 示例把工作拆成 Review、Repair、Validate 三个阶段，并把验证结果反馈给下一轮；这是一个很实用的工程模式。[4] 但它是工程案例，不应被描述为已经通过受控实验验证的通用最优架构。

07 · 跨会话状态持久化：不要让下一轮从聊天记录里猜

长期 Agent 经常跨越多个 Context Window。第一轮结束时，模型上下文可能被清空；下一轮可能使用不同模型、不同 Worker，甚至由另一个团队接手。如果任务进度只保存在对话历史中，系统就很难稳定恢复。

一个最小的持久化状态至少应包含：

  • Identity：task_id、来源事件 ID、幂等键、创建时间。
  • Goal & Scope：成功标准、允许修改的范围、不能触碰的资源。
  • Progress：已完成事项、待办事项、依赖关系、当前状态。
  • Version：Git commit SHA、文档版本、输入数据版本或外部资源 ETag。
  • Evidence：测试命令、结果摘要、日志位置、验证器版本和时间戳。
  • Handoff：最近一次失败、下一步建议、需要人回答的问题。
  • Budget：已经消耗的尝试次数、Token、费用和时间。

Anthropic 的 long-running agent 研究指出，跨会话任务的困难不只是上下文长度，还包括新一轮 Agent 不知道前一轮做了什么、可能重复实现或过早宣布完成。其工程方案使用初始化阶段和增量编码阶段，并留下进度文件与 Git 历史，帮助下一轮快速恢复。[3]

工程建议：把对话历史视为辅助材料，把任务状态视为正式数据。状态文件需要版本、来源和校验；关键决策要能追溯到具体提交或验证结果。对于共享状态的并发 Worker，还需要锁、租约或原子任务领取机制。

08 · 有边界的自主性：为什么“自动化程度越高越好”是错误目标？

Loop 的目标不是让 Agent 永远运行，而是在明确范围内自动推进，并在不确定性、风险和权限边界前停下来。一个持续运行但无法停止、无法审计、无法撤销的 Agent，不是更先进的系统，而是一个扩大了故障半径的系统。

8.1 Authority：最小权限

把权限分为只读、工作区写入、创建 PR、合并、生产发布等不同等级。低风险步骤可以自动执行；合并主分支、删除数据、发起付款、修改访问控制等高后果操作，应要求明确审批。不要把“Agent 能调用工具”理解成“Agent 有权执行任何工具动作”。

8.2 Budget：多维预算

只限制最大迭代次数是不够的。一个 Agent 可能在一次尝试中运行很久，或并行启动多个昂贵任务。建议同时限制最大尝试次数、总 Token、墙钟时间、费用、并发数、工具调用数和每个子任务的资源配额。

8.3 Stop：终止条件

  • 目标验收条件全部通过。
  • 连续若干轮没有产生可验证进展。
  • 失败反馈不再具有可操作性，或验证器出现冲突。
  • 触及权限边界、风险阈值或人工审批条件。
  • 达到预算、超时、重复任务或依赖不可用。

停止不等于失败。一个好的终止状态可以是 completed、needs_human、budget_exhausted 或 blocked。它们都比无限重试、静默退出或伪造成功更好。

09 · 重试的数学：多跑几轮，成功概率一定更高吗？

先构造一个简单模型，帮助理解为什么重试可能提高成功概率，也为什么预算仍然必要。

假设每次尝试相互独立，并且每次尝试成功概率都相同，记为 p。单次失败概率是 1−p。连续 n 次都失败的概率是 (1−p)n，因此至少成功一次的概率为：

P(success by n)=1−(1−p)n

例如，假设 p=0.30，则 1、2、3、4 次尝试的累计成功概率分别约为 30%、51%、65.7%、76.0%。

但是，Agent 的真实重试通常不满足独立同分布假设：下一轮会看到上一轮失败反馈，成功概率可能上升；也可能因为上下文污染、错误方向和资源耗尽而下降。更一般地，如果第 k 次尝试在此前失败条件下的成功概率是 pk，则：

P(success by n)=1−∏k=1n(1−pk)

9.1 把成本和风险加入目标函数

设成功带来的收益为 R，每轮平均成本为 c，风险成本随重试次数 n 增加为 r(n)，风险权重为 λ。简化后的期望效用可以写成：

U(n)=R[1−(1−p)n]−nc−λr(n)

第一项是至少成功一次的期望收益；第二项是执行成本；第三项是失败副作用、误操作概率和验证负担等风险成本。增加一次尝试的边际收益会逐渐下降，因此不能仅凭“还有机会”就无限继续。

在这个简化模型中，从 n 次增加到 n+1 次值得考虑的条件是：新增成功机会的预期收益，大于新增执行成本和风险成本。若每轮独立且成功率恒定，边际收益项为 Rp(1−p)n。

工程含义：重试预算应由任务价值、失败反馈质量、验证可靠性和副作用共同决定。对可回滚的文档格式修复，可以允许少量自动重试；对不可逆的数据删除或资金操作，不能因为重试次数还没用完就继续执行。

以上是独立性假设下的教学推导，用于解释重试成本，不是 Loop Engineering 论文中的实测模型，也不能直接用来预测真实 Agent 的成功率。

10 · 交互实验：亲自观察一个有预算的 Loop

下面用一个完全确定的玩具任务模拟代码修复：第一次测试失败，第二次仍有错误，第三次通过。你可以调整最大尝试次数，观察系统如何在“继续尝试”和“预算耗尽”之间做选择。

范围 1–5

等待启动：系统将按顺序读取测试结果，并在通过、升级或预算耗尽时停止。

试着把预算设为 1：第一次验证失败，系统就必须停止，不能假装完成。设为 2：第二次仍失败，依然无法完成。设为 3 或更高：第三次才会通过。真实系统还需要判断失败是否可修复、是否值得继续、是否触发人工升级；本演示只隔离“预算与停止条件”这一变量。

11 · 端到端案例：自动维护一个软件仓库

假设团队希望 Agent 每天巡检一个开源仓库，自动修复低风险问题，并将高风险问题交给维护者。一个有边界的 Loop 可以这样设计：

阶段具体动作验收 / 安全要求
触发每天定时运行；收到 CI 失败事件时额外触发同一事件 ID 只进入一次队列
发现读取开放 Issue、失败工作流和未解决告警去重；排除已关闭、已修复和超出范围的任务
上下文加载 Issue、相关文件、最近提交、历史失败与项目规范固定基线 commit SHA，记录证据来源
执行在隔离分支中修改代码、文档或测试只允许写入白名单路径；不直接写生产环境
验证运行格式化、静态检查、单元测试与相关集成测试测试结果关联本次 commit；禁止只根据 Agent 自评通过
写回保存 diff、测试报告、成本、状态和下一步状态记录不可覆盖来源和版本信息
决策低风险且通过则创建 PR；失败则有限重试；权限或语义不确定则升级合并与生产部署默认保留人工审批

这个案例体现出 Loop Engineering 的重点：不是让一个 Agent 拥有无限权限，而是把任务划分成多个有明确输入、输出和验收条件的步骤。系统可以自动做大量低风险工作，但最终交付仍然要有可审计的证据链。

OpenAI 的迭代修复示例展示了“检查 → 修复 → 验证 → 把剩余问题反馈给下一轮”的工作流。[4] OpenAI 的 Agent Improvement Loop 示例则把真实运行轨迹、人工反馈、模型反馈、评测集和下一轮 Harness 修改连接起来，强调让每次运行的经验沉淀为可重复执行的评测。[5]

12 · 最小 Python 控制器：让成功、失败和升级成为显式状态

下面的代码不是完整的 LLM Runtime，而是一个小型控制器。act 代表执行 Agent，verify 代表验证器；控制器负责限制尝试次数、把失败反馈传给下一轮、持久化状态，并在通过、升级或预算耗尽时停止。

from dataclasses import dataclass
from pathlib import Path

@dataclass(frozen=True)
class Verdict:
    passed: bool
    feedback: str = ""
    escalate: bool = False

def run_loop(task_id, act, verify, state_path: Path, max_attempts=3):
    state = _load(state_path, task_id)

    if state["status"] in {
        "completed", "needs_human", "budget_exhausted"
    }:
        return state

    while state["attempts"] < max_attempts:
        state["attempts"] += 1
        state["status"] = "running"
        _save(state_path, state)

        proposal = act(
            state["last_feedback"], state["attempts"]
        )
        verdict = verify(proposal)

        if verdict.escalate:
            state["status"] = "needs_human"
            state["last_feedback"] = verdict.feedback
            _save(state_path, state)
            return state

        if verdict.passed:
            state["status"] = "completed"
            state["artifact"] = proposal
            _save(state_path, state)
            return state

        state["last_feedback"] = verdict.feedback
        state["status"] = "retrying"
        _save(state_path, state)

    state["status"] = "budget_exhausted"
    _save(state_path, state)
    return state

仓库中的配套实现 loop_engine.py 补充了 JSON 状态读写、原子替换、任务 ID 校验和终态防重复执行；测试文件覆盖重试后通过、预算耗尽、人工升级、终态不重复执行和状态文件错配。

12.1 为什么先保存 running 状态？

执行前写入状态，可以让系统知道任务已经开始，并记录已消耗的预算。每次验证后再保存反馈与终态。这样即使进程中断，下一次也有机会识别上一次停在什么位置。但这并不自动解决分布式并发或外部副作用的恰好一次执行问题。

12.2 这个玩具控制器没有解决什么？

  • 没有任务租约、并发锁和分布式队列。
  • 没有把外部 API 副作用与状态写入放进同一个事务。
  • 没有 exactly-once 语义；真实系统通常需要幂等键和可恢复操作。
  • 没有真正的容器沙箱、网络隔离、密钥管理和权限策略。
  • 没有实现独立验证器的身份、模型隔离或验证器自身的评估。

因此它是教学控制器，不是生产级自主 Agent 平台。不要把一个 JSON 文件和 while 循环直接部署成有生产写权限的守护进程。

13 · 如何评估一个 Loop 是否真的更好？

如果只统计 Agent 调用了多少次工具、写了多少行代码，容易把忙碌误认为进展。评估至少要同时覆盖最终结果、过程质量、资源成本和治理效果。

维度指标示例要回答的问题
结果质量任务成功率、人工验收通过率、回归缺陷率最后交付的东西是否真的正确？
验证器质量False Pass、False Fail、覆盖率、人工复核一致率系统是否会错误地宣布完成？
执行效率平均尝试次数、端到端耗时、每个成功任务的成本为得到一个正确结果付出了多少代价？
状态质量恢复成功率、重复任务率、状态冲突率下一轮是否能准确接上上一轮？
人类参与人工升级率、审批等待时间、人工返工率自动化减少了多少重复工作，又把什么交给人？
安全治理越权尝试数、预算超限数、不可逆副作用数系统是否在边界内行动？

比较两套 Loop 时，必须固定任务集合、模型版本、工具权限、预算和验证器，或者明确报告这些变量的差异。否则，成功率提升可能来自更大的 Token 预算、更宽松的测试标准或不同的任务难度，而不是 Loop 设计本身。

还应做消融：去掉持久化、去掉独立验证、去掉去重、缩小预算、取消人工升级，分别观察结果变化。对长期运行系统，除了平均成功率，还要报告失败分布、尾延迟、成本分位数和最坏情况下的行为。

14 · 失败模式：Loop 为什么可能越跑越差？

14.1 Infinite Retry：无限重试

没有硬性预算或终止条件，失败就反复执行。结果可能是成本失控、工具限流，甚至对外部系统造成重复副作用。

14.2 Reward / Verifier Hacking：迎合验证器

如果只检查“测试是否通过”，Agent 可能通过删除失败测试、弱化断言或缩小覆盖范围来制造假成功。验证器必须检查目标完整性，而不只是执行退出码。

14.3 Stale State：状态过期

上一轮基于 commit A 的结论，不能直接套用到已经变化的 commit B。审批和测试证据应绑定具体版本；关键输入变化时，旧证据需要失效或重新验证。

14.4 Context Drift：上下文漂移

状态摘要可能遗漏约束，旧记忆可能被误当成当前事实。恢复时应重新检查关键文件、版本和外部资源，而不是无条件相信摘要。

14.5 Oscillation：来回振荡

Agent 在两个方案之间反复切换。可以记录已尝试的方案、失败证据和状态指纹；若连续几轮没有新证据或目标指标没有改善，应停止并升级。

14.6 Trigger Storm：触发风暴

一个任务的写回又触发新的事件，导致循环自我放大。需要事件来源过滤、幂等键、去抖动、并发上限和明确的触发白名单。

14.7 Human Comprehension Debt：理解债务

如果 Agent 持续产出大量没人审阅的变更，系统虽然“跑得动”，维护者却逐渐失去对仓库的理解。需要结构化变更记录、可读 diff、风险摘要和定期人工抽检。

关键原则：一个循环不应只优化“继续运行的能力”，还要优化“识别无效进展、保留证据、停止错误动作和向人交接”的能力。

15 · 研究现状：哪些已经有证据，哪些仍然只是工程假设？

Loop Engineering 作为术语很新，但它所依赖的机制并不是从 2026 年才开始出现。可以沿着研究谱系理解它：

工作贡献与 Loop Engineering 的关系
ReAct (2022 / ICLR 2023)交错生成推理轨迹、外部行动和环境观察提供单次 Agent 运行的内层行动反馈机制
Reflexion (2023)将环境反馈转化为语言反思，并存入 episodic memory说明失败经验可以被显式记录并影响后续尝试
Self-Refine (2023)同一个模型交替生成反馈与改进候选输出提供单任务迭代改进的基础模式
Anthropic long-running harness (2025)通过初始化、进度文件和增量会话支持跨上下文持续工作展示状态交接和长期任务分段的工程设计
OpenAI Codex agent loop (2026)解释模型推理、工具调用和反馈如何组成内层循环展示 Agent Runtime 的循环结构
Loop Engineering: Building Blocks, Adoption, and Impact (2026)梳理实践构件，并开展仓库挖掘探索直接研究新兴 Loop Engineering 实践及其证据缺口

这项 2026 年预印本报告分析了 36,710 个软件仓库，并在启发式筛选的 256 个候选仓库中确认了 217 个自主循环案例。研究还指出：虽然仓库里可以看到循环配置，但几乎没有仓库提交实践讨论中所建议的持久状态文件；受控实验仍是计划中的研究方向。[1]

如何正确解读这组数字？217 / 256 是在启发式筛选候选集中的确认比例，不是“全球 84.8% 的仓库都在使用 Loop Engineering”。36,710 是被挖掘的仓库规模，也不是受控实验样本。该研究支持“这种实践已经出现在开源仓库中”，但不证明“Loop Engineering 一定提高开发效率或代码质量”。

15.1 仍然值得研究的问题

  • 自主等级：只允许自动分析、自动修改、自动开 PR、自动合并和自动部署，哪一种授权边界最合适？
  • 验证器独立性：如何测量验证器的漏检率、偏差和与生成器共享的错误？
  • 状态一致性：多 Agent 并行时，如何处理竞争写入、过期审批、重复事件和状态冲突？
  • 停止策略：如何根据剩余成功概率、边际收益、成本和风险决定是否再试一次？
  • 长期效应：自动循环是否会积累理解债务、评测债务和维护负担？
  • 跨领域迁移：代码修复中的测试门，如何迁移到研究、数据治理、文档维护或运营流程？

16 · 总结：把“持续运行”变成“持续负责”

Loop Engineering 的价值不在于让 Agent 永远不停止，而在于让每一次运行都成为一个有边界、有证据、有状态、有成本记录的工作单元，并让系统知道下一步应该继续、交付、暂停还是升级。

记住四个层次

Prompt 决定怎么说；Context 决定看什么；Harness 决定能做什么；Loop 决定何时再次运行、如何验收和何时结束。

记住五条底线

可验证的成功标准、独立证据、持久状态、硬性预算、人工升级与明确停止条件。

如果要设计自己的第一个 Loop，不妨从一个低风险、可验证、可回滚的任务开始：例如每天检查文档链接、每次 CI 失败后生成诊断报告，或自动整理待处理 Issue。先让触发、状态和验证链条可靠，再逐步增加 Agent 的执行权限。
