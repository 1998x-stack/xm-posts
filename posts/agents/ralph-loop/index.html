Ralph Loop：让 Agent 持续工作，而不是一次性回答

从一个看似简单的 Bash while 循环出发，理解自主 Coding Agent 如何通过任务切片、上下文管理、持久化状态、自动化验证与停止条件，跨越单次会话的限制。

工程方法深度解析（非同行评审论文）建议阅读 28 分钟本科高年级 / 研究生 / Agent 工程实践原始技术文章：2025

01 · 为什么一个 Agent 需要反复启动？

设想你要让一个 Coding Agent 从零构建一门编程语言：它需要读规格、写 Lexer、实现 Parser、生成 LLVM IR、补齐标准库、运行测试、修复编译错误，最后构建真实程序。你会把所有要求一次性塞进一个 Prompt，然后期待它连续工作几个小时吗？

单次长会话的困难不只是“上下文窗口不够大”。更隐蔽的问题是：任务不断增加，历史观察越来越多，早期决策和当前代码逐渐不一致；模型可能重复搜索、重复实现、忘记某个约束，甚至在一个看似合理的局部修复中破坏其他模块。

单次长会话

同一个上下文不断累积工具输出、失败日志、计划和解释。模型需要在越来越长的历史中识别当前最重要的状态。

上下文持续增长

迭代式执行

每一轮只处理一个有边界的任务。完成后把代码、测试、计划和结果写回仓库，再启动下一轮。

工作单元受控

Ralph 的关键变化不是“让模型变得更聪明”，而是把软件工程中的任务调度、状态持久化和验证环节放到模型外部。模型仍可能犯错，但系统能更快地发现错误、保存进展，并给下一轮提供可检查的状态。

先建立正确直觉：Ralph Loop 不是一个更大的 Agent，而是一个包裹 Agent 的外层执行控制器。它让一个长任务变成一系列短任务，并让每次尝试都留下可供下一轮读取的工程状态。

02 · Ralph 到底是什么？

Geoffrey Huntley 在 2025 年 7 月发表的原始文章中，把 Ralph 概括为一种技术（technique），而不是一个特定模型或多智能体框架。最简形式是反复向 Coding Agent 提交同一个 Prompt：

while :; do
  cat PROMPT.md | claude
done

这段代码没有复杂的 Planner、Agent Registry 或消息总线。外层 Shell 负责再次启动 Agent；Prompt 告诉它目标和下一步工作；仓库文件保存上轮留下的结果。Huntley 强调每轮只做一件事，并把规格与优先级计划固定放在每轮都能读取的位置。[1]

因此，Ralph 不等于以下任何一项：

  • 不是模型架构：它不改变 Transformer、注意力机制或模型训练目标。
  • 不是 ReAct 的同义词：ReAct 描述一次 Agent 运行中的 Thought / Action / Observation；Ralph 描述跨轮次的外层执行与恢复。
  • 不是多智能体的必要条件：可以只有一个主 Agent。需要时可把搜索、代码审查或测试摘要交给子 Agent，但这不是循环成立的前提。
  • 不是“失败就无限重试”：没有规格、验证、预算和停止条件的循环，只会把错误重复很多次。

Ralph 的“持久”来自外部状态，而不是模型本身获得了永久记忆。模型每次看到什么、如何恢复、何时停止，都由执行器和项目文件共同决定。

03 · 上下文与持久状态：两个不同的记忆层

理解 Ralph 最重要的概念，是区分 Context（上下文） 与 Durable State（持久状态）。

上下文是当前模型推理时能直接使用的信息：系统指令、Prompt、当前任务、最近的工具输出和对话历史。它属于一次运行过程，容量有限，而且可能被压缩、截断或重新初始化。

持久状态则存在于模型进程之外：代码仓库、规格文件、任务清单、测试、Git commit、构建日志和项目级 Agent 指南。它们可以在下一轮重新读取，也可以被人类检查、修改和回滚。

短暂层：Context

  • 当前 Prompt 与系统约束
  • 当前任务和相关文件片段
  • 最近的工具结果与错误信息
  • 本轮推理中的临时假设

持久层：Repository State

  • 规格、验收标准和任务清单
  • 源代码、测试与配置
  • Git 历史和可回滚检查点
  • AGENTS.md / 项目运行手册

这是一种重要的 Context Engineering 设计：不把所有历史塞进模型，而是每轮根据当前任务重新组装最小必要上下文。它与 Agent Memory 有联系，但也不完全相同：Memory 关心跨任务经验如何沉淀和复用；Ralph 更关心当前项目状态如何让下一轮继续执行。

容易忽略的细节：“重新启动 Agent”不等于“自动恢复任务”。如果上轮只把关键决策留在对话里，没有写进规格、代码、测试或进度文件，那么下一轮确实会失去这些信息。

04 · 用状态机描述 Ralph 的一轮执行

为了分析它的行为，可以把每轮开始时的持久状态写成一个向量。这里的符号是教学抽象，不是 Huntley 原文提出的数学定理。

Dt=(Rt,P,T,Gt,Mt)
式（1）· D：持久状态；R：仓库快照；P：规格；T：验证集合；G：Git 历史；M：剩余迭代预算。

模型本轮看到的上下文不是全部持久状态，而是从中选择、整理后的工作集：

Ct=Init(P,Dt),Δt=A(Ct)
式（2）· Init 代表上下文装配；A 代表当前 Agent。不同实现可以用 Shell、Stop Hook 或其他执行器。

Agent 生成代码变更后，系统先应用变更，再运行验证器。验证结果必须进入下一轮可读取的持久状态：

Rt′=Apply(Rt,Δt),vt=Verify(Rt′,T)
Dt+1=Persist(Rt′,P,T,Gt,vt)
式（3）· Verify 是外部验证器；Persist 把代码、测试结果、进度与必要的检查点写回。

停止条件也应该写成一个逻辑条件，而不是模型主观感觉“差不多了”。

Completet=SpecSatisfied(Rt′,P)∧ChecksPass(Rt′,T)∧NoRegression(Rt′)
式（4）· 完成承诺（completion promise）是信号，不是证据；外部验证仍然必须成立。

这组公式把系统分成四个不同职责：上下文装配、模型生成、外部验证、状态持久化。只要其中一环缺失，循环就可能无法恢复、无法验证或无法停止。

05 · One item per loop：任务粒度决定循环是否稳定

Huntley 多次强调“一轮只做一件事”。这不是要求每轮只能改一行代码，而是要求每个工作单元的目标、边界和验收标准足够明确，能够在一个上下文预算内完成并验证。[1]

任务描述粒度判断更好的验收方式
“构建完整编译器”过大拆成 Lexer、Parser、类型检查、IR lowering、代码生成等任务。
“实现字符串 Token 的转义处理”合适定义输入语法、非法转义行为和单元测试。
“修复所有编译错误”过宽先按错误类型和依赖关系分组，再逐个修复。
“给空输入添加明确错误，并保留原有解析行为”合适增加边界测试、回归测试，验证错误类型和旧行为。

一个好任务通常具备五个属性：目标可描述、修改范围可定位、前置依赖明确、验收标准可执行、失败时能留下可诊断的信息。若某项任务无法在一个 Agent 回合中完成，通常应该先进一步拆分，而不是盲目增加循环次数。

06 · Backpressure：为什么测试反馈比“再想一想”重要？

生成代码很容易，确认代码正确更难。Ralph 的外部反馈（backpressure）负责拒绝明显不合格的增量：单元测试、集成测试、类型检查、Lint、静态分析、安全扫描和构建结果都可以成为反馈信号。Huntley 原文特别强调测试、类型系统和快速构建循环的重要性。[1]

为什么不能只看 Agent 输出的“完成”文本？因为模型的自然语言声明并不等价于软件系统的状态。代码可能没有编译，测试可能被删除，边界条件可能没有覆盖，或者修改引入了原本不存在的回归。

快反馈

格式检查、Lint、局部单元测试、类型检查。它们成本低，适合每个小任务执行。

慢反馈

完整集成测试、端到端测试、性能与安全扫描。成本更高，可以在重要检查点或阶段结束时执行。

一个实用策略是分层验证：先跑最相关的局部测试，失败就停止并修复；局部通过后再跑更广的测试；最后检查 Git diff、依赖变更和安全边界。验证的速度必须足够快，否则每轮循环都在等待，反馈周期会变得很长。

测试也可能被“优化”错：如果任务只要求“所有测试通过”，Agent 可能删除失败测试、缩小断言范围，甚至跳过验证。因此验收条件应包含“原有测试不得被无理由删除或禁用”“测试覆盖的行为不得倒退”等约束，并检查实际 diff。

07 · 计划、规格、AGENTS.md 与 Git：如何让下一轮接得上？

Ralph 的持久化状态不是一份越来越长的聊天记录。更可靠的做法是把不同职责放在不同文件里：

工件职责更新频率
specs/*.md定义目标、功能边界、接口、非目标和验收标准。需求变化时审查更新，不能随意被执行回合改写。
fix_plan.md记录尚未完成的任务、优先级、依赖和当前进度。每轮完成或发现阻塞后更新。
AGENTS.md记录仓库约定、构建命令、测试命令、目录边界和常见陷阱。发现可复用的工程知识时小幅更新。
测试与日志保存机器可执行的行为约束与诊断证据。代码变化时同步维护。
Git commit创建可追溯、可比较、可回滚的版本检查点。每个通过验证的工作单元完成后。

这里有一个重要的设计原则：规格描述“应该是什么”，计划描述“下一步做什么”，测试描述“如何证明”，Git 描述“实际改变了什么”。 不要让一个文件同时承担所有职责。

Git commit 尤其重要。它不仅是备份，还为下一轮提供可审计的变化历史：上一轮修改了哪些文件、改动规模如何、是否删除了测试、失败后从哪个状态恢复。对于高风险项目，建议每轮在独立分支或 Worktree 中执行，并只提交明确验证过的变更。

健康场景中，局部测试先暴露缺陷，Agent 修复后通过验证，状态被持久化。振荡场景中，两个实现方案反复推翻彼此，说明任务约束不足或状态记录不完整。虚假完成场景中，模型发出了完成承诺，但验证器发现测试被删除，因而拒绝终止。

09 · Ralph 与 ReAct：内层行动循环和外层执行循环

Ralph 与 ReAct 可以嵌套理解，而不是互相替代。

例如，一轮 Ralph 任务是“实现 Parser 的数组字面量语法”。这次 Agent 运行内部可能采用 ReAct：

  1. Thought：判断需要先检查现有语法规则。
  2. Action：搜索 Parser 文件并读取相关测试。
  3. Observation：发现数组语法尚未实现，但已有列表表达式。
  4. Thought / Action：提出最小改动，编辑 Parser 并运行测试。
  5. Observation：测试失败，错误信息指出逗号后的 token 未被消费。

当这一轮 Agent 结束后，Ralph 外层执行器检查测试、更新计划并持久化变更。下一轮再选择另一个任务。于是系统形成两个时间尺度：内层 ReAct 负责单轮操作，外层 Ralph 负责跨轮次的任务连续性。

Ralph 与 Harness Engineering：局部模式与完整系统

Harness Engineering 讨论的是更大的系统边界：模型接入、工具接口、上下文交接、项目记忆、权限、安全、任务编排、可观测性、独立评估和维护治理。Ralph Loop 则是这个系统中一种具体的外层迭代执行模式，重点是任务切片、跨轮次状态恢复、反馈验证和停止条件。

因此，Harness 可以包含 Ralph，但 Harness 不等于 Ralph；反过来，一个最小 Bash 循环也不自动拥有完整 Harness 所需的权限隔离、可观测性和评估能力。

继续阅读：Understanding Harness Engineering，了解如何把模型、工具、上下文、状态、安全与验证组织成完整的 Agent Runtime。

10 · 两种常见实现：Shell 进程循环 vs Stop Hook

“Ralph Loop”这个名称在实践中指向不止一种实现。必须先说明具体执行器，否则“每轮上下文是否重置”很容易被误解。

维度经典 Shell RalphClaude Code Ralph Loop 插件
触发方式外部 Shell 的 while / for 循环会话生命周期中的 Stop Hook
进程边界每轮重新启动 CLI 进程在当前 Claude Code Session 内继续
上下文通常是新的模型上下文；需从文件恢复同一会话继续，不能简单视为每轮清空上下文
持久状态Prompt、仓库、计划、Git 历史项目状态文件、仓库、Git 历史和会话 transcript
停止机制Shell 退出码、验证脚本、最大轮数完成承诺与最大迭代数
适合关注进程隔离、上下文重置、外部预算和可恢复性会话内迭代、Hook 行为、状态文件与会话隔离

Anthropic 官方插件 README 说明，插件通过 Stop Hook 拦截退出、重新提交同一 Prompt，并使用工作目录中的文件和 Git 历史保留工作结果。其实现还使用状态文件记录迭代次数、最大迭代数、完成承诺和 Session ID。[2][3]

在官方 Stop Hook 源码中，完成承诺需要与设定字符串精确匹配；达到最大轮数时会清理状态文件并允许退出。Hook 还会检查 Session ID，避免其他会话误触发同一轮循环。[4]

不要把产品插件的实现细节推广成所有 Ralph 的属性。尤其是上下文重置：进程级循环通常重新开始一次模型调用；Stop Hook 插件则是在同一会话中重新注入 Prompt。选型时应核对具体执行器的源码和版本。

11 · 一个更可控的 Shell 循环示例

下面的代码展示外层控制器的关键结构。它是教学骨架，不是可以不经修改就用于生产的脚本。实际项目必须替换验证命令、处理退出码、设置工作目录隔离，并根据模型 CLI 的版本核对参数。

#!/usr/bin/env bash
set -uo pipefail

MAX_ITERATIONS=12

for ((i = 1; i <= MAX_ITERATIONS; i++)); do
  echo "Ralph iteration $i/$MAX_ITERATIONS"

  # A new CLI process is started for each iteration.
  if ! claude -p "$(cat PROMPT.md)"; then
    echo "Agent process failed; stop for inspection." >&2
    exit 2
  fi

  # This verifier must check objective acceptance criteria,
  # not merely search the model's final text for "DONE".
  if ./scripts/verify-iteration.sh; then
    echo "Verified completion."
    exit 0
  fi

  # Keep the next iteration's state inspectable.
  git diff --check
  git status --short
done

echo "Iteration budget exhausted; human review required." >&2
exit 3

这个骨架故意没有自动 git push，也没有执行 git reset --hard。对于长时间无人值守的任务，建议先在独立 Worktree / 容器和专用分支里运行；验证通过后，再由受控步骤创建 commit 或 PR。部署、数据库迁移、删除数据和修改权限等不可逆操作应设置人工审批。

停止判断的最小可执行模型

完成承诺只是一个输入。只有测试通过、没有未解决阻塞和回归时，才能返回完成状态：

from dataclasses import dataclass

@dataclass(frozen=True)
class Verification:
    completion_promise: bool
    tests_pass: bool
    blockers: int = 0
    regressions: int = 0

def decide(check, iteration, max_iterations):
    if iteration < 1 or max_iterations < 1:
        raise ValueError("iteration and budget must be positive")
    if check.blockers < 0 or check.regressions < 0:
        raise ValueError("counts cannot be negative")

    if (check.completion_promise and check.tests_pass
            and check.blockers == 0 and check.regressions == 0):
        return "complete"
    if iteration >= max_iterations:
        return "budget_exhausted"
    return "continue"

仓库中的 loop_gate.py 与 test_loop_gate.py 给出了对应的标准库实现和单元测试。它验证的是停止策略，不是一个真实 LLM 的代码生成质量，也不代表完整 Ralph 执行器。

12 · 收敛不是保证：如何判断循环在进步？

Ralph 经常被描述为“持续迭代直到完成”。但从算法角度看，循环本身并不保证收敛。Agent 输出具有随机性，任务规格可能不完整，验证器只能观察它覆盖到的行为，下一轮甚至可能推翻上一轮的实现。

为了分析进度，可以定义一个教学用的“未完成势函数”。例如：

Φt=αUt+βRt+γKt
式（5）· U：未满足验收项；R：回归数；K：阻塞数；权重 α、β、γ 由项目风险决定。

理想情况下，一轮有效工作会让未完成项减少，同时不增加回归和阻塞。但这个势函数只是工程诊断工具：它不一定可完全观测，也不是 Ralph 的数学收敛证明。

工程上可以用三条规则检测循环是否正在失效：

  1. 进度必须可观测：每轮记录完成了哪些验收项、哪些测试通过、哪些问题仍未解决。
  2. 变化必须可审查：比较相邻 commit，检测反复修改同一文件、重复实现和无意义回滚。
  3. 停滞必须可退出：连续若干轮没有降低未完成项，或者错误类型反复相同，应停止自动循环并请求人类重新规划。

13 · 典型失败模式：循环为什么会跑偏？

失败模式根因可执行的防护
重复实现搜索结果不完整，Agent 误以为功能不存在。修改前检查代码和测试；要求引用已有实现位置。
方案振荡任务目标太宽，下一轮重新选择另一种合理方案。固定架构决策、接口与约束；缩小单轮范围。
规格漂移原始规格存在矛盾，后续回合不断补偿错误假设。先做独立规划审查；规格变更必须记录理由。
测试投机Agent 只追求通过测试，删除测试或缩小断言。保护基线测试；比较测试数量、覆盖行为与 diff。
假完成模型输出完成标记，但功能或验收条件未满足。完成承诺与独立验证器分离。
上下文丢失关键决策只存在于上一轮对话，没有持久化。更新规格、计划、AGENTS.md 和测试说明。
无限消耗缺少迭代上限、成本预算或外部停止机制。最大轮数、最大时长、token / API 预算和人工中止。
代码库损坏未验证改动进入下一轮，错误不断叠加。独立分支、检查点、失败即停和可恢复工作区。

Huntley 的原始文章并没有把 Ralph 描述成不会犯错的自动工程师。他明确讨论了错误搜索、重复实现、错误规格、占位实现和构建失败，并把持续观察与调整提示称为“调音”。他也强调工程师仍然需要参与判断。[1]

这意味着 Ralph 的真正工程能力，不只是让模型继续运行，而是让每种错误都能留下足够具体的反馈，并让操作人员能够调整规格、测试或执行策略。

14 · 安全与预算：无人值守不等于不受约束

Ralph 的自动化能力越强，权限边界就越重要。循环中的 Agent 可能反复调用 Shell、读写文件、安装依赖、修改配置或访问外部服务。一次错误决策在长时间运行中可能被重复放大。

执行隔离

  • 独立分支或 Git Worktree
  • 容器或受限运行环境
  • 最小化文件与网络权限
  • 只允许必要的命令与工具

预算与审批

  • 最大迭代数与最大运行时长
  • Token、API 和计算成本预算
  • 危险操作前要求人工确认
  • 失败次数与停滞阈值

建议将操作分为三个等级：

  • 低风险：读取文件、搜索代码、运行只读测试，可以在沙箱中自动执行。
  • 中风险：修改源代码、更新依赖、创建 Git commit，应限制工作区并保留检查点。
  • 高风险：推送主分支、生产部署、数据库迁移、删除数据、修改权限和处理密钥，应通过明确的审批门禁。

Anthropic 官方插件使用最大迭代数和完成承诺作为循环控制机制；这些限制不能替代外部资源预算和权限隔离。[2][3] 如果系统出现状态文件损坏、会话串扰或无法可靠中止等问题，外部进程管理器和操作员仍应拥有最终停止权。

15 · 什么任务适合 Ralph？

任务类型适合程度理由
从零构建有规格的项目较适合模块边界清楚，能按功能逐步完成，并用构建与测试反馈。
批量迁移或机械式重构有条件适合需要明确迁移规则、回归测试和小批次变更。
自动修复可复现的测试失败较适合失败信号明确，但必须避免只修改测试来消除错误。
需求不清晰的产品设计不适合直接循环需要先通过人类讨论澄清目标和权衡。
生产事故与线上热修复谨慎风险高、上下文敏感，自动重复操作可能扩大影响。
依赖主观判断的创意任务不适合无人值守缺少稳定、自动化的完成判据。

值得注意的是，Huntley 在原文中把该方法的优势主要放在 Greenfield 项目，并明确表达了对直接用于既有复杂代码库的保留态度。这是作者基于自身实践提出的范围判断，不应被误读为所有项目的普遍定律。[1]

官方插件也把任务定义清楚、成功标准明确、可以自动验证的迭代开发列为主要使用场景，同时提醒不要把它当作需要人类判断的任务的替代品。[2]

16 · 如何严谨评估一个 Ralph 系统？

Ralph 本身是一种工程方法，不是有统一公开 Benchmark 的模型。因此，不能拿某个演示项目的完成时间或作者分享的成本案例，直接推导“Ralph 一定比人工开发快多少”。更合理的方式是为自己的项目建立可复现的评估协议。

指标定义要回答的问题
Verified Task Success通过全部验收条件的任务数 / 总任务数任务真正完成了多少？
Regression Rate引入回归的迭代数 / 总迭代数系统是否在修复中破坏已有功能？
False Completion Rate声明完成但验证失败的次数 / 完成声明次数停止信号是否可信？
Iterations per Verified Task完成一个已验证任务所需的平均迭代数循环是否高效？
Cost per Verified Task完成一个已验证任务的模型、运行与人工审查成本自动化是否真的降低总成本？
Recovery / Rollback Rate需要人工恢复或回滚的任务比例系统是否可恢复？

评估时还应固定模型版本、Prompt、代码仓库快照、测试基线、最大迭代数和权限配置。对于多次随机运行，报告均值、方差和失败案例；不要只展示一次最成功的运行。

如果要比较 Shell 进程级循环与 Stop Hook 方案，还需要单独控制上下文策略：前者每轮重启进程，后者在当前 Session 内继续。否则实验结果会混合“执行器差异”和“上下文生命周期差异”，无法解释究竟是哪一项带来了变化。

17 · 总结：把循环做成可靠的工程系统

Ralph Loop 的核心价值，不是让 Agent 永远不停止，而是让长周期任务拥有明确的工作单元、持久状态、外部反馈和可验证的终止条件。

记住五个原则：
  1. 先把需求写成规格，再启动执行循环。
  2. 一轮只完成一个边界清楚的任务。
  3. 把代码、计划、测试和运行知识写回持久状态。
  4. 每轮都用外部验证器检查真实结果。
  5. 使用最大迭代数、成本预算和人工审批限制风险。

从知识体系来看，Ralph 位于 Agent Engineering 的外层执行控制：它建立在工具使用、软件工程 Agent、上下文管理和持久化状态之上，并与 ReAct、Agent Memory、Context Engineering 形成互补。

建议沿着这条路径继续学习：

  • Understanding ReAct：理解单次运行中的思考、行动和观察。
  • Understanding SWE-agent：理解 Agent 如何通过 ACI 搜索、编辑和验证代码。
  • Understanding Agent Memory：理解跨会话经验如何写入、组织和重用。
  • Understanding Harness Engineering：理解模型、工具、上下文、状态、权限和评估如何组成完整运行时。
  • Ralph Loop：理解这些能力如何被外层执行控制器组织成长周期任务。
