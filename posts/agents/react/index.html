PAPER STUDY · ICLR 2023 · AGENTS & TOOL USE

Understanding ReAct

模型何时该思考，何时该行动？从 Thought → Action → Observation 的闭环，理解语言模型如何与外部世界共同解决任务。

Shunyu Yao et al. · ICLR 2023约 32 分钟ReAct · Agentic Reasoning & Tool Use

01 · 从一个失控的检索问题开始

问题不是模型不会组织语言，而是它不知道什么时候该停止猜测，去外部世界取证。纯 Chain-of-Thought 可以连续推导，却可能在第一个错误事实后不断放大偏差；只执行工具的代理能检索，却可能忘记“为什么要找这个事实”。

设想一个虚构的问答：“Lumen 计划归属哪个团队？这个团队的负责人是谁？” 文档索引只告诉你 Lumen 属于 Aurora 团队；还需要第二次查询才能知道负责人。推理与外部动作必须在同一条任务轨迹中轮流发挥作用。这正是 ReAct 所针对的缺口。

核心转变：不是“先想完，再执行”，而是每次观察都可能修正下一步意图；推理不自动等于事实，动作也不自动等于有效进展。

02 · CoT、Act 与 ReAct：少了哪一环？

原论文使用可控制的消融比较：CoT 保留自然语言推理但移除工具动作与观察；Act 保留动作与观察但删去语言思考；ReAct 保留两者的交错轨迹。三者并非大小不同的“模型架构”，而是同一个语言模型在不同提示轨迹下的行为形式。

CoT 的长处

完整的语言推导便于跨步骤综合；短处是推导期间没有被外部证据纠正的必然机制。

Act 的长处

可获得真实环境反馈；短处是动作选择缺少明确的子目标分解与进度跟踪。

03 · 论文 §2：把 Thought 加入可选动作空间

论文从交互式代理出发：在第 t 步，观察属于环境观察空间 O，实际动作属于环境动作空间 A，策略按历史上下文选动作。下面使用对应的下标与条件概率。

ct=(o1,a1,…,ot),π(at|ct)
式（1） · 第 t 步历史上下文与条件动作策略

关键的形式化：除环境动作集 A 外，引入语言空间 L，其中的输出被称作 Thought。它只更新模型拥有的上下文，不直接修改环境，不立即获得外部观察。原文用扩展动作集说明这一点。

𝒜^=𝒜∪ℒ
式（2） · 扩展动作空间等于环境动作与语言思考的并集
ct+1=(ct,a^t),a^t∈ℒ
式（3） · 思考步骤仅改变上下文
ct+1=(ct,at,ot+1),at∈𝒜
式（4） · 环境动作执行后追加外部观察

式（3）–（4）是将原论文 §2 的文字机制写成统一记号的教学展开；真实环境的时间索引、提示 token 顺序与观察返回格式依工具定义而定。上式不是 ReAct 新提出的神经网络训练损失，也不意味着语言思考能保证决策正确。

04 · 从 few-shot 轨迹到 search / lookup / finish

原论文知识检索任务使用一个简化 Wikipedia 接口：search[entity]、lookup[string]、finish[answer]；HotpotQA 使用 6 个示例、FEVER 使用 3 个示例，示例包含人工撰写的 Thought、Action 和工具 Observation（论文 §3.1–3.2）。检索结果是外部信息，不能作为模型已经知道的事实。

Question: [虚构] Lumen 计划所属团队的负责人是谁？
Thought 1: 需要先确定 Lumen 的团队归属。
Action 1: search[Lumen]
Observation 1: Lumen 归属于 Aurora 团队。
Thought 2: 还缺少 Aurora 的负责人信息。
Action 2: lookup[Aurora]
Observation 2: Aurora 团队负责人是 Lin。
Thought 3: 两条记录已构成可核对的链。
Action 3: finish[Lin]

以上是自制的封闭世界教学轨迹，不是论文附录的原始案例，也不是实际模型生成结果。它展示了为什么一次工具调用往往不足以完成多跳任务。现代函数调用 API 的 JSON schema、角色分隔和权限系统属于后续工程实现，不是 2023 年 ReAct 论文的必备组件。

05 · 交互：观察如何改写下一步计划？

在下面的可重复轨迹中，按“下一步”依次观察两次工具调用。切换至“首轮检索失败”能看到重写查询，而不是把空结果当成答案。演示使用预置规则与虚构资料，不会发送网络请求或调用真实模型。

Lumen → Aurora → Lin

场景：资料索引可以按项目名检索。

任务：找出虚构计划 Lumen 的所属团队负责人。

当前步骤 0 / 7

对照：当 Observation 不可靠或为空，ReAct 并不会在数学上保证“再搜一次就有答案”；是否更改查询、回退 CoT、请求人工接管，都是策略或产品策略问题。

06 · 论文表 1：检索并不保证 ReAct 单独最优

论文报告的是固定实验设置下的提示成绩，不是后来的商业 Agent Benchmark。模型为 PaLM-540B，HotpotQA 用 exact match，FEVER 用 accuracy。原表中，ReAct 的 HotpotQA EM 是 27.4，略低于 CoT 的 29.4；FEVER accuracy 为 60.9，高于 CoT 的 56.3。混合策略才在各自任务上取得最高提示成绩。

方法HotpotQA · EM ↑FEVER · Accuracy ↑
CoT29.456.3
Act25.758.9
ReAct27.460.9
CoT-SC → ReAct34.264.6
ReAct → CoT-SC35.162.0

来源：Yao et al.（2023），Table 1，PaLM-540B prompting；混合方法的回退启发式见 §3.2。SC 通过采样与答案投票引入额外调用预算，因此不能将所有行解释成等成本比较。

一个重要启示：需要搜索的事实性问题与依赖综合推理的问题可能偏好不同的控制策略。ReAct 的贡献不是在所有数据集直接超越 CoT，而是提供了“内部语言推理 + 外部证据”的可组合接口。

07 · 论文表 3–4：在长程交互任务中表现如何？

ALFWorld 是文字化的家庭任务环境；WebShop 是页面导航和商品选择任务。二者与 HotpotQA 的答案匹配不是同一种指标。论文在 ALFWorld 对多个提示试验报告了 best-of-6；WebShop 报告一次提示的成功率（SR），也给出 Score。

ALFWorld：ReAct 的 best-of-6 = 71%，Act 的 best-of-6 = 45%，BUTLER 的 best-of-8 = 37%；ReAct 的六次平均为 57%，不可与最优值混用。WebShop：ReAct 的 SR = 40.0%，IL 的 SR = 29.1%，人类专家 SR = 59.6%。这里 10.9 个百分点的差值来自表中的未四舍五入数字，摘要中的“10% absolute”是概括说法。

来源：论文 Table 3–4、§4，指标均为成功率（%）。这些是作者报告的历史结果，本文没有重跑 PaLM、ALFWorld 或 WebShop。

08 · 为什么不把每一个动作都解释一遍？

ReAct 的语言思考并非必须紧跟每一次环境动作。在长程游戏中，高层子目标只在必要时出现；观察本身常已足以决定下一次具体动作。作者将 ReAct 与一种接近 Inner Monologue 的密集外部反馈方案（ReAct-IM）比较，ALFWorld best-of-6 的整体成功率为 71% 对 53%（论文 Table 3）。

这并不意味着“少思考一定更好”。更准确的解释是：高层计划、子目标检查与常识定位，不等同于重复描述环境状态。增加冗余 Thought 可能消耗上下文，降低追踪能力；删光 Thought 则可能退化成 Act。

09 · 工具是证据通道，也可能成为失败通道

作者人工分析 HotpotQA 轨迹（论文 Table 2）发现，ReAct 的失败中有 23% 属于无用或空搜索结果，47% 属于推理错误（含循环）；这些百分比是作者抽样标注的失败类型分布，不是整个数据集的错误率。搜索不足与错误自我修正，是方法的重要边界。

特别需要区分三层：工具结果可能过时或错误；模型可能误读可信结果；某个结果即使正确也可能与问题无关。检索只增加可用证据，不会自动赋予来源真实性或引用正确性。

10 · 最小可运行控制器：有限状态而非神奇的 Agent

文章附有 react_controller.py 与 test_react_controller.py，用标准库实现预置工具观察、动作白名单、最大步数、缺失信息回退与可核验的状态轨迹。它严格不是论文原模型或 GPT-3 / PaLM 推理复现；作用是将“Thought 不执行工具、Action 才返回 Observation”转成可测试的不变量。

from react_controller import replay
trace = replay(fail_first=True, step_limit=8)
assert trace[-1]["kind"] == "finish"
assert trace[-1]["value"] == "Lin"
assert sum(s["kind"] == "action" for s in trace) == 3
# 测试也覆盖无白名单工具、预算不足与可恢复空结果。

真正的语言模型版本还需模型接口、终止判定、prompt 结构化、可靠检索、工具错误处理以及评测数据。用可执行控制器讲清界限，比将一段固定脚本冒称“模型理解了世界”更可复核。

11 · 现代工具 Agent：哪些是论文外的工程要求？

部署到真实检索、文件系统或网页浏览时，ReAct 的思路只能作为控制流程。一个实际系统还需要：明确可调用工具及参数 schema、参数校验、工具结果来源/时间戳、敏感操作审批、权限最小化、幂等和重试上限、token / 费用 / 时延预算、审计记录以及不受外部内容注入的指令边界。

特别是网页正文和工具返回是不可信数据：其中写着“忽略前面指令”并不因此成为可执行命令。检索结果只能提供事实候选，不应覆盖用户意图、系统指令或工具权限。论文 ReAct 并未提供现代的完整安全防护与攻击抵御证明。

切忌时代错位：LLM function calling、MCP、浏览器 Agent 和多 Agent 编排可以使用 ReAct 式循环，但这些接口与术语不应被倒写成 ICLR 2023 的实验设计。

12 · 如何设计一个可信复现实验？

至少保证同一基础模型、相同工具接口、相似调用/提示预算与共同评价集，再比较 Standard、CoT、Act、ReAct 和 ReAct+CoT-SC。为每条轨迹保留可追踪的 Thought 类型、动作名称与参数、Observation 来源、是否终止、步数与成本；以任务成功和事实可靠性为主，额外记录空检索、循环、错误工具和终止失败。

注意 best-of-six 并不等于一个生产 Agent 的单次可靠性；单纯把最高结果并排展示容易产生选择偏差。对现代模型应重新评估，原文 PaLM-540B 与旧版 GPT-3 的结果不代表今日所有模型的性能。

13 · 何时不适合用 ReAct？

当任务完全确定、不需外部观察时，直接计算或可验证程序通常更简洁。若工具慢、昂贵或高风险，频繁交错调用会造成明显的时延、预算与安全负担。若检索源不可靠，增加动作可能放大噪声；若上下文太长，代理可能重复动作或遗忘目标。应将这些限制当成设计条件，而不是通过更长的提示词掩盖。

ReAct 的精髓是将“下一步思考”和“下一次真实观察”放在同一个反馈回路里，让人可以审计行动依据；但可观察的语言轨迹不等于对模型内部推理过程的完整解释。
