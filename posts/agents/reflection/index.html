Understanding Reflection in LLM Agents

模型第一次回答错了，下一次为什么可能变好？从 Self-Refine、Reflexion 到 CRITIC，拆解反馈、评价、修正与经验记忆如何组成一个可验证的学习闭环。

01 · 为什么需要反思：一次生成不等于一次学习

LLM 可以生成一段看起来很有说服力的解释，但“解释得像正确”与“真的发现了错误”是两回事。Reflection 试图把模型从一次性输出器，变成能够读取反馈、定位错误、提出修正，并在下一轮改变行为的系统。

先看一个最小的程序任务：给定数组 [1, 2, 3]，计算平均值。模型第一次写出 sum(values)，程序能运行，却返回 6；正确答案应该是 2。这里存在四种不同能力：

① 发现不一致

运行测试，观察到 6 ≠ 2。这一步需要评价信号，不只是更多文字。

② 解释失败原因

定位到“求和”与“求平均”之间缺少除以元素个数的步骤。

③ 把反馈变成修正

将实现改成 sum(values) / len(values)，再运行同一组测试。

④ 让经验影响下一次

记住：遇到平均值任务，检查分母是否包含样本数量；不能只修复当前这一行。

测试失败是评价，解释失败是反思，修改程序是修订，保留可复用规则则是记忆。只有它们形成闭环，系统才可能在后续任务中受益。

先记住一句话：Reflection 不是“再让模型想一遍”，而是让模型把已经发生的输出或行动，与某种反馈信号进行比较，并将比较结果转化为下一步的可执行变化。

02 · 反思的最小闭环：从轨迹到反馈，再回到行动

在 Agent 场景里，模型的对象不只是最终答案，而是一整条轨迹：看到了什么、采取了什么动作、工具返回了什么、任务是否完成。反思模块需要读取这条轨迹，并结合评价信号生成一条“下一次可以做什么不同”的经验。

把图中的组件拆开：

  1. Actor（行动者）：根据任务、当前状态和已有记忆生成答案或动作。它可以是单个 LLM，也可以是 ReAct 式工具 Agent。
  2. Trajectory（轨迹）：保留输入、思考摘要、工具调用、观察结果和终止状态。它回答“刚才究竟发生了什么”。
  3. Evaluator（评价器）：判断输出是否满足任务约束。它可以返回二元通过/失败、分数、错误栈或结构化反馈。
  4. Reflector（反思器）：将轨迹和评价转成具体、可操作、可验证的修正建议，而不是泛泛地说“再仔细一点”。
  5. Memory（记忆）：选择性保存经验，并在下一次相关任务中检索。并不是每次失败都值得永久记住。

如果没有评价器，模型很难知道自己是否真的改好了；如果没有反思器，失败信号可能只是一条“0 分”；如果没有记忆，系统可能每次都从相同的错误重新开始。

03 · 三条核心技术路线：内部反馈、外部验证与经验记忆

Reflection 不是一个单一算法。最有用的划分方式，是看反馈从哪里来、是否经过独立验证，以及经验会不会跨轮次保留。

路线 A：Self-Refine——同一个模型反复生成、评价、修订

Self-Refine 将一个模型拆成三个逻辑角色：Generator 先生成候选结果，Feedback 模块指出具体不足，Refiner 根据反馈修改候选结果。三种角色可以由同一个 LLM 承担，不需要额外训练或强化学习。

关键在于反馈必须可定位、可行动：不是“这段代码不够好”，而是“第 2 个分支没有处理空列表；请补充边界条件，并保留原有接口”。随后系统重新评价修订结果，直到达到停止条件。

路线 B：CRITIC——让外部工具提供模型自身无法可靠提供的证据

CRITIC 的核心想法是：模型可以调用搜索引擎、代码解释器或专门的检查工具，对初始答案的某些维度进行验证，再根据工具反馈修正。工具并不会自动替模型思考，但它可以提供与生成模型相对独立的证据。

路线 C：Reflexion——把失败经验写入情景记忆，改变下一次行动

Reflexion 将 Actor、Evaluator、Self-Reflection 和 Memory 组合起来。Actor 执行任务，Evaluator 给出结果，Self-Reflection 将轨迹中的错误压缩成自然语言经验，再存入 episodic memory。下一轮 Actor 在生成动作时可以读取这些经验。

三者的关系：Self-Refine 主要回答“当前答案怎样变好”；CRITIC 主要回答“怎样获得更可靠的反馈”；Reflexion 进一步回答“怎样让这次失败影响下一次任务”。它们是互补路线，不是必须互相替代的模型架构。

04 · 数学形式化：把自然语言反思写成一个可控状态更新

为便于分析，令第 t 轮交互轨迹为 τt。其中 o 表示观察，a 表示动作。轨迹记录的是“模型做了什么”，而不只是最终回答。

式 1 · 交互轨迹
τt=(o0,a0,o1,a1,…,oT)

T 是该轮轨迹的终止步数。具体 Agent 还可以记录工具参数、异常、时间戳和来源标识；这是教学抽象，不是 Reflexion 论文唯一的轨迹序列化格式。

评价器将轨迹映射为反馈信号 rt。它可以是标量，也可以是结构化错误。反思器再结合轨迹、评价和当前记忆，产生语言经验 φt。

式 2 · 评价与反思
rt=E(τt),φt=R(τt,rt,Mt)

反思的关键不是把失败分数重复写一遍，而是给出“错误位置、证据、可能原因、下一步修正”之间的联系。

将经验写入记忆时，系统需要控制容量。设 K 为允许保留的经验数量，⊕ 表示候选追加，Trunc 表示按策略裁剪、去重或筛选。

式 3 · 有预算约束的记忆更新
Mt+1=TruncK(Mt⊕φt)

这是解释记忆容量控制的抽象算子。实际系统可以使用最近优先、重要性评分、向量检索、时间衰减或人工审核；不能把简单截断当作最优记忆算法。

下一轮策略根据任务输入 x 和更新后的记忆做出动作。需要强调：典型测试时 Reflection / Reflexion 更新的是上下文与记忆，不是模型参数。

式 4 · 经验影响下一轮策略
at+1∼πθ(·|x,Mt+1)

θ 在这里保持固定。若系统把反思反馈整理成 SFT / DPO / RL 训练样本并更新权重，那已经进入更长期的训练时学习范畴。

05 · 论文证据：三种方法分别证明了什么？

5.1 Self-Refine：不训练模型，也能在测试时迭代修改输出

Madaan 等人的 Self-Refine 以同一个 LLM 兼任生成、反馈和修订角色。论文在 7 类任务上进行评估，覆盖对话响应、代码优化与可读性、数学推理、缩写生成、约束生成等七类任务。NeurIPS 2023 论文摘要报告：相较于同一生成模型的一次性生成，平均任务表现提升约 20 个百分点（absolute）。

这个结果支持“迭代反馈在若干任务上有用”，但不意味着任意任务只要多问模型几次就会提升。反馈质量、任务是否可分解、评价目标是否明确，都影响结果。

5.2 Reflexion：语言经验能够影响后续尝试

Reflexion 将稀疏的成功/失败信号转换成自然语言经验，并把经验放进情景记忆。在 ALFWorld 的 134 个环境任务中，论文报告 ReAct + Reflexion 在启发式自评价设置下完成了 130 个任务。

在 HumanEval Python 的 pass@1 表格中，论文报告 Reflexion 为 91.0，GPT-4 基线列为 80.1；但这不是“同一模型、同一提示、同一预算下只切换 Reflection”的纯净消融。阅读数字时必须同时看模型、生成策略、测试生成方式和评价协议。

同一论文也展示了反思并非处处提升：MBPP Python 上 Reflexion 为 77.1，而表中的 GPT-4 结果为 80.1。作者将部分问题归因于自动生成测试的误报与漏报——测试套件本身不可靠时，错误反馈会误导反思器。作者还在 HumanEval Rust 最难的 50 道题上做了消融：基础模型 pass@1 为 0.60；保留自我反思但去掉测试生成降至 0.52；保留测试而去掉自然语言自我反思为 0.60；完整 Reflexion 达到 0.68。这说明“盲目反思”可能比不反思更差，而测试信号与语言归因需要协同。注意这只是该论文的 GPT-4 / Rust 子集设置，不是普遍规律。

5.3 CRITIC：外部工具提供更独立的验证依据

CRITIC 将搜索、代码执行等工具接入自我批评流程。它强调，模型对自身输出的评价可能与原始生成共享盲点；外部工具能在特定任务上提供相对独立的反馈。ICLR 2024 版本覆盖开放式问答、数学程序合成与毒性降低任务。

5.4 反思的边界：不是所有自我纠错都有效

Huang 等人在 ICLR 2024 研究 intrinsic self-correction：模型仅依靠自身能力评价并修正初始答案，而不引入外部反馈。论文指出，在推理任务中，模型通常难以可靠地仅凭内部反馈纠错，有时反而会降低表现。

Kamoi 等人在 TACL 2024 的批判性综述进一步指出，研究需要区分“是否能修正初始错误”“能否修正已经最优的答案”“是否优于强基线”等不同问题。综述认为，通用任务中仅使用 prompted LLM 自身反馈的可靠证据不足；在能够提供可靠外部反馈的任务上，自我纠错更有效。

5.5 2026 的统一视角：Verbal Reinforcement Learning

2026 年的《The Rise of Verbal Reinforcement Learning》预印本提出更宽的视角：自然语言反馈可以在 Agent 生命周期的不同阶段发挥作用——问题定义时作为 Grounding Signal，推理时作为 Deliberative Feedback，训练时作为 Learning Signal。Self-Refine、CRITIC 和 Reflexion 主要落在推理时的 Deliberative Feedback；SFT、PPO、DPO 则属于训练时的 Learning Signal。

06 · Reflection 与 CoT、Self-Consistency、ReAct、RL 有什么区别？

这些概念经常被混在一起，因为它们都可能让模型产生更多 token 或更多轮调用。但它们改变的是不同对象。

可以把它们放进同一条系统链：CoT 负责生成候选推理，Self-Consistency 负责聚合候选，ReAct 负责与环境交互，Reflection 负责从已观察到的反馈中提炼修正，而训练方法则可能把积累的数据压缩成参数更新。

07 · 反馈质量决定上限：模型不能靠语言凭空制造真相

反思系统最容易被忽视的部分不是 Reflector，而是 Evaluator。一个系统可以非常擅长生成“听起来合理”的批评，却仍然不知道自己是否真正修正了错误。

建议把反馈写成结构化记录，而不是单句“你错了”。一个可执行的反馈至少应包含：

  • Observation： 实际发生了什么？保留原始工具输出或测试结果。
  • Expected： 目标、约束或正确行为是什么？
  • Delta： 观察结果与预期之间的差异在哪里？
  • Attribution： 最可能的错误来源是什么？证据支持到什么程度？
  • Action： 下一轮具体改哪个步骤、参数或假设？
  • Verification： 如何确认修正有效，且没有引入回归？
重要边界： 搜索结果、编译器输出、网页文本和工具日志都可能是错误或不可信数据。它们可以成为评价证据，但不能因此获得更高指令权限，也不能自动覆盖系统约束或用户目标。

08 · 经验如何进入记忆：不要把每一次失败都永久保存

Reflexion 论文区分了短期轨迹和长期反思经验：轨迹保留当前尝试的细节，反思文本则提炼可以指导后续尝试的经验。论文实践中限制保留经验的数量，以控制上下文长度；这也提醒我们，记忆容量本身就是系统设计变量。

现代 Agent 系统里，可以进一步区分三种表示：

Episodic · 情景记忆

某次任务发生了什么：输入、动作、观察、结果和时间戳。它保留可追溯的原始经历。

Semantic · 语义记忆

多次经历中提炼出的稳定事实、规则和约束，例如“该 API 的分页参数从 0 开始”。

Procedural · 程序性记忆

可复用的操作流程或技能，例如“先读取配置，再验证权限，最后执行写操作”。

Injected Context · 注入上下文

当前任务真正需要的少量记忆，而不是把整个历史库一次性塞进模型窗口。

建议采用“候选经验 → 证据核验 → 去重与归纳 → 设定有效范围 → 写入 → 按任务检索”的流程。对来源不明、无法复现、与任务无关或可能包含恶意指令的内容，应拒绝写入或保留为待验证状态。

09 · 交互实验：切换反馈来源，观察下一轮有什么不同

下面使用同一个平均值任务，切换三种反馈模式。所有数据都是教学用的固定示例，不会调用真实模型，也不代表论文 benchmark。

任务：计算数组 [1, 2, 3] 的平均值目标答案 = 2
Initialsum([1, 2, 3]) → 6
Test toolFAIL：expected 2, got 6
Feedback当前实现计算的是总和；平均值需要再除以元素个数。
当前步骤 1 / 3

外部测试提供了独立的数值差异；反思器负责把差异解释为可执行修改。

观察重点：三种模式都可能生成修订文本，但只有工具验证模式能明确引用测试结果；Reflexion 模式还会把“总和与平均值的区别”保留到下一次相关任务。记忆不等于自动正确，它仍然需要来源、有效范围和过期策略。

10 · 何时继续，何时停止：反思本身也有成本

每增加一轮反思，都要付出模型调用、工具执行、时延和上下文预算。更重要的是，修订可能破坏原本正确的答案。因此系统不应把“多反思几轮”当成默认目标。

我们可以定义一个用于工程决策的启发式净收益。它不是 Self-Refine 或 Reflexion 原论文中的目标函数，而是把正确率收益与系统成本放到同一张账上。

式 5 · 反思的边际净收益（教学推导）
ΔU=[P(S|F)−P(S)]V−CLLM−Ctool−Clatency−Cregression

F 表示新增反馈，S 表示任务成功，V 表示成功价值。若净收益不大于 0、独立验证已通过，或预算已经耗尽，就应停止或请求人工接管。

实际停止条件可以组合使用：

  • 外部验收通过，且没有未解决的硬约束。
  • 连续几轮没有新增证据，修改只是在措辞或实现细节上来回摆动。
  • 新增反思带来的成功概率提升不足以覆盖调用成本。
  • 评价器置信度不足，或出现互相矛盾的评价结果。
  • 达到最大轮数、最大 token、最大工具调用数或任务截止时间。

11 · 反思为什么会失败：六类典型风险

  1. 循环盲点：生成模型与反思模型共享相同知识缺口，批评只是在重复原先的错误假设。
  2. 错误评价器：测试套件覆盖不足、隐藏条件缺失，或模型评审标准与真实任务目标不一致。
  3. 过度修订：原始答案本来正确，模型为了响应“请改进”的提示反而引入新错误。
  4. 记忆污染：一次偶然失败被概括成通用规则，后续任务持续受到错误经验影响。
  5. 成本失控：没有停止条件，Agent 在相似候选间反复评价，产生大量 token、工具调用和时延。
  6. 反馈注入：工具输出或检索文档包含恶意指令，若未经隔离就写入记忆，可能造成跨任务污染。

Reflexion 论文对代码生成也明确讨论了测试生成的 false positive / false negative 风险：错误测试可能让不正确实现通过，或让正确实现失败。由此可见，Reflection 的性能上限常常取决于验证器，而不只是 LLM 的表达能力。

12 · 如何评测 Reflection：不要只看最终答案分数

一个可信的评测应回答：反思到底修正了什么？需要多少额外成本？它是否让正确答案退化？写入记忆的经验在后续任务中是否真的有用？

指标定义它回答什么问题
Initial Success未反思时的成功率强基线本身有多好？
Post-Reflection Success固定反思预算后的成功率反思之后到底成功了多少？
Reflection Gain后测成功率 − 初始成功率反思带来多少净提升？
Regression Rate原本正确、修订后变错的比例模型是否会破坏正确答案？
Verifier Error评价器误报 / 漏报率反馈信号是否值得信任？
Cost per Success总调用成本 ÷ 成功任务数收益是否值得额外计算？
Memory Utility加入记忆后相对无记忆条件的变化跨轮次经验是否真的可迁移？

实验设计至少应控制基础模型版本、初始提示、温度与采样预算、工具接口、最大尝试次数、评价协议和任务拆分。建议做逐项消融：移除 Reflector、移除外部 Evaluator、移除 Memory、限制反馈长度、改变最大尝试次数，并报告均值、方差与失败案例。

13 · 工程设计清单：把反思从 Prompt 技巧变成系统能力

  1. 明确反馈契约：要求评价器返回观察、预期、差异、证据来源和置信度。
  2. 优先使用可验证信号：能运行单元测试就不要只问模型“你觉得对吗”；无法自动验证时，明确保留不确定性。
  3. 把修订做成差异：记录修改了哪一段、为什么修改、由哪条证据触发。
  4. 保留最佳候选：只有在新的验证指标改善且没有触犯硬约束时才替换当前最佳版本。
  5. 限制预算：设置最大轮数、工具调用数、token 和时间预算；失败时能够安全停止。
  6. 记忆写入设门槛：要求来源、时间、适用范围、验证状态和失效条件；不把一次模型猜测写成永久事实。
  7. 安全隔离：将外部工具输出视为不可信数据；记忆检索不能改变工具权限或覆盖高优先级约束。
  8. 保留审计轨迹：记录初始候选、反馈、修订、验证结果、成本和最终停止原因。

最小可运行示例用确定性程序说明控制流，而不是假装复现论文中的 LLM。下面的教学实现固定模拟一个“求平均值”任务：第一轮错误地求和，收到明确反馈后改为求平均，再用相同测试确认结果。

from reflection_demo import run_mean_reflection

result = run_mean_reflection([1, 2, 3], max_rounds=3)

assert result["success"] is True
assert [x["candidate"] for x in result["attempts"]] == ["sum", "mean"]
assert result["attempts"][-1]["output"] == 2.0
assert len(result["memory"]) == 1

该示例是固定策略的可测试教学模拟，不调用 LLM、不执行任意生成代码，也不是 Reflexion 论文的模型复现。它只验证“反馈 → 经验 → 下一轮修订 → 再验证”的控制流不变量。

14 · 核心结论：反思的价值在于反馈闭环，而不是反思文本的长度

第一：没有反馈，就很难知道自己错在哪里；没有可操作的反思，评价信号也很难变成修正。

第二：内部自我批评成本低，但容易共享盲点；独立工具和环境反馈更可验证，但有覆盖、时延和误报边界。

第三：Reflexion 的关键增量是把失败经验写入情景记忆，让后续行动能够利用过去的教训。

第四：Reflection 不等于模型参数学习。测试时反思通常改变输出、上下文和记忆；训练时反馈才可能改变权重。

第五：优秀的反思系统必须知道什么时候停止、什么时候保留原答案，以及什么时候承认评价器并不可靠。
