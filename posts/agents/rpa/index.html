Understanding Robotic Process Automation (RPA)

从 UI 模拟到流程编排：软件机器人如何可靠地执行重复业务任务？以及它为什么不会被 LLM Agent 简单取代？

核心对象：业务流程与软件机器人·研究范围：2018–2026·约 35 分钟

01 · 为什么企业还需要“机器人”来点按钮？

想象一个普通财务流程：员工收到供应商发票，在文件系统中读取单据，打开采购系统查找订单，再登录 ERP 创建应付记录，最后把处理结果写回表格并通知同事。每一步都不难，但它横跨多个系统，重复发生，而且必须遵循相同的业务规则。

理想情况下，这些系统应该通过统一 API 或业务集成层交换数据。但现实企业往往同时运行新旧系统、外包平台、桌面客户端和历史遗留应用。系统之间没有统一接口，重构成本又很高，于是人就成了系统之间的“胶水”：复制、粘贴、切换窗口、核对字段、重复提交。

RPA 的切入点正是这个缝隙：不先重写这些系统，而是让软件机器人像使用者一样操作现有界面，把可重复的数字劳动变成可编排的程序。

核心问题不是“能不能自动点击”，而是： 哪些重复工作可以被准确描述成规则？机器人如何知道自己处于哪个业务状态？如果界面变化、网络超时或写入失败，怎样避免错误继续扩散？

van der Aalst、Bichler 与 Heinzl 在 2018 年提出的基本观察是：RPA 是一种 outside-in 自动化方式，机器人通过其他系统的用户界面执行操作，而传统信息系统改造更接近 inside-out，即从系统内部重构流程或接口。[1]

02 · RPA 究竟是什么？先把边界讲清楚

Robotic Process Automation（RPA）：使用预配置的软件机器人，按照业务规则和预定义活动顺序，自动执行原本由人完成的数字化任务。传统 RPA 的核心特征是通过用户界面模拟人的操作；现代 RPA 平台也可能把 API、文件和脚本作为同一工作流中的动作，但 API-only 集成本身应与 UI 型 RPA 区分。[1][5]

这里的“Robot”不是实体机械臂，而是运行在计算机上的软件实例；“Process”也不意味着机器人天然理解整个企业流程。传统 RPA 的执行逻辑通常由人先设计：触发条件、变量、判断分支、应用操作、异常路径和结束条件都被编码成工作流。

2.1 Outside-in 与 Inside-out

  • Outside-in（RPA）：从应用外部模拟用户，点击控件、输入字段、读取页面反馈。优点是对遗留系统侵入性较低；代价是容易受界面布局、控件标识和登录状态变化影响。
  • Inside-out（系统集成）：从应用内部 API、消息总线、数据库或服务接口进行集成。接口稳定且可用时，通常比屏幕坐标点击更可靠，也更容易进行结构化验证。

成熟的自动化方案不应把“RPA”理解成“所有动作都必须模拟鼠标”。应优先使用有契约、可授权、可观测的稳定接口；当接口不可用或改造代价不合理时，再用 UI 自动化作为兼容层。

2.2 RPA、BPM、API Automation 与 Agent 的区别

范式主要对象决策方式适合解决的问题
BPM / Workflow端到端业务流程流程模型、事件、规则与人工任务跨部门编排、流程治理、SLA 与审计
API Automation服务接口与数据契约结构化请求与响应稳定系统集成、事务与批量数据处理
Traditional RPA重复的 UI 任务预定义规则与状态转换跨旧系统的高频、低歧义操作
IPA结构化与非结构化业务输入RPA 加 OCR、ML、NLP 等模型文档理解、分类、抽取与规则执行
LLM GUI Agent动态环境中的开放任务观察、推理、规划、行动、再观察流程不固定、界面变化或需要语义判断的任务

BPM 与 RPA 是互补关系：BPM 从更高层设计、执行、监控和改进业务流程；RPA 往往从较低层把其中一段稳定的重复任务自动化。RPA 不会自动修复一个糟糕的业务流程，也不等于完整的 BPM 平台。[5]

03 · 不是所有工作都值得自动化：先选对流程

RPA 项目最昂贵的错误之一，是把一个本身不稳定、规则不清晰、例外频繁的流程直接写成机器人。机器人会忠实地重复流程缺陷，而且可能比人工更快地放大错误。

2018 年的 RPA 论文用“工作长尾”解释自动化的经济边界：少数高频案例往往高度相似，值得优先标准化；大量低频、复杂和非标准案例则可能仍需人类处理。[1] 这不是固定的 80/20 业务定律，而是提醒我们：案例频率与案例多样性必须同时考虑。

3.1 一个候选流程的六个问题

  1. 规则是否明确？ 同样的输入是否总能按相同规则得到相同动作？规则是否有可追溯的业务负责人？
  2. 频率是否足够高？ 每天、每周或每月重复多少次？是否有稳定的峰值和季节性？
  3. 输入输出是否结构化？ 字段是否能被稳定读取、校验和映射？文档是否需要复杂语义理解？
  4. 应用是否稳定？ UI、权限、登录、数据格式和流程步骤是否频繁变化？
  5. 例外率和认知负担如何？ 需要多少上下文判断、跨来源核实和人工协商？
  6. 失败代价有多大？ 错误写入是否会影响付款、税务、客户权益或合规记录？是否有补偿和回滚方案？

Farinha 等人在 2024 年通过系统综述与 Delphi 专家研究提出了 32 项 RPA 流程筛选标准，并在 6 个组织的 18 个流程上进行评估；其中流程可行性、流程描述质量、输入与输出数据特征是获得较高重视的维度。[3]

2026 年的 RPA–BPM 系统综述进一步归纳：高频、规则驱动、数字化输入稳定、结构化数据、低认知判断的流程通常更适合传统 RPA；流程选择不当是整个生命周期的前置质量问题。[5]

3.2 把“适合自动化”拆成可审查的假设

优先候选高频、重复、输入结构化、规则稳定、界面相对稳定，并且异常能明确升级。
谨慎候选输入半结构化、例外需要语义理解、跨系统状态难以确认，或操作影响资金与权益。
先重设计流程本身存在重复审批、字段冲突、无效等待或职责不清，自动化会放大现有浪费。
不宜直接自动化低频、强歧义、需要价值判断或无法安全验证最终业务状态的任务。

04 · Process Mining：先观察真实流程，再决定自动化什么

传统流程设计常依赖访谈和流程图，但员工实际执行的路径可能与制度文档不同：有人绕过某一步，有人重复录入，有人遇到系统错误后用 Excel 补救。只看“理想流程”容易选错自动化对象。

4.1 Event Log 与 Task Trace

  • Event Log（事件日志）：来自业务系统的案例 ID、活动名称、时间戳、资源等字段，描述业务对象经历了哪些活动。
  • Task Trace（任务轨迹）：来自桌面或应用交互的点击、输入、窗口切换、复制粘贴等记录，更接近员工在界面层面的具体动作。

Process Mining 从事件日志中发现流程模型、比较不同流程变体，并进行一致性检查；Task Mining 更关注用户交互序列，能帮助定位跨应用的重复动作，但也带来更高的员工隐私与监控治理要求。

El-Gharib 与 Amyot 在 2023 年对 RPA 与 Process Mining 的结合进行了系统综述：他们从 605 个候选记录中筛选出 32 篇研究，发现研究主要聚焦 UI 交互日志的采集、预处理和流程发现；数据清洗、日志质量与生命周期其他环节仍存在明显研究缺口。[2]

4.2 三个关键分析任务

  1. Process Discovery： 从事件日志中重建实际活动路径，识别主路径、变体、循环和等待。
  2. Conformance Checking： 将真实执行轨迹与规范模型比较，定位偏离、漏步骤和额外步骤。
  3. Performance Analysis： 分析活动耗时、队列等待、返工率和瓶颈，判断自动化是否真的改善端到端流程。
重要边界： Process Mining 能告诉我们流程如何发生、偏差在哪里；它不能自动证明一个流程在法律、风险和业务价值上适合自动化。候选决策仍然需要业务规则、成本和责任审查。

05 · RPA 运行时架构：Bot 不是一段宏脚本

单个桌面宏可能只有“打开页面、点击按钮、输入字段”。企业级 RPA 则需要把机器人放进一个受控运行时：谁能启动任务、谁提供凭据、多个机器人如何竞争队列、失败如何重试、结果如何审计、业务异常交给谁。

5.1 控制平面（Control Plane）

  • Orchestrator： 发布机器人版本、启动作业、分配 Worker、管理并发和运行状态。
  • Queue / Scheduler： 维护待处理案例、优先级、超时、重试次数和资源分配。
  • Policy Gate： 在执行前检查操作者、机器人身份、业务对象和动作风险。
  • Credential Vault： 以最小权限提供短期凭据；不把密码硬编码在流程文件中。
  • Audit / Metrics： 记录输入摘要、动作、状态转换、错误、人工审批和最终结果。

5.2 执行平面（Execution Plane）

Bot Worker 运行一个具体流程实例。它通过 Adapter Layer 与应用交互：能用稳定 API 时优先 API；需要操作遗留界面时使用 DOM、Accessibility Tree 或可靠的 UI Automation Selector；只有在必要时才退回坐标点击或 OCR。

每个适配器都应该有明确的输入输出契约。例如，read_invoice_total() 不应该只返回一个字符串，还应该说明币种、精度、来源字段和读取失败时的行为。post_invoice() 则应返回可用于后置核验的业务标识，而不是仅仅告诉机器人“按钮已被点击”。

5.3 持久化任务状态

不要只把进度存在当前浏览器页面或内存变量里。进程崩溃、机器重启或人工接管后，系统仍然要知道案例 ID、当前阶段、已完成动作、幂等键、重试次数、审批状态和证据引用。持久状态使机器人可以恢复，而不是从头重复所有动作。

06 · 生命周期：从候选发现到持续改进

RPA 不是录制一次点击就结束。一个可运营的生命周期至少包含：发现候选、评估适配性、标准化流程、开发与测试、部署编排、监控与持续改进。上线后的异常和业务变化必须回到流程分析与规则修订，而不是无限叠加补丁。

2026 年的 RPA–BPM 系统综述将研究主题归纳为流程识别、实施生命周期、效益、挑战、技术整合和治理六个维度，并提出战略对齐、运营执行、持续改进三个支柱。[5]

阶段必须产出的工件质量门槛
发现与评估流程描述、频率、变体、风险、ROI 假设业务负责人确认候选和责任边界
标准化规则版本、字段字典、异常分类、人工路径规则无歧义，异常有明确归属

07 · 把机器人理解成状态机，而不是“自动点击器”

一个可靠的机器人应该围绕业务状态运行。以发票入账为例：任务接收后先验证字段，再匹配采购订单，确认审批，再提交入账，最后读取真实记录进行核验。每次转换都要定义前置条件和后置条件。

7.1 为什么长流程会放大微小失败？

如果一个流程包含 n 个步骤，每一步成功概率为 pᵢ，并暂时假设各步骤失败相互独立，那么整条流程一次执行成功的概率是：

Pworkflow=∏i=1npi

若 12 个步骤的成功率都为 99%，整条流程一次成功的概率约为 88.6%。这是独立同分布假设下的教学算例，不是任何 RPA 产品的实测指标。它说明：单步看起来“几乎不会失败”，不代表多步骤流程就足够可靠。

7.2 重试必须区分瞬时故障与业务状态不确定

假设每次尝试遇到独立瞬时故障的概率为 q，最多执行 r 次重试（总尝试次数为 r + 1），在每次尝试都没有副作用且失败相互独立的理想模型中，最终成功概率为：

P(success)=1−qr+1

但 UI 自动化中常见的是“请求已经提交，响应却丢失”。此时超时并不意味着业务动作失败。如果机器人再次点击“提交”，可能产生重复订单、重复付款或重复客户记录。

工程原则： 只有确认操作是幂等的，或已经通过业务键查询确认上次没有提交，才允许自动重试。对于不确定的写入结果，先对账、再决定重试或人工升级。

7.3 状态转换的最小契约

每一步至少记录：状态、前置条件、动作、后置条件、幂等键、超时策略、审计证据。如果后置条件无法验证，就不能把动作标记为成功。

09 · 从 RPA 到 IPA，再到 Agentic Process Automation

传统 RPA 擅长稳定、可重复的确定性动作，但当输入变成扫描件、自由文本、动态表单或多来源信息时，纯规则流程会遇到边界。Intelligent Process Automation（IPA）在确定性执行器前增加 OCR、文档理解、分类、机器学习或 NLP，让系统能够处理半结构化输入。

9.1 能力应该分层，而不是全部交给一个大模型

  • 感知层： OCR、版面分析、文档分类和字段抽取，将图片或文档转换为带置信度的结构化候选。
  • 语义层： LLM 对非结构化描述进行归类、补全上下文、解释异常或提出候选计划。
  • 策略层： 业务规则、权限、风险阈值和人工审批决定哪些动作可以执行。
  • 执行层： API、RPA Bot 或 Workflow Engine 执行已授权的具体动作。
  • 验证层： 读取真实业务状态，核对关键字段和副作用，再决定是否完成。

这不是“让 LLM 接管所有按钮”。更可靠的设计是把语义不确定性限制在输入理解、异常解释和计划提议环节；高频、稳定、可验证的动作仍由确定性执行器完成。

9.2 什么时候用 API，什么时候用 RPA，什么时候用 Agent？

任务特征优先方案原因
有稳定 API、字段和事务语义清楚API / Workflow更容易保证契约、可观测性和后置校验
没有可用 API，但 UI 稳定且规则固定Traditional RPA用较低侵入方式连接遗留系统
文档半结构化，需要抽取与分类IPA + 人工抽检把模型置信度和业务规则结合起来

动作高影响且不可逆人类审批 + 受控执行器不能只依赖模型自我判断或 UI 成功提示

10 · AutoRPA：把 Agent 的一次性探索变成可复用技能

AutoRPA 是 2026 年 ICML 论文提出的一个直接连接 RPA 与 LLM Agent 的方向。[6] 论文指出：ReAct 风格 Agent 可以通过多轮观察与推理处理动态 GUI 任务，但每次重复任务都重新调用模型进行规划，会带来额外 Token 消耗与运行开销；传统 RPA 执行高效，却需要人手工编写和维护流程。

10.1 Translator–Builder 两阶段

  1. Translator： 从 Agent 交互轨迹中提取可复用步骤，把硬编码的 ReAct 动作转化为更可参数化的过程描述。
  2. Builder： 通过检索增强生成，综合多条相似轨迹，合成稳健的 RPA 函数，而不是简单复制一条成功轨迹。
  3. Verification： 在目标 GUI 环境中运行生成函数，检查实际结果和预期后置条件。
  4. Hybrid Repair： 当确定性函数无法处理变化时，使用 ReAct 式 Agent 辅助定位和修复，再重新验证。

论文在多个 GUI 环境的实验中报告，生成的 RPA 函数在相似任务上可减少 82%–96% 的 Token 使用量。[6] 这是论文报告的 Token 消耗指标，不等同于成功率、端到端延迟或企业生产 ROI；也不意味着一次生成的函数可以无条件迁移到任意应用和版本。

可以把它理解为“技能编译”： Agent 在不确定环境里探索并形成轨迹；系统把经过验证的重复部分固化为可复用函数；只有遇到新变化时，才重新调用更灵活的推理能力。

10.2 这与 ReAct、Function Calling、Harness 的关系

  • ReAct 解释 Agent 如何在 Thought、Action、Observation 之间循环。
  • Function Calling 解释模型如何通过结构化 Schema 调用外部工具。
  • Harness Engineering 解释工具权限、运行时、状态、观测、验证和失败恢复如何组织起来。
  • RPA 则提供一种确定性、可重复的动作执行方式；AutoRPA 探索如何把 Agent 轨迹转化为这种执行方式。

11 · 企业自动化最难的部分：安全、审计与治理

RPA 机器人通常以某个用户或服务身份访问业务系统。它可能读取个人信息、修改客户记录、生成付款指令或更新监管数据。因此，机器人执行能力越强，权限、审计和状态验证就越不能被当成附属功能。

11.1 六条工程护栏

  1. Least Privilege： 每个 Bot 使用独立身份，只能访问完成当前任务所需的系统和数据。
  2. Secret Management： 凭据放在受控 Vault 中，禁止写入脚本、截图、日志和普通配置文件。
  3. Human Approval： 付款、删除、权限修改、外部发送等高影响动作应有明确审批门槛。
  4. Idempotency： 为业务操作设计稳定的业务键，重试前先检查状态，避免重复写入。
  5. Read-after-write Verification： 不以按钮点击、Toast 提示或页面跳转作为最终成功证据；读取持久化记录并核验关键字段。
  6. Auditability： 记录谁触发、哪个版本执行、访问了什么对象、发生了哪些状态转换、由谁审批、最终结果是什么。

11.2 “界面保存成功”不等于“业务记录正确”

2026 年的 ERPBench 研究专门针对企业软件中的持久化状态设计评测：它把截图驱动的 Agent 操作与真实数据库中的 Ground Truth 对照。论文预印本报告，在部分运行中，Agent 能够把表单保存下来，但保存的关键业务字段仍然错误；有的系统保存成功率最高可达 85%，而正确字段值的比例却低至 3%。[9]

这个结果提醒我们：操作层面的成功、界面层面的反馈和业务层面的正确是三个不同的判断。企业自动化必须把最终状态核验纳入任务完成条件。

11.3 典型失败模式与对应防护

失败模式为什么发生防护方式
Selector 漂移控件 ID、DOM 或布局变化优先语义定位；版本化测试；失败时停止而非猜坐标
固定等待失效网络和渲染耗时不稳定等待可观测条件、超时和取消机制
重复副作用提交成功但响应丢失，重试再次写入业务幂等键、状态查询、去重和对账
上下文缺失跨页面或跨案例状态被混用显式任务 ID、状态存储和数据隔离
权限过大机器人沿用员工全量权限独立服务身份、最小权限、审批与凭据轮换
规则漂移业务制度和表单字段变化规则版本化、变更审批、回归测试和监控
错误被静默接受只检查页面提示，不检查业务记录读回持久化状态，验证金额、对象 ID 和业务约束

2018 年的奠基性讨论就已经提醒：模仿人的软件机器人可能在上下文变化时做出错误决定，而且错误可能长时间不被发现；模拟人的身份还会引入安全与伦理风险。[1] 这些问题不会因为今天的模型更强就自动消失。

12 · ROI 与评测：不要只统计“节省了多少人时”

自动化的商业价值取决于处理频率、人工单位成本、运行成本、开发投入、维护负担和失败代价。一个最简单的教学成本模型是：

Nbreak-even=Cbuild+HCmaintcmanual−crun

其中，Cbuild 是一次性开发与部署成本，H 是评估周期，Cmaint 是单位时间维护成本，cmanual 是每个案例的人工成本，crun 是每个案例的机器人运行成本。只有当人工单位成本高于自动化单位成本时，这个简单模型才存在正的盈亏平衡点。

这个公式没有包含风险、延迟、错误补偿、许可、基础设施、组织变更和资本成本，不能直接当作企业财务模型；它只是提醒：自动化频率不够高，或维护成本过高时，机器人可能永远无法收回开发投入。

12.1 建议分层观察 KPI

  • 运营： 端到端周期时间、吞吐量、队列等待、首次成功率、重试率、人工接管率。
  • 质量： 字段准确率、业务规则违例、重复写入、错误关闭率、读回核验通过率。
  • 经济： 每案例总成本、开发周期、维护工时、许可与基础设施成本、返工成本。
  • 治理： 审计完整率、权限违规、凭据暴露、人工审批覆盖率、规则变更后的回归通过率。

如果一个机器人把点击速度提升了，却让业务异常率、人工返工或风险敞口上升，那么它并没有真正改善业务流程。

13 · 最小可运行示例：带幂等保护的发票机器人

下面的代码是一个纯 Python 教学模拟器，不会连接真实 ERP、浏览器或财务系统。它刻意把业务状态机与系统适配器分开：业务规则负责判断是否可以入账，Adapter 模拟一个可能在提交后丢失确认响应的系统。

机器人使用发票 ID 作为业务幂等键。即使第一次写入已经成功，但响应超时，第二次调用也会返回同一条记录，而不是创建第二条入账记录。

from dataclasses import dataclass, field
from enum import Enum

class State(str, Enum):
    RECEIVED = "RECEIVED"
    VALIDATED = "VALIDATED"
    MATCHED = "MATCHED"
    APPROVED = "APPROVED"
    WRITE_UNCERTAIN = "WRITE_UNCERTAIN"
    POSTED = "POSTED"
    VERIFIED = "VERIFIED"
    DONE = "DONE"
    HUMAN_REVIEW = "HUMAN_REVIEW"

class TransientUIError(Exception):
    pass

@dataclass(frozen=True)
class Invoice:
    invoice_id: str
    amount_cents: int
    po_amount_cents: int
    approved: bool = True

class FakeERP:
    def __init__(self, timeout_after_commit_once=False):
        self.records = {}
        self.post_count = 0
        self.timeout_after_commit_once = timeout_after_commit_once

    def post_invoice(self, invoice_id, amount_cents):
        if invoice_id in self.records:
            return self.records[invoice_id]
        self.records[invoice_id] = amount_cents
        self.post_count += 1
        if self.timeout_after_commit_once:
            self.timeout_after_commit_once = False
            raise TransientUIError("commit succeeded; acknowledgement lost")
        return amount_cents

    def read_invoice(self, invoice_id):
        return self.records.get(invoice_id)

@dataclass
class RunResult:
    state: State
    events: list = field(default_factory=list)

def run_invoice(invoice, erp, max_retries=1):
    events = []
    def emit(state, detail):
        events.append({"state": state.value, "detail": detail})
    def review(detail):
        emit(State.HUMAN_REVIEW, detail)
        return RunResult(State.HUMAN_REVIEW, events)

    emit(State.RECEIVED, "case accepted")
    if invoice.amount_cents <= 0:
        return review("amount must be positive")
    emit(State.VALIDATED, "required fields are valid")
    if invoice.amount_cents != invoice.po_amount_cents:
        return review("purchase order mismatch")
    emit(State.MATCHED, "invoice matches purchase order")
    if not invoice.approved:
        return review("approval is missing")
    emit(State.APPROVED, "business approval is present")
    for attempt in range(max_retries + 1):
        try:
            erp.post_invoice(invoice.invoice_id, invoice.amount_cents)
            break
        except TransientUIError:
            emit(State.WRITE_UNCERTAIN, "reconcile before retry")
            if attempt == max_retries:
                return review("retry budget exhausted")
    stored = erp.read_invoice(invoice.invoice_id)
    if stored != invoice.amount_cents:
        return review("read-after-write verification failed")
    emit(State.POSTED, "record exists")
    emit(State.VERIFIED, "persisted amount matches")
    emit(State.DONE, "postconditions satisfied")
    return RunResult(State.DONE, events)

13.1 测试应该证明什么？

  • 金额与采购订单不一致时，状态进入 HUMAN_REVIEW，并且没有写入记录。
  • 审批缺失时，机器人不会绕过审批继续提交。
  • 提交后确认响应超时，使用同一业务键恢复，最终只产生一条记录。
  • 最终状态必须通过读取持久化记录核验，而不是只根据按钮返回值决定。
生产系统还需要更多东西： 持久化任务状态、分布式锁、凭据保险库、真实 UI/API Adapter、事务边界、补偿动作、结构化审计、速率限制、人工审批和安全测试。这个小程序只演示状态机与幂等重试的核心思想。

14 · 2025–2026 研究前沿：自动化正在从“录制流程”走向“可验证的技能”

14.1 RPA 候选识别正在变得更数据驱动

Wewerka 与 Reichert 的系统映射研究识别并分析了 63 篇 RPA 相关出版物，提出用于比较既有与未来 RPA 研究的分类框架。[4] 2026 年 11 月发表的研究 Automatic Candidates Identification for RPA Based on Textual Process Descriptions 探索从自然语言流程描述中自动识别可自动化任务：研究扩展到 183 份流程描述和 2,262 个标注活动；在跨数据集测试中，合成文本训练后迁移到人类编写描述，Macro-F1 从 0.935 降至 0.648，自动化类别 F1 从 0.948 降至 0.434。[7] 这说明文本分类可以辅助早期候选发现，但合成数据和真实组织文档之间存在明显分布差异。

14.2 LLM 可以生成流程模型，但复杂度仍然是难点

2026 年的 BPMNGen 研究探索从自然语言描述生成 BPMN 2.0 模型，并分别评估语义质量与模型可理解性。结果显示，LLM 对简单和中等复杂度流程已有较好表现，但更复杂的流程仍然困难；作者也指出评估场景相对简单、参与者群体为非专家。[8]

流程模型的“语法正确”不等于“语义正确”，更不等于“可以安全执行”。生成的 BPMN 仍需专家审查、约束检查和执行前验证。

14.3 GUI Agent 的基准成绩不能直接代表企业可靠性

OSWorld 在 2024 年引入 369 个跨真实桌面和 Web 应用的任务，论文报告当时最佳 Agent 的任务成功率为 12.24%，而人类为 72.36%。[10] 这不是对 RPA 的直接评测，也不是当前模型水平的排行榜。Stanford AI Index 2026 汇总的更新结果显示 Claude Opus 4.5 在 OSWorld 上达到 66.3%；不同模型版本、任务配置和评测设置不可直接视为一条严格可比的时间序列。[12]

2026 年 Findings of ACL 的 WindowsWorld 包含 181 个任务、17 个桌面应用，其中 78% 本质上涉及多个应用；领先 GUI Agent 在多应用任务上的成功率仍低于 21%。[11] ERPBench 则进一步要求检查企业数据库中的真实状态，而不是只观察屏幕上的动作反馈。[9]

14.4 目前最值得关注的研究方向

  • Process-aware Agent： Agent 不只操作界面，还需要理解案例状态、业务约束和流程模型。
  • Skill Distillation： 把反复出现且已验证的 Agent 轨迹编译成稳定、可复用的确定性函数。
  • State-grounded Evaluation： 以真实业务状态、数据库记录和后置条件评估任务成功。
  • Risk-aware Orchestration： 根据动作影响、可逆性和置信度选择自动执行、人工审批或拒绝。
  • Process Mining + LLM： 把事件日志、流程模型、文本描述和执行反馈结合起来，持续发现与改进自动化机会。

15 · 最后，把 RPA 记成五个判断

1. RPA 是软件机器人它通过 UI 执行预定义的数字化任务，不是实体机器人。
2. 先选流程，再写 Bot频率、规则稳定性、输入质量、异常率和失败代价决定自动化是否值得。
3. 运行时必须有状态队列、状态机、幂等键、重试、后置核验和审计是企业级自动化的基础。
4. Agent 不等于 RPAAgent 处理不确定性，RPA 执行稳定步骤；两者可以协作，而不是简单替代。
5. 成功必须由业务状态证明按钮点击、Toast 提示和页面跳转都不是最终业务正确性的证据。

RPA 的长期价值并不在于让软件机器人模仿人类的每一次点击，而在于把重复的数字工作变成可解释、可验证、可治理的执行能力。未来的 Agentic Process Automation 也不应放弃这些工程纪律：模型可以负责理解和规划，但真正改变企业记录的动作仍必须受到权限、状态、验证与责任机制的约束。
