Understanding
State Machines

状态机：从有限自动机、Mealy / Moore 与 Statecharts，到 Agent Runtime 的可靠状态控制。

核心对象：State · Event · Transition理论 × 工程 × 可验证实现约 32 分钟

01 · 为什么一个 status 字段还不够？

一个任务对象只有 status = "running"，并不意味着系统真的有一套可靠的状态模型。

假设一个 Agent 正在执行工具调用：它可能先校验参数，再等待人工审批，然后执行工具，最后成功、失败、超时或取消。如果代码只是在不同函数里随意写入字符串，系统就可能出现“已取消的任务又被重试”“未审批的高风险操作进入执行”“成功任务被重复提交”等非法行为。

状态机解决的不是“如何给对象加一个状态字段”，而是把系统允许发生的行为写成显式规则：当前处于什么状态、发生了什么事件、哪些条件必须成立、执行什么动作、转移到哪里。

没有显式转移模型

多个模块各自修改状态字符串；合法路径分散在 if/else、异常处理和定时任务中。局部看似合理，组合后却可能出现非法跳转。

有显式转移模型

状态与事件组成可审查的转移表；非法事件可以拒绝，守卫可以被测试，完整路径可以被模拟或模型检查。

核心直觉：状态描述系统“现在处于什么行为阶段”；事件描述“什么事情发生了”；转移规则描述“在什么条件下，系统允许如何变化”。

02 · 把状态机写成数学对象

先从最小的确定性状态转移系统开始。令 S 为状态集合，E 为事件集合，s₀ 为初始状态。一个部分定义的转移函数可以写成：

δ:S×E⇀S,st+1=δ(st,et)

这里的 ⇀ 表示函数可以是部分定义的：某个状态下某个事件可能没有合法转移。工程实现通常应把这种情况明确表示为拒绝、忽略或错误，而不是偷偷落入默认分支。

有限自动机的五元组

在形式语言理论中，确定性有限自动机（DFA）还要显式定义输入字母表和接受状态：

A=(Q,Σ,δ,q0,F)
  • Q：有限状态集合。
  • Σ：输入符号表。
  • δ：转移函数，DFA 中每个状态和输入符号恰好对应一个下一状态。
  • q₀：初始状态。
  • F：接受状态集合；输入串结束时落入 F，才接受该字符串。

这一定义与 Sipser《Introduction to the Theory of Computation》第一章的有限自动机定义一致。教材原文 PDF ↗。Rabin 与 Scott 1959 年的论文系统研究了有限自动机及其判定问题：Finite Automata and Their Decision Problems ↗。

例如输入串 10110 中有三个 1，因此路径最终落在 O，字符串被拒绝。DFA 的关键不是图形长什么样，而是对每一个状态和输入符号，转移结果都唯一。

03 · 状态机的几个重要家族

DFA 与 NFA：转移结果是否唯一？

DFA 对每个状态与输入符号给出唯一的下一状态。非确定性有限自动机（NFA）允许一个输入对应零个、一个或多个候选下一状态；接受语义是“至少存在一条路径到达接受状态”。在表达能力上，DFA 与 NFA 识别相同的正则语言；子集构造可以把 NFA 转换成 DFA，但最坏情况下状态数量可能显著增加。

维度DFANFA
转移状态 × 符号 → 单一状态状态 × 符号 → 状态集合（可含 ε 转移）
接受唯一运行路径最终进入接受态存在一条运行路径最终进入接受态
适用直觉执行路径明确、实现直接描述模式更紧凑，便于表达“多种可能”

Mealy 与 Moore：输出由什么决定？

在顺序电路和输出自动机中，状态机不仅改变状态，还产生输出。Mealy 机的输出函数依赖当前状态与输入；Moore 机的输出函数只依赖当前状态。Mealy 的输出常标在转移边上，Moore 的输出常标在状态节点里。

λMealy:S×E→O,λMoore:S→O

Mealy 的 1955 年论文讨论顺序电路的形式化综合方法；Moore 的 1956 年论文从有限自动机的外部实验角度研究状态可辨识性。Mealy (1955) ↗、Moore (1956) ↗。

04 · 从一条边拆开：事件、守卫与动作

真实软件中的状态机通常不只是“看到事件就跳转”。一个可审查的转移规则可以拆成：

Event · 事件

外部输入或内部信号，例如 submit、approve、timeout、tool_result。

Guard · 守卫

决定转移是否允许的布尔条件，例如权限通过、预算充足、重试次数未超限。

Action · 动作

转移前后执行的操作，例如写日志、发送请求、提交事务或安排计时器。

扩展有限状态机（EFSM）把数据变量纳入状态描述。可以把一条转移理解为：

(s,e,x)→g / a(s′,x′)

其中 x 是数据上下文，g 是守卫，a 是动作。如果 x 的取值域是无界整数、任意字符串或任意对象，那么整个系统不再是“有限个完整状态”的简单 FSM。工程上仍常称 EFSM，但不能把有限状态自动机的所有理论性质不加区分地套上去。

动作的边界：守卫应尽量是纯判断；动作可能产生副作用。不要在判断“是否允许转移”的同时偷偷发送外部请求，否则重试、并发和回滚都会变得难以推理。

05 · 为什么复杂系统需要 Statecharts？

扁平 FSM 的一个问题是状态组合爆炸。假设任务生命周期有 5 个状态，审批有 3 个状态，预算监控有 2 个状态。若把所有维度硬编码成一个枚举，理论组合上界就是 5 × 3 × 2 = 30 个组合；但很多组合根本不合法，且共享行为会重复出现。

Harel 在 1987 年提出 Statecharts，扩展传统状态图，引入层次（hierarchy）、并发（concurrency）和通信（communication），使复杂离散事件系统可以模块化表达。原始论文：Statecharts: A Visual Formalism for Complex Systems ↗。

层次、并发与历史状态

  • 层次状态：一个复合状态包含子状态；进入父状态时，还要按初始子状态规则进入具体活动状态。
  • 正交区域：多个区域同时处于活动状态，同一事件可能分别被各区域处理。它是状态配置语义，不自动等价于真实并行线程。
  • 历史状态：退出复合状态时记录上次活动的子状态，重新进入时可以恢复浅历史或深历史。
  • 进入 / 退出动作：状态激活或退出时执行相应动作；必须考虑动作顺序和失败语义。

W3C 的 SCXML 1.0 Recommendation 将这些语义落实为可执行的状态机表示：W3C SCXML 规范 ↗。例如 SCXML 的 parallel 状态会让其所有子区域同时激活，但事件处理顺序和冲突规则仍由解释算法定义。

07 · 如何证明状态机没有走错路？

画出状态图只是第一步。可靠性来自对所有可能路径的检查，而不是只测试一条“正常流程”。至少需要区分以下问题：

Safety · 安全性

坏事永远不会发生。例如未审批的高风险任务永远不会进入 running；终态任务不会再次触发执行。

Liveness · 活性

好事最终能够发生。例如已批准且资源可用的任务，在环境持续响应等前提下最终成功、失败或被取消，而不是永远卡住。

Reachability · 可达性

某个状态是否能从初始状态到达？例如 failed 是否可达，或者某个状态是不是永远不可达的死代码。

Deadlock · 死锁

系统是否可能进入没有任何可用转移、却又不属于合法终态的配置？超时和恢复路径常在这里暴露缺口。

Lamport 对安全性和活性的经典区分是：安全性要求某些坏事永不发生；活性要求某些好事最终发生。活性声明必须写出环境假设，例如服务最终恢复、审批者最终响应，不能把“可能发生”误写成“必然发生”。参考：TLA+ Tutorial · Safety versus Liveness ↗。

从状态图到测试策略

  • 状态覆盖：每个状态至少被访问一次。
  • 转移覆盖：每条合法转移至少执行一次。
  • 守卫边界：重试次数等于上限、审批权限刚好缺失、预算恰好归零时分别测试。
  • 非法事件：在每个关键状态注入不允许的事件，确认系统拒绝且状态不变。
  • 事件序列：测试 cancel → retry、success → fail、duplicate submit 等危险组合。
  • 持久化恢复：在状态写入前后模拟进程崩溃，验证重启后不会重复执行副作用。

08 · 工程实现：把转移表变成可测试代码

实现时，不要把状态机散落成几十个互相调用的回调。把状态、事件和上下文作为显式输入；转移函数只负责判断下一状态与上下文更新。完整代码与测试：agent_state_machine.py ↗。

from dataclasses import replace

def transition(state, event, context):
    if state == IDLE and event == SUBMIT:
        return VALIDATING, context
    if state == VALIDATING and event == PASS:
        if context.requires_approval:
            return AWAITING_APPROVAL, context
        return RUNNING, replace(context, attempts=1)
    if state == AWAITING_APPROVAL and event == APPROVE:
        return RUNNING, replace(context, attempts=1)
    if state == RUNNING and event in (FAIL, TIMEOUT):
        if context.attempts < context.max_attempts:
            return RETRY_WAIT, context
        return FAILED, context
    raise InvalidTransition(state, event)

这段代码刻意把“非法转移”作为异常，而不是默认返回原状态。生产实现还应补上明确的拒绝策略、结构化错误、持久化事务与并发版本控制。

可靠 Agent Runtime 的实现约束

  1. 先定义状态，再定义事件：状态代表稳定的行为阶段；事件代表发生的事实，不要把每个函数名都当成状态。
  2. 守卫可重复计算：守卫尽量无副作用，输入明确，方便单元测试和审计。
  3. 副作用与状态提交协调：如果状态已写入但外部请求未发出，或请求已发出但状态未写入，系统都可能失去一致性。使用事务、Outbox、幂等键或可恢复命令记录来处理。
  4. 重试有预算：明确最大次数、退避、可重试错误类别和幂等前提；不是所有失败都能安全重试。
  5. 并发更新带版本：为状态记录增加版本号或序列号，用 compare-and-swap / 乐观锁拒绝过期写入，避免两个 Worker 同时从同一旧状态执行。
  6. 每次转移可追踪：记录 entity_id、from_state、event、guard_result、to_state、attempt、transition_version、correlation_id。
  7. 超时与取消是一等事件：长任务需要明确的 timeout、cancel、compensate 与恢复路径。
一个重要区别：状态机定义合法行为；持久化工作流引擎还要负责把状态、事件、计时器、重试、并发执行和外部副作用可靠地落地。两者有关联，但不是同一个东西。

09 · TCP：状态机不是抽象玩具

TCP 连接的生命周期就是一个经典的协议状态机。RFC 9293 §3.3.2 列出 LISTEN、SYN-SENT、SYN-RECEIVED、ESTABLISHED、FIN-WAIT-1、FIN-WAIT-2、CLOSE-WAIT、CLOSING、LAST-ACK、TIME-WAIT 和 CLOSED 等状态；转移由 OPEN、SEND、RECEIVE、CLOSE、ABORT、报文标志位与超时事件触发。

注意 RFC 自己也提醒：状态图只是状态变化的摘要，不是完整协议规范。真实 TCP 行为还包含序列号校验、重传队列、报文处理顺序、错误响应和计时器细节。不能只照着图写一个简化版，就声称实现了 TCP。

工程启示：协议状态机让边界条件可见，但状态图必须与规范中的事件处理规则一起阅读。状态转移图是规格的一部分，不是规格的全部。

来源：RFC 9293 · State Machine Overview ↗。

10 · 不要把所有带有“State”的东西混为一谈

概念状态是什么转移 / 更新主要问题
有限状态机 FSM有限个离散符号状态事件触发确定或非确定转移哪些行为路径合法？
Statecharts / EFSM层次状态配置 + 数据变量守卫、动作、并发区域、历史复杂控制流如何模块化？
State Space Model通常是向量化的动态状态状态方程随时间更新如何压缩和传播历史信息？
MDP环境状态（可观测或部分可观测）动作引起概率转移并产生奖励在不确定环境中如何决策？
Event Sourcing由事件日志重建的业务状态追加事件，再折叠得到当前状态历史事实如何持久化与重放？
Workflow Engine持久化的流程实例与步骤状态事件、计时器、重试、Worker 调度长任务如何跨进程可靠执行？

特别是 FSM 与 SSM：FSM 的状态是有限集合中的离散控制位置；SSM 的状态通常是数值向量，用状态方程编码和更新历史信息。Mamba 等选择性状态空间模型属于后者，不是把传统有限状态机换个名字。可以接着阅读仓库中的 Understanding Mamba ↗。

FSM 与 MDP 也不等价。MDP 在状态与动作条件下引入概率转移和奖励，研究策略如何优化期望回报；确定性 FSM 则主要刻画允许的控制路径。一个实际 Agent 可以把 FSM 用作外层安全控制器，同时把 MDP / RL 用于策略学习，两者可以组合，但不能互相替代。

Event Sourcing 关注事件作为持久事实与状态重建；FSM 关注状态变化的合法性。Workflow Engine 则把流程模型变成可恢复的执行系统。它们可以一起使用：FSM 定义转移规则，事件日志保存事实，工作流运行时调度任务。

11 · 设计一个状态机前，先回答这些问题

  • 状态是否互斥？一个实体是否可能同时处于多个活动状态？若是，是否需要层次状态或正交区域？
  • 每个状态有哪些合法事件？未知事件是拒绝、忽略，还是转为错误？
  • 同一状态与事件是否可能匹配多条守卫？如果可能，优先级和确定性如何定义？
  • 所有非终态是否都有超时、取消或人工恢复路径？
  • 终态是否真正不可逆？如果需要重开任务，是否应创建新实例而不是篡改历史？
  • 动作失败时状态如何处理？副作用是否幂等？重试会不会重复扣费或重复写入？
  • 并发 Worker 如何竞争状态更新？是否有版本号、租约和 fencing token？
  • 安全性与活性分别是什么？哪些环境假设必须成立？
  • 是否能自动生成转移表、状态图、测试用例和可观测性事件？
最小交付物：状态集合、事件集合、转移表、守卫与动作定义、终态约束、非法事件策略、测试序列和恢复方案。只画一张图而没有这些定义，通常还不是一份完整的状态机规格。
