Understanding Jev：类型化概率决策模型

从 Choice、Score、Noul 到贝叶斯风险与 Agent 工作流：理解模型怎样给出一个可执行的判断，以及为什么最终的行动规则必须由软件负责。

研究对象：TypeSafe AI Jev 模型文档版本：1.14.0 阅读时间：约 28 分钟 资料核对：2026-11-21

01 · 为什么软件需要一种“只做判断”的模型？

很多自动化任务并不需要模型写一段话。它只需要回答一个边界清楚的问题：这张工单交给哪个团队？这次操作是否危险？这段回答是否有证据支持？

设想一个客服系统收到下面的消息：

用户消息（教学案例）

“我的账户今天被扣了两次钱。我已经提交过一次退款申请，但还没有收到处理结果。请问现在应该找谁？”

系统接下来要做的不是写一篇客服回复，而是完成几个软件决策：

  • 工单应该进入 Billing、Support，还是 Delivery？
  • 用户是否明确提出退款？
  • 这条工单是否应该立即升级给人工？
  • 如果模型对归属团队不确定，能否先进入人工分流队列？

传统 LLM 可以被要求输出 JSON，但实际系统仍要面对“生成文本 → 解析 → 校验 → 处理异常 → 执行策略”的链条。严格 JSON Schema 可以减少格式错误，却不能自动解决概率是否可信、何时应该拒绝，以及错误动作会造成多大损失的问题。

因此，真正值得研究的问题不是“Jev 能不能替代 LLM”，而是：当软件只需要一个有限集合中的判断时，是否应该把判断接口从文本生成中分离出来？

02 · Jev 是什么？它不是什么？

TypeSafe AI 将 Jev 定位为首个 System One Model。它接收一份待判断的状态（state）和调用方定义的问题（questions），返回类型受约束的答案及概率信息，而不是自然语言段落。官方文档把它描述为一种供软件直接消费的结构化决策模型。[1][2]

fθ:(s,Q)→(A,P)

这里的 fθ 是教学用的抽象记号：s 是输入状态，Q 是问题与候选答案的定义，A 是类型化答案，P 是与答案相关的概率信息。它不是 TypeSafe 已公开的神经网络结构公式。

“System One”应该怎样理解？

名称借用了 Daniel Kahneman 对快速、直觉式 System 1 与较慢、审慎式 System 2 的区分。这里强调的是任务形态：快速、范围受限、适合由代码消费的判断。它不意味着模型拥有与人类大脑相同的认知机制，也不代表它能可靠处理多步数学推理。

必须划清的边界：Jev 的类型安全保证输出落在预先声明的结构和答案空间中；它不保证答案符合事实。一个格式完全合法的错误选择，仍然可能触发错误的退款、封禁或工具调用。

截至 2026-11-21 的公开版本

TypeSafe 当前模型文档列出的最新稳定版本是 jev-1.14.0，jev-latest 指向该版本。1.14 增加了 Box 问题类型；Choice、Score、Noul 仍是本文讨论的核心决策原语。[3]

TypeSafe 公开了 API、问题类型和训练目标说明，但这些信息不足以重建其完整模型架构、参数规模或训练数据。RLCD（Reinforcement Learning for Calibrated Decisions）是厂商对训练方法的命名；不能仅凭名称推断其具体损失函数、采样算法或内部网络结构。[1][4] 发布文章还使用了“cannot hallucinate”的营销表述，但同一文章明确说明其零类型错误图并非经验测量，而是由 schema matching 的结构保证得出。因此，合理的工程解释是“输出类型和结构受约束”，而不是“模型永远不会做出事实错误的判断”。

03 · 三种核心概率原语：Choice、Score、Noul

三种原语的区别不是表面上的字段命名，而是它们对应不同的数学对象。先问清楚答案空间是什么，再选择问题类型。

类型答案空间主要输出典型问题
Choice有限、无序的选项集合choice、每个选项的 probabilities、confidence工单属于哪个团队？
Score有序的等级标尺，通常 2–10 个等级score、每个等级的概率、confidence故障严重程度属于哪个等级？
Noul是 / 否noul，即回答为 Yes 的概率消息是否明确要求退款？

3.1 Choice：在离散选项中选择

如果候选答案之间没有自然顺序，就使用 Choice。假设选项集合为：

Y = {billing, support, delivery}

模型返回一个被选中的类别，以及对所有候选项的概率分布。下面的向量是一个方便讲解的教学算例：

P(Y | x) = {
  billing:  0.70,
  support:  0.20,
  delivery: 0.10
}
selected choice = billing

三个概率相加为 1。choice 是最大概率对应的选项；完整概率向量则保留了次优候选的信息。Choice 最多可声明 255 个选项；如果真实数据可能不属于任何已知选项，应显式考虑 other、none_of_the_above 或配套的 Noul 判断，而不是强迫模型在错误集合中二选一。[5]

3.2 Score：在有序等级上估计位置

如果答案存在顺序，例如故障严重程度，可以定义等级：

  • 0：轻微，不影响主要功能；
  • 1：中等，存在可用的替代方案；
  • 2：严重，关键功能不可用且没有替代方案。

Score 返回各等级的概率，并计算概率加权的位置：

s=∑i=0n−1piℓi

例如，三个等级的概率是 (0.10, 0.60, 0.30)，等级值为 (0, 1, 2)，则得分为 0×0.10 + 1×0.60 + 2×0.30 = 1.20。这个 1.20 是等级轴上的期望位置，不是“故障真实严重程度精确等于 1.20”。等级间距是否具有等距意义，取决于你设计的 rubric；若 0→1 与 1→2 并非等价变化，直接对等级编号取期望就需要格外谨慎。[6]

3.3 Noul：判断一个命题是否成立

Noul 对应二元事件，输出一个 0 到 1 的数值，表示模型认为命题为真的概率。比如 noul = 0.91 表示模型对“这条消息提出了退款请求”给出 0.91 的概率估计。Noul 本身没有单独的 confidence 字段；概率值已经表达了 Yes / No 两种结果的倾向。[7][8]

3.4 Box：1.14 的视觉扩展

Jev 1.14 还提供 Box：在图片中定位目标，输出归一化的上、下、左、右边界。它是空间定位结果，不是 Choice 那样的类别概率分布。官方把图片与 Box 能力标记为 preview / dreamer-ready，并明确提醒尚未达到生产可靠性标准；本文不把它当作成熟的通用检测器。[3][9]

04 · 多个问题并行返回，不等于一个联合概率模型

Jev 可以在一次请求里同时接收多个问题。它们共享同一份状态，并行计算；官方文档明确说明，每个问题独立地针对同一状态进行评估。[2][3]

例如，针对一张客服工单，可以同时提出：

  • Q₁：应该交给哪个团队？
  • Q₂：用户是否明确要求退款？
  • Q₃：消息是否包含重复扣款的证据？

这能降低多次往返请求的开销，也能让代码提前拿到多个维度的判断。但这里有一个经常被忽略的统计边界：

三个边际分布，不自动组成一个联合分布。分别得到 P(团队 | 状态)、P(退款请求 | 状态) 和 P(重复扣款 | 状态)，并不意味着你已经得到了这三个事件的联合概率。不能未经验证就把它们相乘，声称得到 P(A ∩ B ∩ C | 状态)。

“问题独立评估”描述的是模型接口的执行方式，不代表现实世界中的变量彼此独立。真实的工单团队、退款意图和重复扣款事实可能高度相关。若业务规则需要联合概率，应该用明确的联合模型、额外数据或可验证的条件结构来估计；否则，让代码把独立判断组合成明确的业务策略，并把组合规则当作工程假设来测试。

05 · 概率、confidence 与 calibration：三个不能混淆的概念

5.1 概率分布回答“模型把质量放在哪里”

Choice 的概率向量描述模型在候选类别之间如何分配概率质量。对刚才的三分类算例：

p = (0.70, 0.20, 0.10)
p_max = 0.70

这里 p_max = 0.70 是最可能选项的概率。它并不自动意味着“这次选择有 70% 的真实正确率”；那需要通过同一任务分布上的真实标签验证。

5.2 Jev 的 confidence 是分布集中度摘要

对含有 n 个选项的 Choice，TypeSafe 文档定义的 confidence 是：

confidence=pmax−1n1−1n

当概率均匀分布时，confidence 为 0；当概率全部集中在一个选项时，confidence 为 1。对于三个选项、最大概率 0.70 的例子：

confidence = (0.70 - 1/3) / (1 - 1/3)
           = 0.55

因此，0.70 是 top-option probability，0.55 是分布集中度 confidence。两者不是同一个统计量。官方文档特别提醒：confidence 并不等于“所选答案正确的概率”。对固定选项数的 Choice，confidence 只是 top probability 的单调变换，并没有创造一份独立的新证据。若需要判断第一名是否只比第二名略高，应继续检查完整概率向量，尤其是 top-to-second ratio（pmax / psecond）；它回答的是“第一名领先第二名多少”，而 confidence 回答的是“概率质量集中到什么程度”。对 Noul，直接使用 P(Yes) 更清楚；官方给出的 0.7 / 0.3 可作为起始阈值，中间区间应有独立的复核结果，而不是强行四舍五入。[8]

5.3 Calibration 是群体层面的概率可靠性

概率校准问的是：在大量预测中，所有被模型赋予 0.8 置信概率的预测，是否大约有 80% 最终正确？用 top-label 校准表达为：

P(Y^=Y∣pmax=p)=p

这是一个关于预测集合的统计性质，不是单个样本的保证。一个预测的概率为 0.95，并不意味着我们可以证明这一次判断有 95% 的客观正确性；只有在足够大的、与部署分布匹配的验证样本上，才能检查模型是否满足相应的校准关系。[10]

5.4 ECE 与 Brier Score

Expected Calibration Error（ECE）通常把预测按置信度分箱，比较每个箱中的平均置信度和实际准确率：

ECE=∑b=1B|Sb|N·|acc(Sb)−conf(Sb)|

ECE 越低通常意味着分箱层面的概率与准确率更接近。但 ECE 依赖分箱数、分箱策略和样本量；单独报告一个 ECE 数字会掩盖局部过度自信或子群体失准。建议同时报告 reliability diagram、Brier Score / NLL、分组校准和置信区间。Guo 等人的经典研究也表明，现代神经网络的置信度可能失准，温度缩放是常见的后处理方法之一。[10]

Score 的 confidence 还会考虑等级之间的距离：相邻等级之间的概率分散，与两端等级之间的概率分散，可能得到不同的 confidence。其官方定义为：

confidence=max(0,1−∑i=0n−1pi|i−m|MADunif)
MADunif=1n∑i=0n−1|i−n−12|

其中 m 是概率最大的等级编号。这个定义让“概率分布在相邻等级之间摇摆”和“概率分布在两个极端等级之间摇摆”得到不同的 confidence。它仍然是对概率分布形状的摘要，不应直接解释为该分数有多大概率正确。[8]

06 · 从概率到动作：贝叶斯风险，而不是盲目取最大值

概率本身不是业务决策。业务真正关心的是：选错某个动作会付出多少代价？例如，把重复扣款工单误路由给 Delivery，和把普通咨询误路由给 Billing，成本可能不同。

令真实类别为 y，系统动作是 a，损失函数为 L(a,y)。给定当前状态 x，动作 a 的条件期望风险为：

R(a∣x)=∑y∈YL(a,y)P(y∣x)

最优动作是让条件期望损失最小的动作：

a*=arg minaR(a∣x)

注意这里的决策对象是 动作，不是模型的 top label。一个概率最高的类别，未必对应最低的期望损失。

6.1 二分类阈值为什么不总是 0.5？

假设有一个二元判断：是否拦截一笔疑似欺诈交易。令 p=P(欺诈 | x)。误报（把正常交易拦截）成本为 CFP，漏报（放过欺诈）成本为 CFN，正确决策损失为 0。

拦截的期望损失是 CFP(1−p)，放行的期望损失是 CFNp。令两者相等，可以得到阈值：

p>CFPCFP+CFN

如果误报成本是 20、漏报成本是 180，阈值就是 0.10，而不是 0.50。漏报越昂贵，系统越应该倾向于拦截。这个阈值来自决策成本，而不是模型“更有信心了”。[11]

07 · 交互实验：最高概率的选项，是否一定应该自动执行？

我们用一个完全虚构的三分类客服分流案例，观察概率和动作成本如何共同决定结果。假设错误路由的损失分别为：

  • Billing 路由错给 Support：4；错给 Delivery：5。
  • Support 路由错给 Billing：3；错给 Delivery：4。
  • Delivery 路由错给 Billing：5；错给 Support：4。
  • 人工复核成本：由滑块控制，且假设对三种真实类别相同。

这也解释了为什么“设置一个全局 confidence 阈值”通常过于粗糙：不同动作的误判成本不同，同一模型在只读操作、可撤销操作和不可逆操作上，应该采用不同的风险预算。

08 · 拒绝决策：Abstention 与 Selective Prediction

一个可靠的决策系统不应该被迫对每个输入都给出自动动作。它至少需要三种结果：

  • Accept / Act：概率与预期风险满足自动执行条件。
  • Review / Defer：证据不足或风险较高，交给人工或更强的推理模型。
  • Reject / Block：策略明确禁止该动作，或者模型判断不适用。

如果系统通过阈值 τ 决定是否回答，那么可以定义覆盖率（coverage）与选择性风险（selective risk）：

Coverage(τ)=P(accept)
Rsel(τ)=E[ℓ(y^,y)∣accept]

提高阈值通常会降低覆盖率、减少自动回答数量；如果模型的不确定性信号有效，留下来的样本应当具有更低的错误风险。部署时要报告风险—覆盖率曲线，而不只是一个“准确率”。[12]

实际的拒绝策略不应只看 confidence。对 Choice，可以评估目标动作的 top probability、第二名差距、错误成本和校准情况；对 Noul，直接针对 P(Yes) 设置双阈值，中间区域交给复核；对 Score，还需要检查等级分布是否呈现多峰或跨级分裂。

09 · Jev 如何嵌入 Agent：把判断、策略与执行分开

Agent 不只是一个模型。它通常包含状态收集、规划、工具调用、执行反馈和终止判断。Jev 可以承担其中某些窄范围判断，但不应接管整个行动闭环。

一个更稳健的工作流

  1. 构建状态：代码先从数据库、检索结果和当前会话中提取与问题有关的字段，避免把大量无关上下文交给模型。
  2. 定义问题契约：为每个判断写清楚问题、候选项、边界条件，以及“其他 / 不确定”路径。
  3. 并行调用：把需要的 Choice、Score、Noul 问题放进一次请求，但把它们当作分别评估的维度。
  4. 计算风险：代码读取概率，结合业务成本矩阵、权限和阈值，决定执行、复核或拒绝。
  5. 受控执行：只有通过权限检查的动作才能调用工具；转账、删除、对外发送等高风险副作用应有额外审批。
  6. 记录与评估：保存模型版本、问题定义、候选项顺序、概率、最终动作、人工修正和真实结果，用于持续校准。

一个典型的组合是：LLM 负责理解用户意图并生成解释；Jev 负责对有限选项进行快速判断；业务代码负责规则和动作；人工负责高风险或低证据场景。它们不是互相取代，而是把任务放到最适合的组件中。

10 · 独立研究证据：表现、校准与偏差都要看

Jev 是一个很新的商业模型。评价它时必须区分厂商文档、厂商自报结果和独立研究；不同版本、任务、语言、标签定义和问题措辞，都会影响结论。

10.1 37 个数据集上的公开基准

Deußer 等人的独立基准研究评估了 Jev 1.13.0：覆盖 37 个数据集、多个任务家族，共 346,009 次请求，并与两个开放权重模型在相同请求上比较。作者报告 Jev 在部分分类、路由和理解任务上表现较强，但也观察到低资源语言、细粒度或噪声标签、rubric 评分等场景的性能下降。[13]

该研究的价值在于提供了冻结模板、完整请求与响应以及可复核的评测代码。它并不意味着 Jev 1.14.0 在所有任务上都具有相同表现，也不能把一个 benchmark 的概率校准直接迁移到你的线上业务。

10.2 独立校准审计：任务与措辞会改变概率可靠性

Meng 对 Jev 1.13.0 做了一项校准审计，包含 3,244 次评估、2,372 条不同文本，涉及两个公开分类任务。该预印本报告：校准误差会随着任务和问题表述变化；同一任务的两种问法之间，校准误差差异达到 0.071；一个四分类中间概率区间中，模型给出的 0.750 对应的实际正确率约为 0.612。[14]

这些结果不是对 Jev 全部能力的最终判决：研究范围是特定版本、两个任务和特定评测协议，作者也明确提醒这是探索性分析。但它足以支持一个工程结论：不要把“厂商称其为 calibrated”理解成“任何业务分布都已经校准”。

10.3 偏差研究：选项顺序与问题变体会影响判断

另一项对 Jev 1.13.0 的研究分析了 41,500 次回答，覆盖认知反思、锚定、合取、框架、沉没成本、零风险和定价偏差等任务。研究发现，部分无关数值和选项顺序会影响判断；在特定改写后的合取任务中，模型违反概率合取规则的比例达到 54%。[15]

这里需要特别注意：这是预印本中的特定任务结果，不是一个可泛化的“Jev 偏差率”。它提示我们不能只检查最终选项是否变化，还要检查概率向量、confidence 和最终动作是否对无关的格式变化敏感。

10.4 风险预算：校准概率不等于受控错误率

Messoudi 与 Mansar 的研究把问题推进了一步：如果系统没有人工复核通道，每个输入都必须被分配一个动作，怎样保证“被允许通过的那一组样本”中的漏放风险不超过预算？他们在六个 moderation、safety 与 reranking 数据集上比较普通阈值、经验阈值和 Learn Then Test（LTT）。[16]

在有定义的测试风险设置中，朴素阈值策略有 42.0%（105 / 250）超过预设风险预算，经验阈值为 51.7%（108 / 209），LTT 为 7.8%（12 / 153）。这些比例的分母只包含测试风险可定义的设置；LTT 也会在无法获得证书时拒绝部署该阈值，并采用保守 fallback。它不是一个“永不出错”的保证。

校准、Bayes Risk 与 LTT 解决的是不同问题：
  • Calibration：概率数值是否与长期观测频率相符？
  • Bayes Risk：给定概率与损失矩阵，哪个动作的期望损失最低？
  • Risk Control：在明确抽样假设和风险预算下，能否用独立校准样本为某个策略阈值提供有限样本保证？

LTT 不会自动让模型概率更校准。它把评分器和候选阈值固定后，使用独立校准样本检验候选策略；其保证依赖校准样本与部署总体的抽样假设。它展示了概率接口之后仍然需要一层统计决策治理。

10.5 选择性推理：决策模型也可以按需“慢下来”

Zheng 与 Chen 研究了如何在类型化答案接口中加入按需推理：先快速读取候选答案分布，只有在预期收益足够时才启动推理；过程中读取中间答案，并在不确定性足够低时提前停止。其 768 道 ProofWriter、LogiQA 2.0 与 ARC-Challenge 问题实验中，准确率从直接读取的 70.96% 提升到 84.38%；相较 1,024-token 终止读取，管线时间降低 46.30%，准确率差异为 −1.17 个百分点。[17]

这不是 Jev 1.14 的内置功能，而是一个研究方向：System One 的快速判断可以与受控的 System Two 推理预算组合，而不是只能在“完全不推理”和“每次都长推理”之间二选一。

10.6 表格数据：内容不变，组织方式仍可能改变答案

关于 Tabular Data 的研究比较了四种类型化决策模型和三个 LLM，覆盖行分类、事实验证与异常检测，并对同一内容构造 21 种格式或措辞改写。研究报告：部分决策模型对问题措辞变化相对稳健，但没有被测试的模型能够对表格组织方式保持完全稳健；在某些改写下，至少三分之一的行级决策会发生变化。[18]

这提醒工程师：将表格转成 JSON、调整列顺序、重命名字段、改变候选项描述，都属于输入契约的一部分。数据语义相同，不意味着模型的输出分布必然相同。

10.7 研究版图已经超出单一产品

Chen 等人的综述把 Typed Decision Models 放在 LLM 路由、零样本分类、Safety Guard、标签概率读取和部署适配成本的交汇处。作者版本标注已被 ACM SIGKDD Explorations 接收；作者同时披露参与 AnyJev 相关研发，因此这篇综述适合作为研究地图，不应单独作为中立的性能证据。[19]

证据综合：类型化输出能减少解析和结构错误；概率接口让风险控制与拒绝策略更容易实现；但准确率、校准、鲁棒性和公平性仍然必须在目标任务、目标版本与目标人群上独立验证。

11 · 适用边界：什么时候应该使用，什么时候不应该？

方案擅长主要代价 / 风险更适合
传统分类器固定标签、稳定任务、低延迟新任务或新标签可能需要训练 / 调整输出头高频、长期稳定的分类
LLM + JSON Schema复杂语义、开放式解释、灵活任务仍需处理生成、成本、延迟和语义验证需要推理与自然语言表达的工作
Jev / 类型化决策模型有限选项、窄问题、概率输出、并行判断任务校准、选项设计、问题措辞和版本变化路由、审核、评分、边界清楚的判断
确定性代码算术、日期比较、权限、硬约束不能独立理解开放语义必须精确、可审计的规则

官方已公开的失败模式

TypeSafe 的 Model Jaggedness 文档列出多类已知弱点：字面理解、数学与计数、日期比较、多层间接推理、无关上下文过多、对抗性内容、指令与 criteria 冲突，以及 Choice 选项顺序影响。[16]

  • 不要把计算交给模型：金额、时间差、阈值比较、计数等由代码执行。
  • 不要把多个判断塞进一个问题：拆成原子问题，再由程序组合。
  • 不要无限扩大 State：先检索、过滤和归一化，只提供问题所需的字段。
  • 不要忽略选项顺序：在测试集上轮换选项顺序，检查答案和概率是否稳定。
  • 不要让 State 中的文本变成指令：外部内容可能包含提示注入或误导信息；它是数据，不是权限来源。
  • 不要让模型直接批准高风险动作：将授权、金额上限、审批与审计放在确定性控制层。

数据治理同样重要

Jev 是托管式 API，调用方需要把状态发送给服务提供方。官方说明客户请求和响应不用于模型训练，并在法律 / 企业文档中单独说明数据保留选项；但“不用于训练”不等于“数据没有离开你的基础设施”。在传递个人信息、财务记录或机密内容前，应先核对适用的数据处理协议、保留策略、区域和组织权限。[3]

12 · 工程实践清单：把概率决策做成可审计的软件

下面的纯 Python 示例把三个容易混在一起的步骤拆开：验证概率分布、计算期望风险、比较自动动作与人工复核。它是教学用策略代码，不是 Jev SDK，也不复现 Jev 模型。

from jev_decision_policy import choose_with_review

probabilities = {
    "billing": 0.70,
    "support": 0.20,
    "delivery": 0.10,
}

costs = {
    "route_billing": {"billing": 0, "support": 4, "delivery": 5},
    "route_support": {"billing": 3, "support": 0, "delivery": 4},
    "route_delivery": {"billing": 5, "support": 4, "delivery": 0},
}

decision = choose_with_review(
    probabilities,
    costs,
    review_cost=1.0,
)

assert decision.action == "review"
assert abs(decision.risks["route_billing"] - 1.30) < 1e-9

完整的可运行实现和测试位于仓库源码：jev_decision_policy.py 与 test_jev_decision_policy.py。它们只使用 Python 标准库；GitHub Pages 只发布文章和静态资源，不会把 Python 源码作为可执行页面部署。

上线前至少验证这些不变量

  1. 概率必须是有限数值、非负，且总和在容差范围内接近 1。
  2. 输出标签必须与调用方声明的答案集合完全一致；未知标签不能悄悄映射到默认动作。
  3. 所有候选动作必须有完整的成本矩阵；缺失的成本不能被默认为 0。
  4. 拒绝 / 人工复核必须是明确的动作，并且有自己的成本、时限与负责人。
  5. 校准集与线上分布要尽量一致；任务、语言、标签、问题措辞或模型版本变化后重新评估。
  6. 保存模型版本、State 摘要、问题定义、选项顺序、概率、策略版本、最终动作和人工修正。
  7. 高风险副作用必须经过独立权限和审批检查，不能只依赖模型概率。
版本治理：如果你针对 jev-1.14.0 调好了阈值，就应固定该模型版本并记录策略版本。官方文档提醒，jev-latest 是会移动的别名；升级模型后要重新跑目标任务评测，而不是假设旧阈值仍然有效。[3]
