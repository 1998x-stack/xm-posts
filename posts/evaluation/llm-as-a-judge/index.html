EVALUATION SYSTEMS · JUDGE RELIABILITY

Understanding
LLM-as-a-Judge

让模型评价模型：从一条评分 Prompt，到一套有标准、有证据、能校准、可审计的自动评测系统。

评测与复现 / LLM-as-a-Judge研究生进阶约 42 分钟核心问题：如何评价评审器本身？

01 · 为什么我们需要一个“模型评审器”？

当模型已经能写文章、生成代码、解释数学证明时，最难的部分往往不再是“生成一个答案”，而是判断这个答案到底好不好。

先想一个具体任务：同一个问题交给两个语言模型。模型 A 给出一段 80 字的回答，模型 B 给出一段 300 字的回答。哪一个更好？如果问题要求准确、简洁地解释一个数学概念，B 的篇幅更长不代表它更正确；如果问题要求给出边界条件，A 的简短也不代表它更清晰。

传统自动指标可以解决一部分问题。例如 BLEU、ROUGE 通过与参考答案比较 n-gram 重合度，适合某些有参考文本的任务；单元测试可以判断代码是否通过指定用例；Exact Match 可以判断答案字符串是否完全一致。但开放式生成通常存在多种合理表达，参考答案可能不完整，风格、事实、推理和指令遵循也不是一个数字能够同时概括的。

LLM-as-a-Judge 的核心思路是：把一个能力较强的语言模型作为评价器，向它提供任务、候选答案和明确的评价标准，让它输出分数、偏好、排序或可核验的批评意见。它把自然语言理解能力转化为一种可扩展的评价接口。

最重要的区分：生成模型回答“我能生成什么”，评审模型回答“按照给定标准，哪个输出更符合要求”。评审器不是天然的真理来源；它本身也是一个需要被验证、监控和校准的模型。

02 · LLM-as-a-Judge 究竟在判断什么？

先把问题形式化。设输入任务为 q，必要上下文为 c，候选输出为 y。评价标准（rubric）记为 r，它规定评价维度、每个维度的含义、分值锚点、证据要求和权重。评审模型记为 Jθ，其中 θ 表示模型参数及其版本。

评审器接收 (q, c, y, r)，输出结构化结果 z。一个实用的结果至少应包含：各维度分数、支持判断的证据、最终判断、置信度或不确定性标记，以及是否需要人工复核。

表 1：评价目标不同，Judge 的任务定义也不同
评价维度要回答的问题更合适的证据不能混淆的概念
Instruction following是否完成用户要求？逐项对照指令和约束遵循指令不等于事实正确
Factuality关键事实是否正确？权威来源、检索证据、数据库表达流畅不等于事实成立

这张表揭示一个关键原则：先定义被测量的构念（construct），再设计评分方式。如果“有帮助”没有被拆成可观察的行为，模型就可能用“语言优美”“篇幅很长”之类容易识别的表面信号替代真正目标。

03 · 一次可靠的评审，应该经过哪些步骤？

Step 1：固定任务与评价单位

不要只给 Judge 一句“请评价回答质量”。应当明确任务是什么、输入包含什么、候选答案是否匿名、评估对象是单轮回答还是多轮对话、哪些信息可被引用、哪些内容属于不可信输入。任务边界决定了后续指标是否有意义。

Step 2：写出可以执行的 Rubric

Rubric 不是一句形容词，而是一份评价协议。每个维度需要定义：评价对象、分数范围、正反例、边界条件和证据要求。比如“事实正确性 1–5 分”仍然太宽泛；更好的定义是：5 分表示所有关键可核验事实均有证据支持，4 分表示存在非关键遗漏但无实质错误，1 分表示核心结论错误或捏造证据。

Step 3：调用 Judge 并约束输出结构

要求模型输出固定 JSON Schema，而不是一段难以解析的自由文本。结构化字段可以让系统检测缺失维度、非法分数、引用缺失、平局和人工升级条件。格式校验只能证明输出可解析，不能证明判断本身正确。

Step 4：执行独立校验与偏差审计

对代码使用测试，对数学使用符号或数值验证，对事实问题使用来源核查；对 pairwise 结果交换候选顺序，对相同样本重复运行，并抽取一部分样本由人类专家标注。不同类型的检查针对不同失效模式，不应让一个 Judge 自己证明自己。

Step 5：聚合、校准并报告不确定性

聚合之前先保留单次判断、提示词版本、Judge 模型版本、采样参数和证据。汇总结果要报告样本量、置信区间、人工一致性和已知偏差，而不是只展示一个漂亮的平均分。

04 · 四种常见评审范式

4.1 Pointwise：给一个回答打分

输入一个候选答案，按 rubric 对每个维度评分。例如，事实正确性 4/5、指令遵循 5/5、表达清晰度 3/5。它适合构建质量画像和发现具体缺陷。但不同 Judge 对“4 分”的内部尺度可能不同，因此跨模型、跨任务比较原始分数时必须谨慎。

4.2 Pairwise：比较 A 和 B 哪个更好

Pairwise 让模型在同一个问题下比较两个答案，输出 A 胜、B 胜或平局。它通常比直接问“这个回答值几分”更容易形成相对判断，也适合 A/B 模型对比和偏好数据收集。风险在于候选顺序、答案长度、模型身份和比较提示词都会影响选择。

4.3 Listwise：一次比较多个候选

Listwise 把多个候选放在一起排序，能节省部分调用成本，但候选数增加后，注意力分配、比较复杂度和位置排列空间都会变大。若模型只选“最好的一个”，并不意味着它已经可靠地给出了完整排序；需要明确未选候选之间是否真的可比较。

4.4 Critique / Verifier：解释哪里有问题

Critique 输出优点、缺陷、遗漏和修订建议；Verifier 对一个可验证命题或推理步骤进行核验。对于代码、数学和事实任务，最好把语言模型的批评与独立工具结合：Judge 负责定位可能的问题，测试或外部证据负责确认问题是否真实存在。

05 · 数学模型：评分、偏好和评审质量

5.1 Rubric 加权评分

设一个回答有 K 个评价维度，第 k 个维度的分数为 sk，权重为 wk。一个简单的总分是归一化加权和：

(1)
S(y)=∑k=1Kwksk(y)∑k=1Kwk

例如，事实正确性权重 0.5、指令遵循权重 0.3、表达清晰度权重 0.2。某回答分别得到 4、5、3 分，那么总分是 0.5×4 + 0.3×5 + 0.2×3 = 4.1。

注意：这个 4.1 是在给定 rubric 和权重下的聚合结果，不是客观世界中的“真实质量”。如果 rubric 漏掉了关键安全约束，精确计算只会更精确地汇总一个不完整目标。权重也应在评测前确定，不能看到结果后为了偏好某个模型而随意调整。

5.2 Pairwise 与 Bradley–Terry 偏好模型

若每个候选 i 有一个潜在质量参数 θi，Bradley–Terry 模型将 i 胜过 j 的概率写成：

(2)
P(i≻j)=exp(θi)exp(θi)+exp(θj)

这类模型可以从成对比较中估计相对强弱，也能用于构建排行榜。它依赖一个重要假设：候选偏好可以由相对分数解释。真实评测中，偏好可能随任务、评价维度和上下文变化；模型 A 在代码任务上更强，不代表它在事实问答或写作任务上也更强。

5.3 与人工判断的一致性

如果把人工标签记为 hi，Judge 标签记为 ji，最直观的精确一致率是：

(3)
A=1N∑i=1N1[ji=hi]

但精确一致率没有扣除“仅仅因为标签分布”而产生的偶然一致。Cohen's kappa 用观察一致率 po 与边际分布推算的偶然一致率 pe 做校正：

(4)
κ=po−pe1−pe

对于连续分数，可以报告 Pearson 相关或 Spearman 秩相关；对于有序等级，可以考虑加权 kappa；对于多位标注者，可以考虑 Krippendorff's alpha。指标选择要匹配数据类型与标注协议。

相关不等于一致。 如果 Judge 总是比人工多打 1 分，两者的 Pearson 相关可能很高，但它们并不一致。若目标是让 Judge 复现人工分数，应同时看绝对误差、偏差和一致性，而不是只报相关系数。

06 · 代表性研究：从 G-Eval 到 JudgeBench

6.1 MT-Bench 与 Chatbot Arena：把偏好评价规模化

Zheng 等人在 NeurIPS 2023 的研究 Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena 探索用强 LLM 评价开放式对话模型。MT-Bench 提供多轮问题集，Chatbot Arena 收集真实用户的成对偏好。论文报告 GPT-4 Judge 在其研究设置中与人工偏好的总体一致率超过 80%，达到与人类之间一致率相近的水平。

这个结果说明强模型可以成为规模化评价的有用近似，但不能把“超过 80%”理解为任何任务、任何 Judge、任何 rubric 都有 80% 准确率。论文同时讨论了位置偏差、冗长偏差、自我增强偏差和有限的推理能力。评价任务、样本构成和人类标注协议都会改变这个数字。

6.2 G-Eval：把评价步骤和输出格式显式化

G-Eval（EMNLP 2023）使用 LLM 先根据任务说明和评价标准生成更细的 Evaluation Steps，再以表单式结构对候选文本评分。它将“请打分”拆成更清楚的评价步骤和字段，并研究输出评分 token 的概率信息。

论文报告，在其摘要评价实验中，GPT-4 作为评审器与人工评分的 Spearman 相关达到 0.514。这个数值是特定数据集与任务设置下的实验结果，不应被挪用为所有 LLM-as-a-Judge 系统的通用表现。作者还指出评审器可能偏好由 LLM 生成的文本，这提示我们必须审计评审器自身的偏好。

G-Eval 还利用评分 token 的概率信息进行加权。假设评分范围是 1 到 R，模型对每个评分 token 的输出概率为 pr，则可以计算概率加权分数：

(5)
s^=∑r=1Rr·pr∑r=1Rpr

直觉上，如果模型在 3 分和 4 分之间犹豫，概率加权可以保留这部分不确定性，而不是只读取最终选中的一个整数。这里的 pr 是评分 token 的条件概率，不等于经过校准的“答案正确概率”；它受 tokenizer、提示词、输出格式和候选 token 集合影响，不能直接跨任务比较。

6.3 JudgeBench：评审器也需要考试

JudgeBench（ICLR 2025）提出一个更严格的问题：如果两个答案中一个存在细微但关键的事实或逻辑错误，Judge 能否识别？它构建 350 组成对答案，覆盖常识、推理、数学和代码，并强调指令遵循、事实/逻辑正确性、风格偏好之间的层级关系。

这个层级很重要。先判断答案是否响应了问题，再检查事实与逻辑是否正确，最后才考虑风格是否符合偏好。一个答案即使表达流畅、结构完整，如果核心结论错了，也不应靠“写得好看”获得更高分。JudgeBench 的困难样本表明，一些能力很强的模型在细微正确性比较上也可能只略高于随机猜测。

6.4 2025–2026：从单一分数走向可靠性协议

2025 年的 Judging the Judges 系统研究了评审器的位置偏差，在 15 个 Judge、MT-Bench 与 DevBench 上分析超过 150,000 次评价，并提出 Repetition Stability、Position Consistency 和 Preference Fairness 等指标。研究强调：偏差不仅与 Judge 有关，也会随候选答案质量差距和任务类型变化。

2026 年的综述 Large language models as judges: recent advances... 将文本与代码评审、Rubric prompting、成对比较、多 Judge 集成、工具增强验证、校准、公平性和对抗鲁棒性纳入统一视角。另一篇 2026 年预印本 Reliability without Validity 报告，在其大规模实验中，精确一致率与 Cohen's kappa 的差距可达 33–41 个百分点；Judge 排名会随 Benchmark 改变，而很高的重复稳定性也可能与明显的位置偏差并存。该工作目前应按预印本看待，数值不能脱离其数据集和协议直接泛化。

07 · 最容易被忽略的问题：Judge Bias

评审器并不是一个中性的函数。即使评价标准写得很详细，模型仍可能受到输入顺序、篇幅、措辞风格、模型身份和上下文提示的影响。偏差的危险在于：它会让评价系统稳定地偏向某一类输出，而不是随机地产生噪声。

7.1 Position Bias：先出现的答案更容易获胜

在 Pairwise 评审中，设候选 A 和 B 的内容完全不变。第一次提示词按 A、B 的顺序输入；第二次只交换顺序，按 B、A 输入。如果 Judge 两次都选“第一个”，它实际偏好的可能是位置，而不是候选内容。

交互实验：改变 Judge 的选择策略

选择一种评审行为，观察原始顺序与交换顺序下，Judge 到底跟随候选内容，还是跟随位置。

原始顺序（A 在第 1 位）选择 A候选顺序：A → B
交换顺序（B 在第 1 位）选择 B候选顺序：B → A
审计结论：两次都选择同一个候选 A。候选身份保持一致，Position Consistency = 1。

注意：这里展示的是教学用的确定性样例，不是对真实模型的测量。真实审计需要多个任务、重复运行和不同 Judge 版本。

08 · Meta-evaluation：如何评价评审器本身？

这是整个体系的核心：我们不能只问“Judge 给出的分数是多少”，还必须问“这个分数是否有效、是否稳定、是否公平”。

8.1 Agreement：是否与人类参考判断一致？

准备一个由人工标注的校准集。每条样本至少由多位标注者独立判断，保留原始标签和分歧，而不只保留多数票。再让 Judge 对同一批样本评分或比较，计算精确一致率、Cohen's kappa、Spearman 相关或适合当前数据类型的指标。

更重要的是，必须测量 Human–Human Agreement。假设三位专家之间的一致率本身只有 72%，那么 Judge 与某一位专家的 72% 一致，不能直接被称为“错误 28%”；它可能接近单个人类标注者的可达到水平。反过来，如果 Judge 与人工多数票高度一致，但人工标注本身存在系统偏差，也不能把多数票当作绝对真值。

8.2 Consistency：相同输入是否稳定？

在相同提示词、相同模型版本和相同采样设置下重复运行，观察评分方差、选择分布和判断翻转率。然后再对提示词做轻微但语义等价的改写，测试结果是否发生不合理变化。必须记录 temperature、seed（若可用）、模型快照、系统提示词和工具版本。

稳定性回答的是“重复测量是否相似”，并不回答“测量是否正确”。一个总选第一位的 Judge 可能每次都选择第一位，重复稳定性非常高，但它仍然不是一个公平的比较器。

8.3 Fairness & Robustness：无关变化是否改变结论？

设计一组反事实对照：交换 A/B 顺序、改变答案长短、匿名化模型身份、改变格式、改写非关键措辞、加入恶意指令，观察评分变化。对客观任务，还要使用外部验证器检查结论，例如数学答案的精确计算、代码的测试结果、事实陈述的来源支持。

8.4 Calibration：分数应该对应什么含义？

校准关心的是：当 Judge 给出某个分数或置信区间时，这个数值在经验上意味着什么。一个 4/5 分不自动等于“80% 正确概率”；它首先只是 rubric 上的有序等级。若希望把分数解释为概率，需要在独立的人类标注集上学习映射，并在留出数据上检查可靠性曲线、Brier Score 或 Expected Calibration Error（ECE）。对于有序评分，还应保留等级间距并考虑 ordinal calibration，而不是未经验证就把 1–5 分线性映射为 0–100%。

校准集应覆盖不同任务难度、不同分数区间和边界案例。若模型升级、rubric 改版或数据分布变化，原来的映射可能失效，需要重新评估。不要用训练校准映射的同一批样本报告最终校准成绩。

8.5 一个可执行的最小评测协议

  1. 建立分层样本：按任务类型、难度、答案质量差距、语言和长度分层抽样，避免只测简单题。
  2. 收集人工标签：至少记录多位标注者的独立判断、分歧率和裁决规则。
  3. 固定评审协议：公开模型版本、系统提示词、rubric、温度、采样策略和输出 Schema。
  4. 测量三类指标：人工一致性、重复稳定性、偏差与鲁棒性；必要时增加校准误差和成本。
  5. 独立验证：在未用于提示词调参的留出集上复测，并报告置信区间。
  6. 设置人工升级条件：边界样本、低置信度、评审器分歧、异常分布和高风险决策进入人工复核。
研究结论的正确读法：2025 年位置偏差研究和 2026 年的可靠性研究共同提醒我们，评审器的稳定性、偏差和人类一致性是不同的统计维度。不能用单一准确率或多 Judge 共识代替完整的 Meta-evaluation。

9.2 可复现的指标代码

下面的纯 Python 示例不调用任何模型 API，只计算评审器的两个外部属性：人工标签一致性与成对顺序交换稳定性。它刻意把“候选一致”与“位置偏好”区分开。

from judge_metrics import (
    agreement_rate,
    cohens_kappa,
    position_swap_audit,
    position_consistency_rate,
)

human = ["yes", "yes", "no", "no"]
judge = ["yes", "no", "no", "no"]

print(agreement_rate(human, judge))  # 0.75
print(round(cohens_kappa(human, judge), 3))  # 0.5

# 原始顺序选择 A，交换后选择 B：仍然是候选 A 获胜
print(position_swap_audit("A", "B"))  # candidate_a

# 两次都选择第一个位置：候选改变，暴露首位偏好
print(position_swap_audit("A", "A"))  # first_position

这段代码是指标计算的最小参考实现，不是一个完整的 Judge 服务。真实系统还需要数据采样、模型调用、超时重试、版本记录、隐私保护、权限控制、结果存储和监控。

9.3 上线前检查清单

  • 评价目标与 rubric 在运行前已固定，并保留版本号。
  • 人工校准集与最终测试集分离，避免在同一数据上反复调提示词后报告成绩。
  • 模型、Prompt、采样参数、候选顺序和工具版本可追溯。
  • 对 Pairwise 任务进行 A/B 顺序交换，对 Pointwise 任务进行长短和格式对照。
  • 对事实、数学和代码任务使用检索、计算或测试等外部证据。
  • 报告人工一致性基线、Judge–Human Agreement、稳定性和偏差。
  • 对低置信度、分歧和高风险样本保留人工复核路径。
  • 持续监控模型升级、Rubric 修改和数据分布变化带来的性能漂移。

10 · 什么时候应该使用，什么时候不应该使用？

表 3：选择评价方式时的工程判断
场景建议方式原因
开放式回答质量、写作风格、帮助性Rubric + LLM Judge + 人工校准评价标准复杂，参考答案不唯一
代码功能正确性单元测试 / 集成测试为主，Judge 辅助解释可执行测试比语言模型猜测更直接
数学推导与数值结果符号/数值验证 + 专家审查 + Judge 辅助流畅解释不能替代证明与计算
事实密集型问答检索证据 + 引用核验 + Judge需要可追溯来源，而非仅靠模型记忆
安全、医疗、法律等高风险决策规则系统 + 专家人工审核；Judge 只做辅助错误成本高，不能把模型评分当作最终裁决
大规模候选模型排行榜盲测 Pairwise + 多任务 + 人工抽检必须审计位置、任务构成和排序不确定性

最稳妥的架构不是“用 LLM 替代所有评测工具”，而是让不同工具承担自己擅长的部分：确定性程序验证确定性事实，检索系统提供外部证据，LLM 处理复杂语义判断，人类专家负责高风险裁决和评价标准治理。

记住这条原则：LLM-as-a-Judge 的价值不是让模型成为新的裁判权威，而是把原本昂贵、模糊、难以规模化的评价过程，变成可以被定义、测量、审计和持续改进的工程系统。
