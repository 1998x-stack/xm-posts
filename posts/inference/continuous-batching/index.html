Continuous Batching：为什么要每轮重新组批？

理解 ORCA 的 Iteration-level Scheduling 与 Selective Batching：不是「批次更大」，而是把调度单位从请求缩到生成的一轮。

Serving / Scheduler · 研究生技术精读 · 阅读约 23 分钟 · 2026-11-21

01 · 为什么请求完成了，还不能离开批次？

在线推理不是把一整段文本一次性吐出来：每一轮生成一个 token，生成长度还各不相同。把请求「绑死」在一次 batch 里，会制造不必要的排队与等待。

设 A 只需生成 2 个 token，B 需要 5 个；第三个请求 C 在第 2 轮到达。请求级批处理把 A、B 作为不可改变的工作组，通常等整组结束才能再接纳 C；迭代级调度每轮完成后可以检查 EOS、移除 A，再考虑 C。Continuous Batching 指的是随生成迭代动态更新批次成员，不是简单地把所有请求放进更大的 batch。

这项思路系统化出现于 ORCA（OSDI 2022）的 iteration-level scheduling。论文还指出，如果执行引擎仅在整批结束时把控制权交还服务层，外部调度器就无法真正做到每 token 级别的成员更新。[ORCA §3]

02 · 两层循环：请求生命周期与模型迭代

先区分两个经常混淆的状态机：请求可能处于等待、Prefill、Decode、完成；而引擎每一轮按当前可运行请求组织计算。Prefill 处理已有提示，Decode 对每个活跃序列推进一个 token。ORCA 原论文称它们为 initiation 和 increment phase，不应将现代推理引擎的全部细节反向归于 ORCA。

Bt+1=(Bt∖Ft)∪At
教学化的集合表示；B 为活跃请求，F 为本轮完成请求，A 为新接纳请求，并非原论文逐字公式。

数学上集合更新很简单，系统上却受到显存、KV Cache 生存期、最大活跃请求数、排队公平性和执行引擎开销约束。一个「候选请求」即使在等待，也未必能加入，因为保存它的上下文会占用显存。

03 · 为什么还需要 Selective Batching？

不同请求的上下文长度不同；若将所有 Attention 输入强行堆成同一三维张量，可能需要 padding，也可能无法直接组合。但「不能批量算 Attention」并不意味着「整个 Transformer 都不能批量算」。

ORCA 的 Selective Batching 将 Linear、LayerNorm 等可在 token 维度合并的算子展平执行，而针对各请求独立的 Attention 保留各自的 KV 边界；论文在此使用较窄的 Attention 定义，不包含 QKV 与输出线性投影。

Xflat∈ℝ(∑i=1BLi)×H
B 为请求数，Lᵢ 是本轮第 i 个请求的 token 数，H 为 hidden size。不同请求的 Attention 仍需保持边界。

关键直觉：线性层具有大量共享参数，批量执行可以摊薄对权重的访问；Attention 的可变历史序列需要隔离计算。真正的工程实现还会考虑 kernel、padding、动态形状和数据布局，不能将这张图理解为唯一实现方式。

05 · 不要把吞吐量等同于响应流畅度

调度需要至少同时看 TTFT（从请求到达至首 token）、TBT 或 ITL（相邻输出 token 的间隔）、完成请求的端到端时延、token throughput，以及满足具体 SLO 的 goodput。后两者可能上升，而长尾请求的间隔仍然恶化。

Throughput=完成的输出 token 数观测时间（秒）
这是常见工作量归一化指标；不能据此单独推断用户可感知时延。

论文原始评测在 GPT-3 175B 的特定对照设置中报告过相对 FasterTransformer 的显著收益（同等延迟条件下最高 36.9 倍吞吐）；该结果与当时模型、硬件、基线和工作负载绑定，不能当作所有现代模型或其他框架的预期加速比。[ORCA Abstract / §6]

现代 Continuous Batching 往往与 Paged KV、Prefix Caching、Chunked Prefill 和优先级调度协同；ORCA 的核心贡献是迭代级调度加 Selective Batching，不是这些后续技术的总称。

06 · 可运行代码：只证明状态转换，不假装复现 GPU

仓库提供纯标准库 mini_batching.py 与 test_mini_batching.py。不需要 PyTorch 或 GPU；测试检查每次迭代最多让每个运行请求增加一个 token、晚到请求不会提前执行、完成请求在本轮后退出。

python -m pytest -q posts/inference/continuous-batching/test_mini_batching.py
python posts/inference/continuous-batching/mini_batching.py

示例里的 1 token/轮不表示每个 token 都耗时相同，亦不代表 GPU batch 内每条请求的算子开销相同；演示目的是隔离调度策略。

07 · 边界与后续知识

  • 代价：每轮调度和小批次带来 CPU/GPU 协调成本；收益受 batch size、序列长度分布与 GPU 内存约束影响。
  • 公平性：持续加入新请求可能导致优先级与等待时间的权衡；ORCA §4.2 讨论迭代级 FCFS，而非宣称所有调度器都采用它。
  • 当请求变长：Prefill 可能打断正在流式输出的 Decode，这正是 Sarathi-Serve 继续解决的问题。
  • 当请求共享前缀：调度顺序还影响 KV 缓存命中率，进入 SGLang / RadixAttention。
