Understanding KV Cache

为什么语言模型只生成一个新 token，却可能一遍遍读取整段对话？从一个缓存动作出发，走到 GPU 显存管理的核心。

自回归推理 · Attention阅读约 30 分钟更新 · 2026-11-20

01 · 为什么生成一个 token，还要回头看？

给定“天气今天很……”，模型生成下一个 token 时，需要关注之前所有允许访问的位置；再生成下一个 token，又要关注更长的上下文。新 token 只有一个，但过去的 token 并没有消失。 如果每一步都重新计算整个前缀，历史位置的 Key 与 Value 将被反复构造。

KV Cache 的最小思想是：在自回归、因果、模型参数固定的条件下，历史 token 在某层产生的 Key 和 Value 不会因未来 token 到来而改变。于是把它们保留下来，下一步只需计算新增位置的 Q/K/V，并让新 Query 读取缓存的历史 K/V。这是推理时的计算复用，不是改变 Attention 的定义。[Vaswani et al., 2017]

容易误解：缓存不会消除与历史 token 的 Attention 计算；新 Query 仍需和允许访问的历史 Keys 计算分数、读取 Values。缓存消除的是历史 Key/Value 的重复生成与上游重复执行。

02 · Prefill 与 Decode 是两种计算形态

一次请求通常先做 Prefill：输入已有 prompt，计算各层的 Key/Value 并初始化缓存；然后进入 Decode：每轮预测下一个 token，持续增加缓存。Prefill 有较长序列、可并行化的矩阵计算；Decode 每轮 Query 通常只有一个位置，逐步增长的历史缓存成为显存容量和带宽问题。

TTFT · Time to First Token

包含排队、Prefill 与首 token 产生等时延。长 prompt 或前缀未命中时往往更敏感。

TPOT · Time per Output Token

衡量首 token 之后输出 token 间的节奏。Decode 的访存与并发调度通常更关键。

03 · 一行 Attention 的完整数学与张量形状

设 batch 为 B，Query head 数为 Hq，KV head 数为 Hkv，每个 head 的维度为 d，当前可见长度为 T。对解码的当前层、当前步 t（此处含当前 token），新的 Q 形状为 [B,Hq,1,d]；缓存 K/V 为 [B,Hkv,T,d]。MHA 时 Hkv=Hq；GQA/MQA 需要把多个 Q heads 映射到某个 KV head。

at,i,h = softmaxi≤t ( qt,h · ki,g(h) / √d + mt,i )g(h) 为 Q head → KV head 的映射；softmax 沿允许访问的 key 位置 i 归一化；m 为可见性 mask（不可见位置为 −∞）。
ot,h = Σi≤t at,i,h vi,g(h)按 Value 的 head_dim 加权求和，得到 [B,Hq,1,d]；后续通常再做 head 拼接与输出投影。
符号物理含义为什么要留意
T当前可见 token 数缓存与单步 Attention 读取量随 T 增长
Hkv独立 KV heads决定存储，而不等于 Query heads
d每个 head 的宽度影响缓存、点积与缩放因子
mt,i因果/窗口等 mask不要重复使用不可访问的位置

以上是标准 decoder-only causal self-attention 的教学表达；Cross-Attention、Sliding Window、MLA 等架构的缓存内容与形状可能不同。

04 · 用四个 token 手工追踪缓存

考虑序列 [A, B, C, D]。Prefill 结束后，某层缓存已经拥有 A、B、C 的 K/V。下一步输入 D：先计算该层 D 对应的 Q、K、V，再读取 [KA,KB,KC,KD] 生成当前 Attention 输出；缓存长度从 3 增为 4。下一轮新的输入来自此前采样/选择的 token。

无缓存且每步重算前缀

每轮计算已见前缀的所有 Q/K/V 以及前缀内部 Attention；仅对最后位置的预测有用的历史中间结果被重复创建。

带 KV Cache 的增量解码

每轮只产生新位置各层 K/V；当前位置 Q 仍与所有可见 Keys 打分，并读取历史 Values。这改变计算调度，不改变因果约束。

对长度为 n 的纯自注意力子问题：完整前缀的 Attention 每轮有 O(n²) 项，逐轮重算累积 O(N³)；缓存增量解码每步只有 O(n) 个 Query–Key 项，累积 O(N²)。这是 Attention 子步骤的渐近计数，不是端到端推理加速倍数。 Prefill、线性层、采样和内存访问仍计入实际成本。

05 · 每个 token 要花多少显存？

若模型有 L 个都使用相同全上下文 KV 存储的 Decoder 层，每层每个 token 各存一份 K 和 V，则一个 batch 的理论原始 KV 数据量为：

MKV = 2 × L × B × T × Hkv × d × s bytess 为每个缓存元素字节数（例如 FP16/BF16 为 2）。该式不包含块元数据、填充、Allocator、Logits、权重、activation、并发结构等额外开销。

例：L=32，B=1，T=4096，d=128，s=2。若 Hkv=8，KV 为 512 MiB；若 Hkv=32，则是 2048 MiB（2 GiB）。这些是公式计算出的示意配置，不指代某一具体模型的实测显存。

交互 · 固定其他参数，只改变 KV heads

L=32 · B=1 · T=4096 · d=128 · FP16/BF16 两字节 · Hq=32

8 KV heads → 512 MiB 原始 KV；相对 MHA 减少 75%

此交互只改变显存算式；不能在推理阶段随意把已经训练好的 MHA 权重直接改成 GQA 而假定输出等价。

06 · MHA、GQA、MQA 为什么影响内存账本？

Multi-Head Attention 使用每个 Query head 自己的 KV head（典型 Hq=Hkv）。Multi-Query Attention 让多个 Query heads 共享一组 K/V；Grouped-Query Attention 将 Query heads 分成若干组，每组共享一组 K/V。[Shazeer, 2019；Ainslie et al., 2023]

更少的 KV heads 意味着更小的缓存、更少的 Decode K/V 读取字节，但不等于总延迟等比例下降。Query 相关的计算、缓存布局、Kernel、Batching 和 GPU 利用率都会影响端到端效果；GQA 通常是模型架构或训练/转换选择，而非通用的无损推理配置开关。

07 · 缓存长度不同，如何避免显存被切碎？

在线 Serving 同时处理多个长短不一的请求。给每个请求一次性预留最大长度会浪费空间，反复要求连续内存也不易管理。PagedAttention（Kwon et al., SOSP 2023） 受虚拟内存思想启发：把请求的逻辑 KV 序列分成固定大小的 token blocks，由 block table 映射到不连续的物理 KV blocks，按需分配和复用。

这样能减少为最长请求预留整段连续空间造成的浪费，并支持跨请求共享、Copy-on-Write 等内存管理能力。但固定块仍存在最后一个未填满块的内部碎片；更小的块有利于降低尾部浪费，却带来更多映射和调度元数据，具体性能依赖实现。

两个层次：KV Cache 是“缓存什么”的算法/推理策略；PagedAttention 是“怎样分配、寻址、共享这份缓存”的 Serving 内存管理方案。不能把两者当作同义词。

08 · 不同用户能复用同一段历史吗？

很多请求共享系统提示、工具定义或长文档前缀。Prefix Caching 在缓存未被回收且前缀键匹配时，复用此前计算好的完整 KV blocks，减少重复 Prefill。vLLM 的 自动前缀缓存设计 描述了按前缀及 block 信息组织缓存键与引用的机制。

命中不等于任意子串复用：要遵守 tokenization、位置编码、前缀上下文和模型状态的一致性；不同 LoRA adapter、缓存盐、模态输入或模型版本也可能影响兼容性。被驱逐的 prefix 仍需重算；匹配完整 blocks 时，不能保证任意未满尾块都同样复用。主要节省的是可复用前缀的 Prefill 工作，而不是所有 Decode 工作。

09 · 长上下文时代的四类缓存策略

  1. Sliding Window / 局部注意力：仅保留当前层可访问的窗口 K/V。只有模型层本身定义这种可见性时才能安全丢弃更老信息；混合局部/全局层要分别管理。
  2. KV Quantization：以更低位宽存储 K/V，降低容量与读取字节；量化/反量化增加开销，精度影响应在具体模型与任务上评估，不能与权重量化混为一谈。
  3. CPU/Host Offloading：把部分缓存搬出 GPU 增加可服务容量；代价是设备间传输和潜在 Decode 停顿。速度与吞吐不能仅由节省的 GPU GiB 推断。
  4. Static vs Dynamic Cache：静态预分配方便编译和固定形状，可能填充浪费；动态增长适合可变长度但需管理分配。参见 Transformers Cache Strategies。

Cache 管理还需与连续批处理、抢占/重算和延迟目标协同。对于 Sliding Window、GQA、MLA 或混合 Attention，不宜把全模型的缓存都强行套入一种统一 Hkv 和 T 的估算。

10 · 最小实现：把“复用”变成可检验的断言

下面展示的是一个 head、一个层、无位置编码、无权重矩阵的纯 Python 教学模型。它分别按每轮重算前缀与逐轮追加 Key/Value 两种方式运行，比较所有输出是否一致。它不是 Transformer 完整实现，也不能代表真实 GPU 加速或 Attention Kernel 的性能。

"""Minimal causal self-attention cache: pure Python, one head, one layer."""
from math import exp, sqrt, isclose

def softmax(xs):
    offset = max(xs)
    a = [exp(x - offset) for x in xs]
    return [x / sum(a) for x in a]

def attention(q, keys, values):
    # q,k are vectors, here with head_dim=1; values are two-dimensional.
    logits = [q * k / sqrt(1) for k in keys]
    weights = softmax(logits)
    return tuple(sum(weights[i] * values[i][j]
                     for i in range(len(keys))) for j in range(2))

def baseline(tokens):
    out = []
    for t in range(len(tokens)):
        keys = [x for x in tokens[:t+1]]  # full recompute, for illustration
        vals = [(x, -x) for x in tokens[:t+1]]
        out.append(attention(tokens[t], keys, vals))
    return out

def cached(tokens):
    keys, vals, out = [], [], []
    for x in tokens:
        keys.append(x)
        vals.append((x, -x))
        out.append(attention(x, keys, vals))
    return out

def kv_bytes(layers, batch, tokens, kv_heads, head_dim, bytes_per_elem):
    return 2 * layers * batch * tokens * kv_heads * head_dim * bytes_per_elem

if __name__ == "__main__":
    samples = [0.25, -0.6, 1.1, 0.8]
    a, b = baseline(samples), cached(samples)
    assert len(a) == len(b) == 4
    assert all(isclose(u, v, rel_tol=1e-12, abs_tol=1e-12)
               for left, right in zip(a, b)
               for u, v in zip(left, right))
    assert kv_bytes(32, 1, 4096, 8, 128, 2) == 536870912
    assert kv_bytes(32, 1, 4096, 32, 128, 2) == 2147483648
    print("PASS: cached outputs equal baseline; cache bytes verified.")

运行 python posts/inference/kv-cache/mini_kv_cache.py 会执行两个断言组：缓存与非缓存输出数值一致；示意配置的 KV 字节数分别为 536,870,912 与 2,147,483,648。查看仓库中的可执行文件。

11 · 从 Attention 到 PagedAttention：证据怎样连接？

Attention Is All You Need（2017） 给出 Transformer 的缩放点积与多头注意力；因果遮挡保证 Decoder 的位置不能读取未来位置。Fast Transformer Decoding: One Write-Head is All You Need（2019） 研究共享 K/V 的 Multi-Query Attention；GQA（2023） 在 MHA/MQA 之间引入可配置的 KV groups。

PagedAttention / vLLM（SOSP 2023） 主要讨论高吞吐 LLM Serving 面临的 KV 存储碎片、重复复制与内存管理限制，提出基于 block mapping 的 PagedAttention，并在论文指定的模型、硬件和负载上评估服务吞吐。论文中的性能结论不能未经条件迁移为“任何模型都快固定倍数”。

现代实现可参阅 vLLM Automatic Prefix Caching 与 Transformers 的缓存策略。这些是后来系统的可选实现/架构发展，不能倒写为 2017 年 Transformer 的原始工程设计。

12 · 怎么证明一项 KV 优化真的有效？

最简洁的实验不是只报“显存少了多少”，而是固定模型与精度、输入长度分布、输出长度、并发量、硬件、Kernel/框架版本与采样策略，分别测量 TTFT、TPOT、端到端吞吐（output tokens/s）、峰值 GPU 显存、KV 占用、Prefix 命中率和请求完成率。

对照必须固定主要观察
无缓存 vs KV Cache同一权重、因果可见性、输入/输出输出数值一致性、执行时间；避免将重复前缀实现当成生产基线
连续分配 vs Paged请求长度与批量分布、模型/内核碎片浪费、可容纳请求数、吞吐与开销
Prefix Cache on/off重复前缀比例、缓存容量、模型命中/驱逐、TTFT；独立后缀 TPOT
KV 量化 / Offload任务、输出、硬件互联质量变化、带宽、吞吐与尾延迟

建议分别报告冷缓存和热缓存；测 P50/P95/P99 延迟，而不是只挑最快一条请求。对部署性能的实际判断，要先确认瓶颈来自容量、带宽、计算还是排队，再选择手段。

13 · 最后，记住 KV Cache 的五个边界

  1. 它缓存的是每层先前位置的 K/V 表示，不是简单缓存完整模型输出。
  2. 它不把逐 token Decode 改成一次性并行生成，也不消灭与历史 token 的 Attention 读取。
  3. 它不自动减少全部 GPU 显存：更长序列和更大并发会使缓存更大。
  4. 它不能无条件跨模型、位置、Adapter、不同前缀或非因果依赖重用。
  5. 它与 GQA、PagedAttention、Prefix Caching 和 KV Quantization 处于不同优化层次，可组合但必须校验正确性和性能。

从这一刻起，把 KV Cache 想成一份会随 token 生长的、按层保存的历史注意力状态。模型决定需要存什么，推理引擎决定怎样放、怎样查、何时共享与回收。
