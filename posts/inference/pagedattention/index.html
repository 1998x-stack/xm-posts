Understanding PagedAttention

为什么 KV Cache 会成为 LLM Serving 的隐形瓶颈？从操作系统的分页思想，到 Block Table、写时复制和真正的 GPU 计算路径。

Kwon et al. · 2023预计阅读 30 分钟vLLM / KV Cache / GPU memory

01为什么一块 GPU 放不下足够多的请求？

模型的权重可以提前装入显存，但回答有多长，我们通常并不知道。每生成一个 token，注意力层就会增加它的 Key / Value 状态。一次请求的 KV Cache 是一条不断增长、长度不可预知的序列。

传统的连续内存预留面临两难：保留很大的连续区域，会浪费尚未使用的空间；保留很小的区域，又可能在扩容时搬迁、出现外部碎片。于是，哪怕 GPU 的算力还有余量，KV Cache 的内存管理也会限制并发请求数。Kwon 等人把这种约束作为 PagedAttention 的问题起点。[论文 §3]

核心转折：不要为不可预测的输出长度预先保留一大段连续空间；把 KV Cache 拆成固定 token 数的小块，实际增长时再申请。

02分页做了什么：逻辑顺序与物理位置分离

一条请求在语义上必须保持 token 的顺序，但显存里不必顺序摆放。PagedAttention 令每个序列的逻辑 KV 块拥有连续编号 0, 1, 2, …；运行时维护 Block Table，将逻辑块编号映射到真实显存中的物理块编号。物理块可以分散在不同地址。[论文 §4.1]

blockid(j)=table[⌊jB⌋];offset(j)=jmodB
j 是序列内的 token 位置；B 是每个 KV 块容纳的 token 数；table 的元素是物理块编号。实际 kernel 还需要根据层、KV head、数据布局计算地址。

这个映射有意借鉴操作系统的页表，但不是 CUDA 的 thread block，更不等于操作系统直接管理的 CPU 虚拟页。它是在推理运行时与注意力 kernel 之间建立的 KV 逻辑块到物理块 的管理抽象。

03走完一次 Decode：什么时候真正分配新块？

考虑块大小 B = 4。初始 10 个 token 占据三个逻辑块；前两块各 4 个，第三块仅 2 个。后续生成先填充第三块的剩余位置，只有长度从 12 变成 13 时才需要第四块。[论文 §4.3]

Nblocks=⌈LB⌉;Wtail=NblocksB−L
对长度 L > 0 的独立序列，尾部浪费满足 0 ≤ Wtail < B 个 token 容量；不包括块表、分配器和后端布局开销，也不等于所有系统配置的总浪费。

这就是论文所说接近零的 KV 内存浪费的机制来源：主要按需使用物理块，而不是预定最坏的输出长度。“接近零”不意味着严格零开销。

04它没有改变 Attention 的数学

对一个 decoder layer、一个 query head 来说，PagedAttention 仍需读取可见历史 token 的 K、V，并计算缩放点积与 softmax。变化的是缓存寻址方式：在用 K/V 参与计算之前，先通过逻辑块编号取回真实的物理块地址。

Attention(q,K,V)=softmax((qKᵀdh)+mask)V
q ∈ ℝdh；K,V ∈ ℝL×dh（单头视图）；softmax 沿历史 key 的长度 L 归一化。causal mask 遮挡不可见位置；块尾未写入的 slot 不能参与归一化。

缓存以模型全部层和 KV heads 计算时，一 token 的理论 KV 存储量是：

MKV/token=2×Nlayers×Hkv×dh×bytes
2 对应 K 和 V，Hkv 是 KV heads 数，不一定等于 Q heads 数；GQA/MQA 可以降低容量但不改变分页映射的主旨。未计量化元数据、对齐和其他运行时开销。

例如一个纯教学配置：32 层、8 个 KV heads、head_dim 128、每元素 2 字节，则每 token 约 128 KiB。缓存 4096 token 的理论大小为 512 MiB / 请求；这是依公式推导的容量，不是论文的实测 benchmark。

05共享与写时复制：同一前缀可以用多少份 KV？

一段 prompt 产生多个候选答案时，其公共前缀完全相同。若每个候选都复制全部前缀 KV，会额外占用显存。论文采用共享物理块并追踪引用计数：多个逻辑块表可以指向相同物理块；当分支准备修改仍被共享的块时，先执行 Copy-on-Write（写时复制）。[论文 §4.4]

共享不等于全局缓存

论文重点讨论并行采样、beam search 等解码分支的块共享，以及可复用前缀。共享需要相同语义上下文和兼容的计算状态。

现代 Automatic Prefix Caching

vLLM 后续使用带前缀语义的哈希建立跨请求的 KV block 复用和驱逐策略。这属于扩展实现，不应写成 2023 年原论文已完整具备的同一套策略。

06从 Prefill 到 Decode：谁分配、谁调度、谁读取？

Prefill

处理输入 prompt；按其长度申请所需 KV 块，计算并写入各层 K/V。Prompt 长度可知，生成长度通常不可预先精确知道。

Decode

每次迭代为活跃序列产生新 token，并按需增长 KV；调度器管理可并发推进的请求，块管理器维护映射与引用计数。

Pressure

可用物理块不足时，运行时需要预占、换出或重算等决策；原论文描述了 swapping 与 recomputation 的权衡。单靠分页不会凭空创造显存。

Release

请求完成、取消或不再需要时减少块引用计数；引用归零的物理块可回收到空闲池供其他请求使用。

这解释了为何 PagedAttention 的价值不是“单个矩阵乘法更快”：它降低 KV Cache 浪费，使高负载服务有机会在同一时刻维持更多请求，由系统吞吐获得收益。论文把内存管理与 iteration-level scheduling、GPU kernel 协同设计。[论文 §4–§5]

07Kernel 层：为什么非连续 KV 仍然能算注意力？

注意力 kernel 不能假设历史 K/V 是一条连续数组。它遍历逻辑 token 或逻辑块，先使用 block_table 得到对应物理块，再按布局地址加载 K/V。完成点积、数值稳定的 softmax 归一化，最后累积 value。数学上聚合的仍是完整可见历史。[vLLM 官方 kernel 解读]

# 机制伪代码：不代表 vLLM CUDA/Triton 的具体循环与指令
for token_idx in range(context_len):
    logical = token_idx // block_size
    physical = block_table[logical]
    slot = token_idx % block_size
    key, value = read_kv(physical, slot)  # 还需 layer/head/layout
    score = dot(query, key) * scale
    update_stable_softmax_and_value(score, value)

与 FlashAttention 不同：FlashAttention 的经典关注点是 Attention 算子内的 IO-aware tiling 和中间矩阵开销；PagedAttention 的核心是 Serving 中持久化 KV Cache 的物理组织与复用。两者可以共同作用，但不是可以互换的同一个算法。

08交互实验：块越大就越好吗？

对于给定 token 长度，较小块通常降低尾块内部碎片，但块数更多；较大块减少块表项，却可能浪费更多尾部容量。实际最优值还取决于访存合并、kernel 并行度、共享命中与请求长度分布。下面改变 B 和 L，只计算理论容量，不模拟 GPU 时延。

容量模拟器

选择每块 token 数，再拖动序列长度。下方的物理块填充状态与尾部浪费会实时变化。

默认：19 tokens / 3 blocks；运行交互可观察布局

L = 19，B = 8 → 3 块、24 槽、5 个尾部空槽，空槽率 20.8%。

注意指标边界：模拟器的“空槽率”是 (分配槽数 − 有效 token 数) / 分配槽数；不是 GPU 实测内存占用率、吞吐、延迟，也没有模拟共享引用计数或元数据。

09可执行的最小 Block Manager

与其抄写生产内核，不如先验证最小不变量：逻辑顺序与物理编号解耦、块大小正确、分支共享引用计数、写入共享块触发 copy-on-write、释放后无悬空引用。仓库提供 mini_paged_cache.py，只用 Python 标准库即可运行：

python posts/inference/pagedattention/mini_paged_cache.py
python -m pytest -q tests/test_pagedattention.py

代码只模拟 KV block 的逻辑存储，不计算 Q/K/V 矩阵，也不复现论文的端到端吞吐实验。通过可执行的断言理解 paging、CoW 的正确性，再去读具体 vLLM backend 的 kernel 更不易迷路。

10论文实验究竟证明了什么？

论文对在线请求到达条件下的模型 Serving 做实验，对比 FasterTransformer 与不同 Orca 实现，测量吞吐与延迟，并评估 block size、kernel overhead 与内存管理策略。具体结论必须连同模型、工作负载及基线理解。

观察论文定位可支持的结论 / 边界
整体 Serving 吞吐约 2–4×摘要；§6 / Fig. 12–14（参见正式版本具体图号）相对论文设定的基线与相近延迟区间；不能推广为任意 GPU、任意模型的固定倍数。
ShareGPT basic sampling 的容量收益§6.2 / Fig. 12–13以 OPT-13B / 66B / 175B 为代表的原始评测中，vLLM 在相近延迟下可承受的请求到达率相对 Orca (Oracle) 为 1.7–2.7×（ShareGPT 配置范围）；该指标是服务请求率，不是单 token 运算加速。
共享的实际节省§6.3 / Fig. 15Alpaca trace 下，并行采样共享节省 6.1–9.8% KV blocks，beam search 节省 37.6–55.2%；具体取决于候选数量与序列长度。
PagedAttention 内核存在额外延迟§7.1 / Fig. 18(a)文中对比高度优化的 FasterTransformer attention kernel，报告约 20–26% 的 attention kernel latency overhead；整体吞吐仍可因 batch 容量改善而提高。
Block size 存在权衡§7.2 / Fig. 18(b)论文中的 ShareGPT / Alpaca traces 下，较大的 block 对短序列可能不利；原系统采用 16 tokens 作为默认块大小，并非现代所有 backend 的永恒固定值。
重算与换出皆有代价§7.3 / Fig. 19小块换出时可能遇到大量小型传输；重算与换出的选取需要考虑块大小及传输成本。

实验以 ShareGPT / Alpaca 的 token 长度分布构造负载，并用 Poisson 过程模拟到达时间；主要指标为每请求端到端延迟除以该请求输出 token 数后的 normalized latency。对照组 Orca (Oracle) 假设预先知道真实输出长度，因此它是论文构造的理想化上界，并非可直接部署的真实预言器。[论文 §6.1]

论文报告的收益属于 系统层（vLLM + PagedAttention + 管理与调度），不是只改一行索引或只换一种 Attention kernel 就必然得到 2–4× 的证明。[SOSP 2023 正式论文]

11代价、边界与今天的实现

带来的能力

按需分配、减少连续预留造成的浪费、通过块表共享前缀及写时复制、给在线动态 batching 留出更多 KV 内存空间。

不能自动解决

显存带宽、模型权重、算子计算量、scheduler 公平性、长序列的二次 attention 工作量、不同 KV dtype 与布局限制。

还要把历史设计和现代工程版本拆开看：vLLM V1、Automatic Prefix Caching、各类注意力后端、GQA/MQA、FP8 KV Cache 等会影响当前的布局与块生命周期，不能直接从 2023 论文逆推出 2026 最新实现。要复现当前系统，请以所安装版本的 vLLM 文档 与对应 Git commit 为准。

论文 §8 也明确提醒：类似分页内存管理适用于动态增长、内存容量受限的场景；对静态大小或主要计算受限的 workload，额外间接寻址可能得不偿失。

12把整条因果链记住

Problem

生成长度未知 → 连续 KV 预留产生碎片与浪费 → 限制可同时运行的序列数。

Mechanism

逻辑块 + 物理块 + Block Table → 按需申请与离散存放；引用计数 + CoW → 安全共享。

System

内存管理、调度与分页注意力 kernel 协同运行 → 在内存受限条件下提高有效 batch 占用。

Evidence

SOSP 2023 的系统实验支持其吞吐收益，同时测出 kernel 开销；真实收益取决于模型与请求分布。
