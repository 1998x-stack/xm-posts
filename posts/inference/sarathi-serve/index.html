Sarathi-Serve：为什么要把 Prefill 切成小块？

从吞吐与尾延迟的拉扯出发，推导 token budget、Decode 优先的混合批次，以及 Chunked Prefill 的真实代价。

Serving Scheduler / Tail Latency · 研究生技术精读 · 阅读约 26 分钟 · 2026-11-21

01 · 流式聊天为什么会突然停一下？

两个用户的回答已经在逐 token 流出，这时进来一条数千 token 的长文总结请求。若调度器直接执行一次完整 Prefill，原本轻量的 Decode 可能遭遇明显的 token 间隔尖峰。

LLM Serving 的两个工作阶段有不同特征：Prefill 对整段提示执行并行计算，倾向于更高算力利用；Decode 每次每条请求生成一个 token，常受权重/KV 访存影响。把大 Prefill 与 Decode 粗暴地串行交错，会在 TTFT 与 TBT 之间形成调度冲突。[Sarathi-Serve §2–§3]

02 · 从 Orca 到 Sarathi：一步还不够细

ORCA 的 iteration-level scheduling 每轮重新挑选批次，解决早结束和晚加入的问题；但这一轮里如果混入一整份很长的 Prefill，正在执行的 Decode 仍可能被拖住。Sarathi-Serve 的核心不是推翻连续批处理，而是控制每轮处理的 Prefill 工作量。

原论文比较 decode-prioritizing 的请求级方式，与 prefill-prioritizing 的迭代级方式，指出前者会让新请求等待，后者则可能造成已在流式生成的请求出现长时停顿。Sarathi 以 chunked-prefill 与 stall-free hybrid batching 寻求折中。

这里的「stall-free」是论文对其调度目标与实验现象的用语；不意味着现实系统在任意负载、任意硬件下都保证零排队或零延迟尖峰。

03 · 核心规则：先 Decode，再填一个 Prefill Chunk

每轮先为当前仍需输出 token 的 Decode 任务预留位置，再让正在进行或新加入的 Prefill 使用剩余预算。这样 Decode 不会仅因一整个超长 Prefill 被作为一个不可切分操作而无限延后。

ndecode+nprefill≤τ
τ 是每迭代最多处理的 token 数；每个持续 Decode 请求在此示例里占一个 token。真正的调度还须受 KV 可分配量等条件制约。
c=min(r,τ−ndecode)
r 是一个候选请求尚未完成的 Prefill token 数；忽略其他已预留 prefill 和显存限制时成立。

注意每个 chunk 在自回归因果 Attention 中必须读取前面 chunk 留下的 KV，避免丢掉上下文；但分块意味着重复的历史 KV 读取、更多调度/启动开销。**算法降低干扰，不会凭空消除算力和显存代价**。[§4.1–§4.3]

04 · 如何从 SLO 推回 token budget？

Token budget 不是纯理论常数。论文方法是根据模型和硬件对不同 token 数的 hybrid batch 做 profile，在 TBT 服务等级目标约束下，选取允许的最大可用预算，同时考虑分块过细带来的 prefill 额外开销。

τ*=maxτ{τ:T(τ)≤SLOTBT}
用于阐释 §4.3 的 profiling 选择方法；T(τ) 要在具体硬件、批次构成与模型上测定，不能用 token 数直接换算真实秒数。

当模型采用 pipeline parallelism，批次工作量忽大忽小还会造成 pipeline bubbles。论文指出控制每轮的工作量分布能够减小这种不平衡；但多机互连与张量/流水线并行策略也会改变综合收益。

06 · TTFT、TBT、Capacity：该如何读评测？

TTFT 从请求到达到首 token；TBT/ITL 是连续输出 token 的间隔；Capacity 只有连同延迟 SLO 和工作负载一起定义才有意义。只报最大吞吐容易掩盖流式体验变差。

论文 OSDI 2024 摘要给出特定配置中的相对 serving capacity 提升：Mistral-7B 在单 A100 上相对 vLLM 为 2.6 倍，Yi-34B 在双 A100 上最高 3.7 倍，Falcon-180B 采用流水线并行时最高 5.6 倍。这些数字取决于 workload、显卡、对比实现和尾延迟约束，并非对一切部署有普适保证。[Abstract; §5]

论文 Table 4 还分别消融 chunked prefill 与 hybrid batching：单有混合批次会放大 TBT，单有 chunking 会增加 TTFT；组合起来改善折中。准确复现这些结论需要对应模型、追踪样本与 SLO，而不能用下方玩具代码生成与论文相同的曲线。

避免把 TBT 和 TPOT 一概混为同一统计口径：TPOT 常用于扣除首 token 后平均输出 token 耗时，TBT 可看每个相邻 token 的间隔，尾部分位数尤其重要。

08 · 适用边界与下一步

  • 前提：需要正确保存跨 chunk KV，并正确处理位置编码/Attention mask；不能把多个 chunk 当作互不相关的提示。
  • 内存：已有 KV Cache 和新增 chunk 在统一内存预算内竞争；若发生 OOM，token budget 仍需结合 admission/preemption 管理。
  • 不应混淆：Continuous Batching 是逐轮更新参与请求；Sarathi 是逐轮控制计算量。
  • 后续：DistServe、Splitwise 等将 Prefill/Decode 放到不同实例处理，需要引入 KV 迁移带宽和跨池调度分析，不能把它们视为简单 chunking 的同义词。
  • 可叠加：RadixAttention 可以消减重复 Prefill，Sarathi 可以控制剩余 Prefill 的每轮干扰。
