Understanding
Tree of Thoughts

当模型走错第一步时，为什么不能停下来换一条路？从线性生成到显式搜索，理解大语言模型如何提出候选思维、评估中间状态、保留希望最大的分支，并在必要时回溯。

01 · 从一道题理解问题：第一步走错，后面再努力也没用

先不要把 Tree of Thoughts 想成一套复杂的提示词。我们先看一道看似简单、却很容易让语言模型走进死胡同的题目。

给定四个数字 4、9、10、13，每个数字必须且只能使用一次，只允许使用加、减、乘、除和括号，最终得到 24。一个有效解是：

(13−9)×(10−4)=24

把这个答案拆成三次可验证的中间操作：

第 1 步：13 − 9 = 4，剩余数字变成 {4, 4, 10}。

第 2 步：10 − 4 = 6，剩余数字变成 {4, 6}。

第 3 步：4 × 6 = 24，得到目标。

关键在于：第一步并不唯一。模型也可能先生成 4 + 9 = 13、10 − 4 = 6、13 − 10 = 3 等候选操作。它们都像是合理的局部动作，但只有部分分支能在后续步骤中到达 24。

如果模型一开始只沿着一条链生成，错误的早期选择会不断影响后续输出。传统 CoT 可以让模型把步骤写出来，却没有默认提供一个独立的机制来保留其他分支、比较它们的前景，再回到先前的分叉点。

先记住一句话：ToT 不只是要求模型「多想几遍」，而是把中间推理状态显式保存下来，并让搜索策略决定下一步探索哪里。

02 · 从 CoT 到 ToT：真正改变的是推理过程的组织方式

要理解 ToT，需要先区分三种常被混在一起的操作：沿一条路径继续生成、生成多条完整路径后投票、在中间步骤就分支并评估。

2.1 Chain-of-Thought：把答案拆成步骤，但通常仍是一条链

CoT 将复杂问题的回答分解成若干连续的中间思维。设输入为 x，中间步骤为 z₁,…,zₜ，最终答案为 y。模型按条件上下文逐步生成：

p(zt|x,z1:t−1),p(y|x,z1:T)

这不是说 CoT 不能产生多种可能，而是说一次采样通常只沿着已经生成的前缀继续向前。生成了错误的中间式后，后面的 token 需要在这个错误上下文里继续工作。

2.2 Self-Consistency：多条完整链，最后汇总答案

Self-Consistency 从同一个问题采样 k 条推理链，然后按最终答案进行边缘化或多数投票。它让模型有机会通过不同路径到达答案，但通常不会在每条链的中间状态上进行显式的局部比较和回溯。

例如，100 条 CoT 样本可能有 37 条回答 24、29 条回答 18、34 条回答 20。Self-Consistency 可以用票数选出 24；但它并没有天然告诉我们「哪一个第一步最值得继续扩展」。

2.3 Tree of Thoughts：让搜索发生在中间状态

ToT 把推理单元从 token 或整条回答提升为有语义的 thought。每个 thought 是当前问题的一段中间解；多个 thought 连接成状态树。系统可以在某个深度同时保留多个候选状态，对它们评分，再选择哪些状态继续生成。

概念边界：ToT 是一种组织 LLM 推理与搜索的框架，不是新的 Transformer 网络层，也不意味着模型参数被重新训练。原论文使用现成语言模型，通过推理时的生成、评估和搜索流程增强问题求解。

03 · 形式化：什么是 Thought、State、Value 和 Search？

论文把问题求解写成一棵搜索树。输入问题记作 x；已经生成的中间思维序列记作 z₁,…,zₜ。一个节点不是单独的一句话，而是当前问题及到目前为止的部分解：

st=[x,z1:t]

在 Game of 24 中，状态可以包含「已经使用的算式」以及「尚未使用的数字」。在填字游戏中，状态可以包含已经填入的单词和由此产生的字母约束。在创意写作中，状态可以是一个段落规划。

因此，thought 的粒度必须跟任务结构匹配：太大，模型很难生成多样候选；太小，评估器又无法判断它对最终目标有没有帮助。

概念含义Game of 24 例子
Input x原始任务4、9、10、13，目标 24
Thought z一个有意义的中间步骤13 − 9 = 4
State s输入与历史步骤组成的部分解已做 13 − 9 = 4，剩余 {4,4,10}
Generator G根据状态提出下一步候选提议 10 − 4、4 + 10 等
Evaluator V估计状态继续求解的前景sure / maybe / impossible
Search A决定保留和扩展哪些状态BFS 保留前 b 个状态

用函数表示，思维生成器接收模型、当前状态和候选数量，返回下一步候选；状态评估器则为一个或多个候选状态提供价值判断：

G(pθ,s,k)→{z1:k},V(pθ,S)→vs

这里的 V 不一定是训练好的价值网络。原论文使用语言模型本身，通过专门的提示词来评估状态；可以逐个独立评分，也可以把多个状态放在一起，让模型进行比较和投票。

04 · 四个设计模块：如何把一个任务变成可搜索的问题？

4.1 Thought Decomposition：先确定每个节点代表什么

不同任务的 thought 粒度不同。Game of 24 的 thought 是一行算式；Mini Crosswords 的 thought 是某个线索的候选单词；Creative Writing 的 thought 则是一段写作规划。论文的一个重要设计原则是：thought 既要小到足以生成多样候选，也要大到足以评估它的前景。

4.2 Thought Generation：提出候选，而不是只续写一个答案

论文讨论了两种生成方式。第一种是 sample：从当前状态独立采样多个 thought，适合创意空间较丰富的任务。第二种是 propose：在同一上下文里让模型连续提出不同候选，适合算式或单词这种结构受限、容易重复的任务。

Sample

给定一个写作任务，独立采样 Plan A、Plan B、Plan C。多样性是主要目标。

Propose

给定剩余数字，连续提出多个下一步算式。候选之间共享上下文，减少重复。

4.3 State Evaluation：判断「这条路还有没有希望」

评估器不是简单判断当前步骤是否正确。它要估计的是：从当前部分解继续向前，是否仍然可能达到目标？ 原论文用两类策略：独立价值评估（如 sure / maybe / impossible 或数值评分），以及在多个状态之间进行投票。

4.4 Search Algorithm：把生成和评估变成真正的控制流

如果只有生成和评分，没有搜索策略，系统仍不知道什么时候扩展、什么时候保留、什么时候停止。原论文实现了 BFS 与 DFS；后续系统可以换成 Beam Search、A* 或 MCTS，但不能把这些算法都误称为原论文的默认实现。

05 · Game of 24：逐步走查一棵思维树

我们用前面的数字说明搜索器实际做了什么。根状态是 {4, 9, 10, 13}。生成器提出多个第一步；评估器根据「剩余数字是否仍有机会凑成 24」给出启发式判断。

第一层候选中，13 − 9 = 4 会得到 {4,4,10}。这是一个可继续探索的状态：10 − 4 = 6 后，剩下 {4,6}，下一步即可相乘得到 24。其他候选不一定立刻错误，但可能需要更多步骤、价值较低，或被评估为不可能。

注意，评估器输出的 sure / maybe / impossible 是启发式，不是数学证明。一个模型可能低估一条实际可行的分支，也可能高估一条最终走不通的分支。真实系统应尽可能把确定性约束交给代码或外部验证器。

把论文算法映射到这个例子

阶段ToT 动作状态变化
Generate提出第一步候选根状态展开为多个子状态
Evaluate评估候选可行性给每个状态分配 sure / maybe / impossible
Select按价值保留候选将前 b 个状态放入下一轮 frontier

06 · 交互：切换 BFS、DFS 与回溯视角

下面是一个固定教学轨迹，不会调用外部模型。它帮助你观察：BFS 为什么逐层保留状态，DFS 为什么可以快速深入，以及遇到死路时为什么需要回溯。

BFS：在同一深度比较多个候选

根状态 {4,9,10,13} 先生成若干第一步。评估器比较候选状态，搜索器保留前 b 个，而不是只相信第一个生成结果。

当前 frontier： {13−9=4}、{4+9=13}、{10−4=6} …

切换按钮会更新上方状态说明。静态默认内容同样描述了一个完整可理解的搜索场景。

07 · BFS、Beam Search 与 DFS：搜索策略如何改变探索顺序？

7.1 BFS：让同一深度的候选公平竞争

令 Sₜ₋₁ 为上一层保留的状态集合。每个状态生成候选后，得到新候选集合 S′ₜ；评估器为它们打分，再保留价值最高的 b 个：

St=Topb(S′t,V)

当 b=1 时，系统每层只保留一个最优状态，容易退化成贪心搜索；当 b 增大时，更多替代路径可以活下来，但生成和评估成本也随之增加。论文 Game of 24 和 Creative Writing 使用 BFS；Game of 24 的宽度 b=5。

7.2 DFS：沿着最有希望的路线深入，失败后回头

DFS 会先对候选排序，然后沿最有希望的状态递归深入。如果状态评估低于阈值，或者已经达到终止深度，就停止当前分支，并回到父状态探索下一个候选。这种机制特别适合深度不固定、局部约束会逐步收紧的任务。

7.3 Beam Search 是不是 ToT？

不完全是。Beam Search 是一种搜索策略：每层保留分数最高的 b 个部分序列。ToT 是更上层的框架，规定了 thought 的语义粒度、候选生成、状态评估和搜索控制。ToT 可以采用 beam-like 的宽度截断，但不能把框架本身等同于 Beam Search。

08 · 状态评估与剪枝风险：模型自己给自己打分，可靠吗？

ToT 的评估器可以采用独立打分或候选投票。独立打分时，模型判断一个状态是否有希望；投票时，模型比较一组状态并选择更值得探索的一个。前者适合有明显可行性线索的任务，后者适合很难定义绝对分数、但能相对比较质量的任务。

独立价值评估

问题：从这个状态继续走，能否达到目标？

suremaybeimpossible

适合有明确约束或可进行短程 lookahead 的任务。

跨状态投票

问题：当前这几个候选里，哪个更值得继续？

候选 A候选 B候选 C

适合开放式任务，例如比较多个写作规划的连贯性。

一个常见误区是把 LLM 评估分数当作客观概率。比如模型给某状态打 8 分，不代表它有 80% 的成功概率；不同任务、不同 prompt、不同深度的分数未必可比。它首先是搜索启发式，而不是经过校准的概率模型。

剪枝尤其危险：一旦把正确路径误判为 impossible，后续就再也没有机会发现它。原论文的 Mini Crosswords 实验中，某些实际可行的词会被模型误判为不可能；移除剪枝虽然能找回部分正确状态，但整体表现反而下降。这说明评估器既不能过度乐观，也不能过度自信地剪枝。

工程建议：把「能否满足硬约束」和「哪条路线更有希望」拆开。前者优先交给程序、约束求解器、测试或环境反馈；后者再由 LLM 提供语义启发式。硬约束验证不应完全依赖同一个生成模型的自我评价。

09 · 三类任务的原论文证据：ToT 不只会解算术题

论文在 NeurIPS 2023 使用 GPT-4 Chat Completion，默认温度为 0.7，实验时间为 2023 年 5 月 5 日至 16 日。下面的结果属于论文历史实验设置，不代表当前模型的性能，也不是本次重新运行得到的数据。

9.1 Game of 24：中间步骤的分支比盲目采样更重要

论文从 4nums.com 的 1,362 道题中选取按人类求解时间排序的第 901–1000 道较难题目，共 100 道。成功的定义非常严格：必须得到一个等于 24 的有效算式，并且四个输入数字各使用一次。ToT 在每个节点生成候选算式，使用 sure / maybe / impossible 评估，BFS 每层保留 b=5 个状态，并对每个候选进行三次价值采样。

结果显示，ToT b=1 为 45%，b=5 为 74%。CoT Best-of-100 为 49%，而 CoT-SC（100 条路径多数投票）为 9%。要注意 Best-of-100 是 oracle 风格的事后最优上界比较，不是普通部署时可直接获得的答案选择器；它与多数投票也不是同一个指标。

错误分析发现，约 60% 的 CoT 样本在生成第一步后就已经失败，说明问题不只是最终答案格式错误，而是早期思维步骤把后续搜索空间压缩到了不利区域。

9.2 Creative Writing：先选规划，再选最终文本

创意写作任务要求生成四段连贯文本，每段分别以给定句子结尾。ToT 先生成五个写作计划并投票选出一个，再基于该计划生成五篇文本并再次投票。自动连贯性评分中，ToT 平均为 7.56，IO 为 6.19，CoT 为 6.93（满分 10）。人工比较中，100 对样本里有 41 对更偏好 ToT，21 对更偏好 CoT，38 对认为二者相近。这里说明的是论文所设任务上的偏好结果，不等于通用写作质量的普遍提升。

9.3 Mini Crosswords：DFS、约束传播和回溯

Mini Crosswords 是 5×5 的填字任务，包含 10 条横纵线索。ToT 使用 DFS，逐步填词，并把已填字母转化为其他线索的约束；如果某个剩余线索被判断为无法填入，就剪掉当前子树并回溯。论文报告 ToT 的字母级正确率为 78%，词级正确率为 60%，完整游戏成功率为 20%（4/20）；IO 与 CoT 的词级成功率分别为 14% 和 15.6%，完整游戏均仅解决 0 或 1 题。

这个实验也暴露出评估器的缺点：模型可能把罕见或过时词汇误判为拼写错误，导致错误剪枝。使用 oracle best state 时，完整解题可达 7/20；去掉剪枝时完整解题率反而下降至 5%。因此搜索效果不仅取决于候选数量，也取决于评估器是否保留了真正可行的路径。

10 · 与 CoT、Self-Consistency、MCTS、RAP、ReAct 的边界

方法核心搜索/控制对象主要机制与 ToT 的关系
CoT一条中间推理链按上下文连续生成 thoughtToT 可以把它看作宽度为 1 的受限情形
Self-Consistency多条完整推理路径采样后聚合最终答案有多样性，但通常没有中间状态搜索
ToT部分解构成的状态树候选生成、状态评估、搜索和回溯本篇核心框架
MCTS决策树节点与访问统计选择、扩展、模拟、回传；平衡探索与利用可作为更高级的搜索策略，但不是原论文的默认算法
RAP推理路径与世界状态LLM 同时承担世界模型与推理代理，结合 MCTS与 ToT 同属测试时规划方向，但引入更明确的世界模型/奖励规划
ReActThought、Action、Observation 轨迹推理与外部工具/环境行动交替重点是与环境交互，不等同于离线思维树搜索

一个很重要的历史细节：ToT 原论文在搜索算法部分明确将 A* 和 MCTS 列为后续可探索方向，而论文实际使用的是 BFS 与 DFS。2023 年的 RAP（Reasoning via Planning）则将 LLM 同时作为 world model 与 reasoning agent，并结合 MCTS 做战略搜索。不要把后续 RAP 的 MCTS 设计倒灌成 ToT 原论文的实现。

同样，ReAct 主要让模型在 Thought 与 Action 之间交替，通过工具或环境观察更新计划；ToT 的重点是对部分解进行分支搜索。真实 Agent 可以把两者结合：在一个规划节点中调用工具获得 observation，再把观察写入新状态，继续搜索。

11 · 成本、预算与工程实现：搜索越宽，账单也可能越大

ToT 把更多计算从训练阶段转移到了推理阶段。对每个状态，系统可能要生成 k 个候选；然后还要对候选进行评估，必要时重复采样以减少评分噪声。因此不能只看成功率，也要统计 token、模型调用、延迟和验证成本。

11.1 一个粗略的搜索规模估计

设最大深度为 T、每个状态生成 k 个候选、BFS 每层保留 b 个状态。若不做剪枝，完整树的节点数随深度呈指数增长；有宽度限制时，候选生成量大致被限制在 O(Tbk) 量级（首层和终止层会有边界差异）。这只是节点规模估计，不等于 API 请求次数，因为一个 prompt 可以返回多个候选，多个状态也可以批量评估。

Ncandidate≈T·b·k

若每个候选状态评估 r 次，评分样本量还会近似按 r 倍增加。实际成本取决于 prompt 长度、上下文重复、批处理、缓存、候选去重、停止条件，以及生成器和评估器是否使用同一模型。

11.2 工程系统建议拆成六个部件

Task Adapter：定义状态、目标、硬约束与终止条件。

Thought Generator：从当前状态生成候选，控制多样性与候选数量。

State Evaluator：评估候选状态，可结合 LLM、规则、执行结果和外部模型。

Search Controller：管理 frontier、深度、beam width、阈值与回溯栈。

Verifier：独立检查最终结果是否满足硬约束。

Trace & Budget Manager：记录状态树、模型调用、token、耗时和剪枝原因。

11.3 一个稳健的停止条件

不要只靠「模型说已经完成」。更可靠的策略是：达到最大深度、预算耗尽、目标被外部验证器确认、frontier 为空，或连续多轮没有产生有价值的新状态时停止。对于高风险行动，最终动作还应经过权限、约束和人工确认。

12 · 可执行的精确算术核验：让硬约束不再只靠模型自评

下面的 Python 示例是一个独立的教学辅助程序：用 Fraction 做精确有理数运算，枚举四个数字的配对和四则运算，找到一个合法的 24 点表达式。它不是原论文的 LLM ToT 复现，也不使用 GPT-4；它展示的是如何把确定性算术验证从语言模型中分离出来。

from fractions import Fraction
from itertools import combinations


def solve_game24(numbers):
    if len(numbers) != 4:
        raise ValueError("Game of 24 expects exactly four numbers")

    items = [(Fraction(n), str(n)) for n in numbers]

    def search(state):
        if len(state) == 1:
            value, expression = state[0]
            return [] if value == 24 else None

        for i, j in combinations(range(len(state)), 2):
            a, expr_a = state[i]
            b, expr_b = state[j]
            rest = [v for k, v in enumerate(state) if k not in (i, j)]

            candidates = [
                (a + b, f"({expr_a} + {expr_b})"),
                (a - b, f"({expr_a} - {expr_b})"),
                (b - a, f"({expr_b} - {expr_a})"),
                (a * b, f"({expr_a} * {expr_b})"),
            ]
            if b != 0:
                candidates.append((a / b, f"({expr_a} / {expr_b})"))
            if a != 0:
                candidates.append((b / a, f"({expr_b} / {expr_a})"))

            for value, expression in candidates:
                result = search(rest + [(value, expression)])
                if result is not None:
                    return [expression] + result

        return None

    return search(items)


if __name__ == "__main__":
    answer = solve_game24([4, 9, 10, 13])
    print(answer[-1] if answer else "No solution found")

这个小程序的价值不是「让搜索替代 LLM」，而是演示一种混合系统思路：模型可以负责提出有意义的候选思维，程序负责检查数字是否重复使用、运算是否合法、最终值是否精确等硬约束。对于可形式化的任务，确定性验证器通常比让模型自己判断更可靠。

仓库同时提供独立测试，验证样例可解、无解输入返回 None，以及精确算术不会把浮点误差当成成功。测试通过只说明这个小型算术程序满足断言，不代表复现了论文的 74% 指标。

13 · 局限与改进方向：树越大不代表推理越聪明

13.1 评估器会犯错，错误剪枝不可逆

若模型把正确分支判为不可能，搜索器可能永远不会访问它。可以用更保守的剪枝阈值、延迟剪枝、保留少量低分探索槽位，以及外部约束验证来降低风险。

13.2 状态之间可能高度重复

不同 thought 文本可能表达同一个实际状态。没有状态规范化和去重时，搜索预算会被近似重复的节点浪费。对算术、代码、规划任务，可以把结构化状态做 canonicalization；对自然语言任务，则需要语义相似度或任务特定的去重规则。

13.3 评价分数未必可跨深度比较

一个浅层状态的 8 分和深层状态的 8 分不一定意味着相同成功概率。可采用深度条件化评分、成对比较、校准集、多个评估器集成，或将模型评价与可验证的环境反馈结合。

13.4 计算预算需要动态分配

不是每个状态都值得生成相同数量的候选。对不确定性高、潜在价值大的节点分配更多样本；对明显不可行或重复的节点尽早停止。可以把候选多样性、评估方差、剩余深度和调用成本纳入预算控制。

13.5 搜索成功不等于现实行动安全

ToT 的可读状态树有助于审查，但并不能自动保证事实正确、目标合理或行动安全。接入浏览器、代码执行、支付或现实环境时，需要独立权限控制、工具沙箱、动作验证和必要的人工确认。

研究启发：ToT 最有价值的遗产之一，是把「推理质量」从单条生成文本，扩展为生成策略、状态表示、价值估计、搜索控制和验证器共同决定的系统问题。后续研究不应只追求更宽的树，还要研究更可信的状态、校准的评估和更经济的搜索。

14 · 总结：用五句话记住 Tree of Thoughts

1. CoT 让模型沿着一条中间推理链继续生成。

2. Self-Consistency 采样多条完整链，再聚合答案。

3. ToT 把中间 thought 组织成状态树，在生成过程中进行评估和搜索。

4. BFS 适合有限深度、可以逐层比较的任务；DFS 适合深度不定、约束逐渐收紧且需要回溯的任务。

5. ToT 用额外推理预算换取搜索能力；评估器误差、剪枝风险和调用成本必须一起设计。
