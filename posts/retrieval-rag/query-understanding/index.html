Understanding Query Understanding

用户说出的句子，不等于系统真正需要解决的问题。Query Understanding 负责把自然语言中的意图、实体、约束和上下文，转换为机器能够检索、比较或安全路由的语义表示。

研究生专题约 32 分钟经典 IR → LLM Search → Agent更新于 2026-11-21

01 · 为什么“看懂关键词”仍然不等于理解用户？

先看一个真实系统很容易遇到的请求：

用户： Find recent papers about efficient LLM inference, especially methods that reduce KV cache memory.

如果系统只做关键词匹配，它可能提取出 recent、LLM inference、KV cache，然后把这些词交给搜索引擎。但这仍然没有回答几个关键问题：

  • 用户要做什么？ 他想找研究论文，而不是运行一个推理服务。
  • “recent” 到底多近？ 最近一年、三年，还是最近发表的几篇？这是一项尚未明确的时间约束。
  • “reduce memory” 指什么？ 峰值显存、KV Cache 字节数、每 token 内存，还是并发请求下的总显存？
  • “especially” 表达什么关系？ KV Cache 优化是核心主题，还是高效推理中的一个优先子方向？
  • 系统应该返回什么？ 论文列表、方法比较表，还是带有论文证据的技术综述？

这些差异会直接改变检索结果。Query Understanding（查询理解）研究的不是“把句子改写得更漂亮”，而是恢复用户真正的信息需求，并将它表达为下游系统可以可靠使用的结构。

可以把它类比成一位研究助理：听到“帮我找最近的 KV Cache 优化论文”，不会立刻把每个词拆开搜索，而会先确认研究对象、时间范围、优化目标和交付形式。机器系统也需要一个类似的“需求建模层”。

02 · Query Understanding 的正式定义

在经典信息检索（Information Retrieval, IR）中，查询是用户向系统提交的表达，但查询文本只是信息需求的一个不完美观测。用户可能不知道专业术语、使用缩写、遗漏限定条件，或者依赖上一轮对话中的指代。

记当前查询为 q，可用的对话历史为 h，系统希望估计的语义表示为 z。一个抽象的理解模型可以写成：

P(z|q,h)

这不是某一篇论文规定的唯一模型，而是一个统一的建模视角：系统根据当前表达和可信上下文，推断“用户在寻找什么、有哪些限制、哪些地方仍然不确定”。

02.1 一个可用的语义表示

对检索和 Agent 系统而言，z 不应只是一个 intent label。它通常至少包含以下字段：

{
  "domain": "information_retrieval",
  "intent": "research_search",
  "entities": ["LLM inference", "KV Cache"],
  "constraints": {
    "time": {"value": "recent", "resolved": false},
    "objective": "reduce_memory"
  },
  "sub_intents": ["efficient inference", "KV Cache optimization"],
  "ambiguities": ["recent 的具体时间窗口"],
  "output_preference": "paper list with evidence",
  "route": "paper_retrieval"
}

注意 resolved: false。这不是解析失败，而是一个重要的正确性标记：系统识别出了“recent”是时间约束，却没有擅自把它解释成“近三年”。好的查询理解系统不仅要知道自己理解了什么，也要知道自己还不知道什么。

意图 Intent

用户要完成的动作，例如查找、比较、解释、购买、导航或执行。

实体 Entities

查询涉及的人、产品、模型、组织、地点、论文或技术概念。

槽位 Slots

实体周围的属性和参数，例如时间范围、模型版本、数据集、指标。

约束 Constraints

必须满足或优先满足的条件，例如“仅开源”“不降低精度”“小于 8GB”。

上下文 Context

当前轮省略的信息、代词指向、用户刚刚修正过的偏好。

不确定性 Uncertainty

多种合理解释的候选、置信度、需要澄清的字段和证据来源。

02.2 识别意图不等于决定行动

理解层的输出只是对用户需求的估计。系统还需要决定下一步是直接检索、先问一个澄清问题，还是在信息不足时暂不行动。可以把这个决策抽象为：

a*=argmaxa∈{retrieve,clarify,abstain}E[U(a,z)|q,h]

直觉是：如果不确定性不会改变结果，就不必追问；如果缺失字段会改变候选集合或执行后果，澄清的价值就会上升。例如，“找一些 KV Cache 论文”可以先检索；“删除旧数据”则不能在对象和范围不清楚时直接执行。

03 · 经典 Query Understanding 的任务谱系

《Query Understanding for Search Engines》（2020）将相关技术概括为三大类：理解搜索者想要什么、把原查询转换成更有效的查询，以及帮助用户完善查询表达。这个划分适合作为第一层知识地图。原书与章节目录。

03.1 Understand：识别查询表达了什么

  1. Query Classification / Intent Classification。 判断查询属于哪个领域、任务或意图类别。例如 informational（获取信息）、navigational（寻找特定站点/页面）、transactional（准备完成交易）。这只是常见分类之一，不是所有产品都必须采用的固定标签集。
  2. Query Segmentation。 将连续词串切分为有意义的短语。例如 new york times subscription 可以切成 New York Times 与 subscription，而不是机械地逐词处理。
  3. Semantic Tagging / Slot Filling。 给片段标注语义角色，例如把“明天”识别为时间槽位，把“东京”识别为地点槽位，把“低于 100 美元”识别为价格约束。
  4. Entity Linking / Query Interpretation。 将表面提及链接到知识库中的实体，并保留多个合理解释。例如 Jaguar 可能指汽车品牌，也可能指动物；只抽取字符串而不消歧，无法可靠地完成后续检索。

03.2 Transform：把原查询转换成更可用的形式

  • Spelling Correction： 修正拼写错误和常见输入变体，但不能把领域术语误改成常见词。
  • Query Rewriting： 在保持用户意图的前提下，补全省略信息、规范表达或消除指代。
  • Query Expansion： 增加同义词、相关概念或生成的伪文档，扩大检索覆盖。
  • Query Decomposition： 把多方面的复杂请求拆成可分别检索的子查询，再融合结果。

03.3 Interact：帮助用户表达尚未说清的需求

  • Autocomplete： 根据输入前缀预测可能的完整查询。
  • Query Suggestion： 推荐相近主题、细化方向或下一步检索。
  • Clarification： 当多个解释会导致不同结果时，提出一个最有价值的澄清问题。
  • Proactive Query Management： 在多轮搜索中发现需求变化，主动更新查询计划，而不是死守第一轮输入。
研究边界： 分类、分词、槽位抽取、实体链接、重写和澄清是不同任务。一个 LLM 可以在一个 prompt 中同时完成它们，但这不意味着它们在理论上是同一个问题，也不意味着它们应该使用同一个评测指标。

04 · 从原始 Query 到可检索表示：完整系统流程

将上述任务组合起来，可以得到一个分层管线。工程上不一定需要七个独立模型，但系统接口最好保留这些逻辑阶段，便于定位错误、替换组件和做消融实验。

  1. 保留原始输入。 保存 raw_query，不让后续改写覆盖用户原话。它是审计、纠错和回滚的依据。
  2. 恢复上下文。 根据可信的对话历史解决“它”“这些方法”“刚才那篇”等指代。只补全有证据支持的省略信息。
  3. 识别领域与意图。 判断这是研究搜索、事实问答、比较、导航、交易还是工具操作。
  4. 抽取实体与槽位。 找到模型名、论文名、时间、指标、地点、预算和其他约束，并尽可能链接到规范实体。
  5. 估计歧义和置信度。 对多义实体、模糊时间和缺失参数保留候选解释，而不是过早拍板。
  6. 选择转换或澄清策略。 决定直接检索、重写、扩展、分解、追问或暂缓。
  7. 路由到下游。 将经过验证的查询表示交给 BM25、向量检索、RAG、搜索 API 或 Agent 工具执行层。

这一结构也解释了为什么 Query Understanding 是一个系统问题，而不只是一个分类器：上游的误判会改变下游的召回、排序和最终答案；下游结果又能反馈给理解层，帮助判断原始解释是否合理。

04.1 原始查询、理解结果和检索查询应该分开保存

raw_query

用户实际输入。只读保留，不能被模型重写覆盖。

query_frame

结构化语义表示：意图、实体、槽位、约束、候选解释与来源。

retrieval_queries

面向特定检索器生成的查询变体；每个变体要保留来源和用途。

这种分离非常关键：一个为 BM25 生成的词汇扩展查询，不一定适合 Dense Retriever；一个为了消歧而生成的解释，也不应该伪装成用户亲自说过的话。

04.2 实现范式：规则、专用模型与 LLM 混合级联

规则与词典

适合稳定、明确、低延迟的领域词汇、拼写纠正和硬约束。优点是可解释、成本低；缺点是维护成本随领域和表达变化而增长。

专用判别模型

意图分类可使用监督分类器；短语切分和槽位抽取可建模为序列标注（例如 BIO 标签）；实体链接通常包含候选生成与上下文消歧两个阶段。

LLM 结构化解析

通过指令和少样本示例生成结构化语义表示，处理长句、组合约束和开放词汇；应使用受约束 schema、字段级校验和显式不确定性。

Hybrid Cascade

高置信度请求由规则或小模型快速处理；复杂、长尾或上下文依赖请求交给 LLM；关键字段不确定时澄清，并将所有输出送入同一验证接口。

一个工程上常见的设计不是“用 LLM 替换所有组件”，而是先定义稳定的 QueryFrame 契约，再让不同实现填充同一组字段。这样既能做离线 A/B 比较，也能逐个替换分类器、实体链接器或重写模型，而不需要重写下游检索系统。

对于 Query Segmentation，要特别区分“短语边界”与 BPE 等子词 Tokenization：前者回答“哪些词组成一个语义单元”，后者回答“模型词表如何切分字符串”。两者都涉及切分，但优化目标和输出粒度完全不同。

05 · Query Rewriting、Expansion 和 Decomposition 有什么区别？

这三个术语经常被混用，但它们解决的是不同问题。最简单的判断方式是：改写在修复表达，扩展在增加匹配线索，分解在拆开多个子目标。

05.1 Query Rewriting：保持意图，修复表达

原始查询：papers about kv cache less memory。

可能的改写：research papers on methods for reducing KV Cache memory consumption during LLM inference。

改写让语义更完整，但不应该凭空添加“必须开源”“只看 2025 年以后”等原文和上下文都没有支持的条件。评价改写时，重点检查意图保持，而不是只看新句子是否流畅。

05.2 Query Expansion：补充匹配线索

Query2doc（EMNLP 2023）提出用 LLM 根据查询生成伪文档，再把生成内容用于扩展查询。论文报告在 MS MARCO、TREC DL 等 ad-hoc 检索数据集上，BM25 的效果提升约 3%–15%；这是论文特定实验设置下的结果，不是对任意数据集和任意检索器的保证。

为什么伪文档可能有效？短查询通常只有少数关键词，而伪文档可以补充术语、相关概念和背景描述，让稀疏检索更容易匹配文档中的不同表述。

扩展的代价是噪声。 Weller 等人的系统研究比较了 11 种扩展方法、12 个数据集和 24 个检索模型，发现扩展带来的收益与检索器原有能力存在明显关系：弱检索器可能获益，强检索器则可能被额外噪声拖累。增加词语不等于增加有效证据。

05.3 Query Decomposition：把复杂需求拆成子问题

例如“比较近几年降低 LLM 推理成本的方法，分析 KV Cache、量化和投机解码的质量—延迟权衡”至少包含三个子目标：

  • KV Cache 优化：显存占用、缓存精度与并发能力。
  • 量化：权重/激活/缓存量化、精度损失和硬件支持。
  • 投机解码：额外计算、接受率、端到端延迟和输出一致性。

2025 年提交、2026 年更新的 ReDI 工作将复杂查询分解为子查询，为每个子查询补充面向稀疏或稠密检索的解释，再分别检索并融合结果。它强调的是“分解后仍要恢复语义”，否则子查询会因为缺少上下文而变得过于短小或含糊。

05.4 用交互实验比较三种操作

查询转换实验室

选择一个操作，观察它改变的是表达、匹配线索，还是任务结构。

原始需求

找近期降低 LLM 推理 KV Cache 内存占用的论文。

转换结果

检索研究论文：降低大语言模型推理阶段 KV Cache 显存占用的方法。

核心意图保持不变，表达更规范。

06 · 多轮对话：理解的不再是单个 Query，而是持续变化的信息需求

传统 Web 搜索常把每个查询看成相对独立的输入；对话式搜索则不同。用户会逐轮缩小范围、纠正系统、引用前文对象，或者改变最终交付形式。

看一个三轮例子：

Turn 1

“找一些 KV Cache 压缩论文。”

状态：主题 = KV Cache 压缩；任务 = 论文检索。

Turn 2

“只看不会明显降低生成质量的方法。”

状态更新：增加质量保持约束；“方法”指上一轮的压缩方法。

Turn 3

“把它们和量化比较。”

状态更新：比较对象 = 已筛选的 KV Cache 方法与量化；输出 = 对比分析。

如果系统只看第三轮，它不知道“它们”指什么；如果系统把全部历史机械拼接，它又可能重复旧约束、引入已被用户撤回的偏好。更稳妥的做法是维护一个结构化的、可追溯的对话状态：

  • 当前目标： 当前轮正在推进的任务。
  • 活动约束： 用户明确提出、尚未撤回的限制条件。
  • 实体指代： “它们”“这篇论文”“上一个方法”指向哪个对象。
  • 状态来源： 每个字段来自哪一轮、是否由模型推断、是否被用户确认。
  • 更新操作： 新条件是新增、覆盖、删除还是纠正旧条件。

SIGIR 2025 的 Query Understanding in LLM-based Conversational Information Seeking 教程将上下文感知、歧义消解、查询细化、主动查询管理和多轮评测列为核心议题。这说明对话式查询理解已经超出了单轮关键词分类的边界。

06.1 什么时候应该追问？

不是每个模糊词都值得追问。一个实用原则是：只有当不同解释会显著改变结果、成本或副作用时，才优先澄清。比如“最近的论文”可以先按产品默认窗口搜索并明确标注；“把旧版本删掉”则必须先确认对象和删除范围。

ICR（EMNLP 2025）提出迭代式 Clarification and Rewriting：系统在澄清问题与重写查询之间交替推进，而不是一次性尝试修复所有模糊片段。其核心启示是：澄清可以是一个逐步收敛的过程。

06.2 让机器的理解可见、可编辑

Anand 等人在 GenIR @ SIGIR 2023 的立场论文中提出交互式 Query Rewriting：系统先用自然语言呈现自己的 machine intent，用户可以 Commit（接受）、Edit（修改）、Explore（继续探索）或 Hard Rewrite（彻底重写），然后再进入最终检索。这改变了传统搜索中“机器在后台悄悄改写，用户只能从结果猜测系统理解”的交互方式。

这个想法的研究价值在于把模型的解释变成用户可检查的对象，并收集比点击行为更直接的意图反馈。但它仍是一种研究框架和早期可行性探索，不代表 LLM 改写一定更准确；延迟、冷启动、候选意图多样性和用户交互成本仍是开放问题。

07 · Query Understanding 如何连接 Agent 与 Tool Calling？

当系统不只是找文档，还要调用工具时，查询理解就成为自然语言与工具接口之间的语义适配层。例如：

“帮我比较三个向量数据库，重点关注过滤能力和混合检索；最后整理成表格。”

理解层可以产出一个候选任务表示：intent=compare_products、entities=vector databases、criteria=[filtering, hybrid search]、output=table。随后由 Agent 规划层决定是否需要搜索、调用哪些工具，以及如何合并结果。

这里必须明确三条边界：

  1. 理解层回答“用户可能想做什么”。 它给出候选意图、实体和参数，不直接执行副作用。
  2. 规划层回答“怎样完成任务”。 它将目标拆成检索、计算、比较和生成等步骤。
  3. 执行层回答“是否允许执行”。 它校验工具 schema、参数范围、身份权限和用户确认；删除、购买、发送等操作尤其不能靠模型猜测授权。

因此，Query Understanding 与 Function Calling / Tool Calling 密切相关，但并不等价。前者形成语义表示，后者负责按照工具接口提交调用；授权和执行安全还需要独立的控制层。

08 · 如何评测 Query Understanding？

一个常见错误是只看意图分类准确率，便声称整个查询理解系统有效。事实上，理解层的局部预测是否正确，与最终检索或任务是否成功，是两个不同层次的问题。

Intrinsic · 内部指标

  • Intent：Accuracy、Macro-F1
  • Slot Filling：Precision / Recall / F1
  • Entity Linking：Accuracy、Recall@k
  • Rewrite：意图保持、约束保真
  • Decomposition：子目标覆盖率、冗余率

Extrinsic · 下游指标

  • Retrieval：Recall@k、MRR、nDCG@k
  • RAG：答案正确性、证据覆盖与引用质量
  • Agent：任务成功率、工具参数正确率
  • Interaction：澄清轮数、用户修正率
  • Systems：延迟、token 成本、吞吐

08.1 为什么局部准确率不够？

假设一个模型把查询中的实体识别正确了，却把“只比较开源方法”这一约束漏掉。实体链接准确率可能很好看，但召回结果会混入闭源方法，最终答案仍然失败。因此需要把查询表示和最终结果一起评测，并按错误类型做切片分析。

08.2 LLM 是否全面优于传统方法？

目前不能这么下结论。Schmidt、Hagen 与 Fröbe 的 2026 年研究比较了 LLM 与传统方法在 Query Intent Prediction、Query Segmentation 和 Query Interpretation 上的表现，同时把它们放入 Robust04 检索流程做端到端评估。作者报告：在内部查询理解评测中，LLM 没有优于传统方法；在端到端检索中，也只有少数方法带来改善。

这个结果并不意味着 LLM 没有价值。它提示我们要区分表达能力、任务准确率、检索增益和系统收益。传统分类器、规则、词典、实体链接模型和 LLM 并不是简单的新旧替代关系：高吞吐、标签稳定的任务可以由轻量模型处理；复杂、长尾、需要上下文推理的请求则可以进入 LLM 或混合级联。

09 · 常见失败模式与工程防护

失败模式发生原因建议防护
意图误判短查询、多义词、缺少领域上下文保留候选解释；必要时澄清；评测长尾类别
语义漂移重写或扩展加入原需求没有的概念保存原文；做约束保真检查；比较原始与改写结果

09.1 一个最小的、可测试的语义解析示例

下面的代码不是完整的生产级 Query Understanding 模型，而是一个刻意简化的规则示例。它展示一个重要接口原则：原始查询必须保留；已识别的实体与约束要结构化；不确定的字段要显式标记，而不是偷偷补全。

from dataclasses import dataclass

@dataclass(frozen=True)
class QueryFrame:
    raw_query: str
    intent: str
    entities: tuple[str, ...]
    constraints: tuple[str, ...]
    unresolved: tuple[str, ...]

    @property
    def needs_clarification(self) -> bool:
        return bool(self.unresolved)


def parse_query_demo(raw_query: str) -> QueryFrame:
    if not raw_query.strip():
        raise ValueError("raw_query must not be empty")

    text = raw_query.casefold()
    intent = (
        "research_search"
        if "paper" in text or "论文" in raw_query
        else "unknown"
    )

    entities = []
    if "llm inference" in text or "大模型推理" in raw_query:
        entities.append("LLM inference")
    if "kv cache" in text or "kv缓存" in raw_query:
        entities.append("KV Cache")

    constraints = []
    unresolved = []
    if "recent" in text or "近期" in raw_query:
        constraints.append("time:recent")
        unresolved.append("recent 的时间窗口尚未定义")

    if "reduce" in text and "memory" in text:
        constraints.append("objective:reduce_memory")

    if intent == "unknown":
        unresolved.append("意图超出本演示规则覆盖范围")

    return QueryFrame(
        raw_query=raw_query,
        intent=intent,
        entities=tuple(entities),
        constraints=tuple(constraints),
        unresolved=tuple(unresolved),
    )

这个示例的重点不是规则有多聪明，而是接口能否诚实表达边界。生产系统可以将规则替换为分类器、序列标注器、实体链接模型或 LLM，但仍应保留原文、字段来源、未解决问题和验证状态。

10 · 总结：把 Query Understanding 放在正确的系统位置

Understand理解用户表达了什么
Transform把查询变成可用的表示
Interact通过建议和澄清补足信息

可以用五句话总结整篇文章：

  1. Query 是用户信息需求的表达，不是信息需求本身。
  2. Query Understanding 将意图、实体、槽位、约束和上下文组织成显式表示。
  3. Rewriting、Expansion、Decomposition 和 Clarification 是不同操作，应按问题选择。
  4. LLM 能提升复杂语言的处理灵活性，但不保证在每个内部任务或最终检索指标上胜过传统方法。
  5. 理解层可以提出执行意图，但工具权限、参数验证和副作用确认必须留在独立执行层。

从知识地图看，Query Understanding 是从用户语言进入检索系统的语义入口；它与 Embeddings、RAG、Conversational Search 和 Agent Routing 相连，但不应与它们混为一谈。
