ANTHROPIC ENGINEERING / DEVELOPER INFRASTRUCTURE

Understanding Agent-scale Source Control

当 Agent 可以并行生成大量代码时，瓶颈可能不再是“谁来写代码”，而是如何让每个 Agent 快速、可靠且安全地读取、修改和合并同一个巨大代码库。

官方工程文章 · 2026-10-13（10-15 更新）主分类：Systems / Developer Infrastructure约 28 分钟

01 · Agent 把代码生产速度推高后，Git 之外的系统开始成为瓶颈

Anthropic 报告：其 monorepo 每日合并量从 2026 年 5 月约 2,500 次增长到 9 月超过 30,000 次；每天约 2,500 万次代码 checkout。若每次都朴素地拉取完整仓库，流量估算超过 600 PB/天。

这些数字来自 Anthropic 对自身工作负载的描述，不是通用行业统计。它们揭示的关键变化是：Agent、CI 和研究任务几乎总是在线运行，重复访问同一个仓库；Git 原本为分布式、可离线的开发者设计，完整本地副本的优势在这个负载下也会变成数据搬运成本。

文章称 Anthropic 的主分支历史接近 100 GB，压缩工作副本超过 25 GB；他们尝试过 shallow clone、sparse checkout、promisor remote、内部镜像和 blob storage seeds，但随着 merge rate 上升，镜像刷新、历史操作与 partial clone 的维护成本也持续上升。

02 · Scion 的五个设计原则

原则Git 默认假设Scion 面向 Agent 的取舍
客户端始终在线客户端可离线，需要完整副本服务端按需回答查询和对象请求
客户端 / 服务端不对称每个 clone 都能作为完整服务端服务端负责历史、merge、rebase；客户端保留有界对象缓存
服务 API 化CI 常需本地 clone 才能查 blame / merge base查询能力直接通过 RPC 暴露
水平扩展镜像或完整 repo copy 受磁盘和内存限制对象、缓存和计算层分开扩展
提交增量化、低协调本地 commit 后 push，refs 是共享状态服务端创建 changeset；尽量减少全局 refs 协调

工作副本也不再是必需品：CI 只想知道两个提交的 diff 或 merge base 时，可以直接问服务端；需要文件时再请求特定 tree 与 blob。Sparse checkout 只 materialize 请求的路径，virtualized checkout 则把文件按需落盘。

03 · Changeset：把提交记录和派生查询结构分开

Scion 的基本写入单元是 changeset，可理解为 write-ahead log 中的一条变更记录。它保存相对 first parent 发生变化的文件列表，以及指向压缩文件内容的 content-addressed blob 引用。与 Git commit 指向完整 tree 不同，Scion 的 changeset 直接表达“这一笔改了什么”。

只记录变化并不意味着所有查询都变慢。Scion 会从 changeset 派生额外数据结构：文件 blame、path history、commit graph skip lists 等。每一种 derived data 都可以根据父 changeset 递归计算，并选择 eager 或 lazy 生成。好处是可以为热点查询新增索引，而不改变客户端协议。

Dfull≈S;Dsparse=∑o∈Rsize(o)

这是解释“只请求需要的对象”的教学记号，不是 Scion 内部协议公式；R 表示本次请求需要的对象集合。

内容寻址意味着对象一旦写入就不可变，因此任意缓存都可以安全复用；refs 不参与每次 commit 或 fetch，ref 更新则可单独通过 compare-and-swap 处理。写入和全局指针移动由此解耦。

04 · 三层缓存：让同一节点上的 Agent 复用对象

Scion 的 scn 客户端从根 tree 开始，检查本地对象存储中缺少哪些 tree，再递归请求；接着对 blob 重复这一过程。请求始终针对特定不可变对象，不需要一次传输巨大 packfile，因此可以分段、缓存和恢复。

每个节点上的 daemon 可以被同一台机器的多个 job 复用；区域 cache 从内存以 daemon 可直接消费的格式流式传输对象；只有 cache miss 时才回源到权威服务端，再由服务端读取 Spanner 或云对象存储。客户端不必知道缓存拓扑。

这不是简单的“多加几层 Redis”。其前提是对象不可变、请求按内容寻址、客户端只声明需要的对象，而且每一层有明确的故障隔离边界。

05 · 工程结果：高收益，但适用范围很窄

文章报告：各层 cache hit rate 超过 99%；Scion 基础设施相对旧 Git mirror 方案的 CPU 和内存 footprint 缩小约 200 倍；CI 与研究任务 checkout 快两个数量级；CI 单独获得约 25% CPU capacity gain。Anthropic 还称，7 人团队在 5 个月内完成 Scion、Antique review surface 和相关系统的建设与迁移。

工程师没有消失，工作重心改变了

Anthropic 描述的团队实践包括：让 Claude 生成和优化大量代码，但由工程师提供系统边界、关键不变量与设计取舍；使用 adversarial review，同时避免对假设性风险过度防御；通过 hermetic simulation、fuzzing、rate limiting 和意图级审查保持质量。

边界：Anthropic 明确表示 Scion 不适合作为一般用途 Git 替代品。它针对极大 monorepo、海量在线客户端和高频 Agent 写入；迁移还要求配套重构 code review、code search 和 CI。小团队或普通开源仓库不应照搬整套架构。

07 · 最小实现：按请求路径筛选对象

def sparse_object_set(objects, requested_paths):
    selected = set()
    for wanted in requested_paths:
        wanted = wanted.rstrip("/")
        for path in objects:
            if path == wanted or path.startswith(wanted + "/"):
                selected.add(path)
    return sorted(selected)

这个 toy 函数只模拟“请求哪些路径对象”，没有实现 tree traversal、权限校验、缓存协议、并发一致性或 changeset 写入。它帮助理解对象选择，不是 Scion 的实现。
