01 · 训练被中断，究竟丢失了什么？

假设你正在 256 张 GPU 上训练一个语言模型。训练已经运行了 19 个小时，集群发生故障，任务被迫重启。你重新加载了上一次保存的模型权重，但发现训练曲线、学习率和数据顺序都接不上。这说明：保存模型参数，不等于保存了训练现场。

训练是一个持续演化的状态机。每一步都会改变模型参数、优化器内部状态、学习率调度器、随机数生成器以及数据读取位置。故障恢复真正需要的是某个一致时刻的训练状态快照，而不是一份孤立的权重文件。

先区分三个经常被混为一谈的概念：

Model Weights

模型参数本身，决定当前网络的函数映射。用于推理发布时通常是最重要的部分。

Training State

模型、优化器、调度器、随机数和数据进度等联合状态。用于从训练中断点继续学习。

Checkpoint Artifact

经过序列化、分片、写入、校验和提交后，能够被可靠加载的一组文件及其元数据。

Recovery Protocol

故障后如何定位最近的完整版本、重新映射分片、恢复状态并继续执行。

这篇文章的核心问题因此变成了四个连续问题：保存什么、何时保存、怎样保存、如何证明恢复正确。

阅读边界：本文讨论的是训练过程的持久化检查点（training checkpoint）。它不是把 Transformer 的激活值暂时存入 CPU，也不是为了减少反向传播显存而进行的 activation recomputation。两者会在第 8 节严格区分。

02 · 一个真正可恢复的检查点包含什么？

以 AdamW 训练为例。设第 (t) 步的模型参数为 ( heta_t)，一阶与二阶矩估计分别为 mₜ、vₜ。优化器更新并不只依赖当前参数，还依赖历史梯度的统计量：

ADAM STATE · UPDATE EQUATIONS
mt=β1mt−1+(1−β1)gtvt=β2vt−1+(1−β2)gt2θt+1=θt−ηm^v^+ε

这里省略了 bias correction 与 decoupled weight decay 的完整项。关键在于：下一步更新依赖历史状态 (m_t,v_t)，而不只是 ( heta_t)。

如果只恢复 ( heta_t)，却把 mₜ 和 vₜ 重置为零，优化器实际上从一个新的历史起点继续运行。即使代码没有报错，训练轨迹也已经改变。

这里有一个容易忽略的边界：如果只在一次完整的 optimizer update 之后保存，通常不需要保存尚未产生的下一步梯度；但如果允许在 gradient accumulation 的微批次中间保存，就还需要保存累积梯度、micro-batch 进度及相应的数据状态。保存边界决定了必须持久化的状态集合。

工程上应先定义一个一致的训练边界（例如 optimizer step 完成、梯度累积清零之后），再定义 checkpoint schema。不要先把一堆对象序列化，再假设它们天然属于同一时刻。

03 · Young–Daly：多久保存一次最划算？

保存太频繁，每次 I/O 都会消耗时间；保存太稀疏，一旦故障就会重做更多训练。我们需要把“保存开销”和“故障损失”放进同一个目标函数。

3.1 建立一个一阶成本模型

先做一个理想化假设：故障以近似恒定的速率随机发生（Poisson failure model），每次检查点成本固定为 C，平均故障间隔为 M，两次检查点之间的训练时间为 ( au)。

YOUNG–DALY · FIRST-ORDER APPROXIMATION
H(τ)≈Cτ+τ2M

把开销表示为单位训练时间的近似损失比例。第一项是周期性保存成本，第二项是故障发生时平均丢失半个间隔的训练工作。

为什么第二项是 ( au/(2M))？如果故障在一个保存间隔内均匀发生，那么从上一次成功保存到故障点的平均距离为：

EXPECTED LOST WORK
Ravg=1τ∫0τtdt=τ2

单位时间内的期望故障次数约为 1 / M，所以故障导致的平均重做开销约为 ( au/(2M))。这个推导是便于理解的第一阶近似；Daly 的工作进一步研究了包含写入时间、恢复时间等因素的更完整模型。

3.2 对保存间隔求最优值

对 ( au) 求导，并令导数为零：

OPTIMAL CHECKPOINT INTERVAL
dHdτ=−Cτ2+12M=0τ2=2CMτ*=2CM

最优间隔随检查点成本和平均故障间隔的平方根增长。保存成本越高，应该保存得越稀疏；故障越频繁，应该保存得越频繁。

3.3 一个可以手算的例子

假设一次检查点的有效成本为 30 秒，集群平均 10 小时发生一次会中断任务的故障。则：

  • C = 30 秒；
  • M = 10 × 3600 = 36,000 秒；
  • ( au^*=√(2 × 30 × 36,000) ≈ 1,469.7) 秒，约 24.5 分钟。

在这个一阶模型下，平均每次故障丢失约 12.25 分钟的训练工作。保存开销与故障重做开销在最优点附近达到平衡。

不要把公式当成固定配置：Young–Daly 假设故障过程和检查点成本相对稳定。真实训练任务中，存储竞争、节点批量失效、抢占通知、异步写入积压和恢复耗时都会改变成本结构。它适合作为初始估计，而不是跳过 profiling 的理由。

04 · CheckFreq：把保存拆成快照与持久化

频繁保存的主要障碍，是保存操作会阻塞训练关键路径。2021 年 FAST 论文 CheckFreq: Frequent, Fine-Grained DNN Checkpointing 给出一个很重要的思路：不要把“拿到一个一致的状态副本”和“把副本写入持久存储”当成一个不可分割的同步操作。

它把 checkpoint 拆成两个阶段：

  1. snapshot()：在一个一致的训练边界捕获状态副本。此后训练可以继续更新原始参数。
  2. persist()：后台把快照写入持久存储，并在确认完成后将其视为可恢复检查点。

4.1 为什么不能任意异步复制参数？

设一次 optimizer update 会改变模型参数。如果后台线程在复制参数时，训练线程同时执行下一次 update，那么快照可能包含一部分旧参数和一部分新参数。这样的文件即使能够反序列化，也不一定代表任何真实训练时刻。

因此异步保存必须定义快照一致性边界。CheckFreq 利用训练循环的结构，在一次权重更新之后启动快照，并允许它与下一轮 forward/backward 重叠；但在下一次会改变参数的更新之前，必须保证快照复制已经完成。之后才可继续异步写盘。

4.2 PyTorch DCP 的异步保存：两层异步，而不是一个开关

PyTorch Distributed Checkpoint 提供 torch.distributed.checkpoint.async_save。它将状态先 staging 到 CPU 等内存缓冲区，再在后台执行存储写入。这里有一个非常重要的细节：传统 async_save 的磁盘写入是异步的，但 GPU 到 CPU 的 staging 仍可能阻塞训练线程。

PyTorch 2.9 引入 DefaultStager 与 async_stager，可以进一步把 state_dict 构建和 D2H staging 放到后台线程。官方教程给出的时间线是：普通 async_save 仍有同步 CPU copy；完全异步 staging 则可以让 CPU copy 与 GPU compute 重叠。

方式状态快照 / D2H磁盘写入主要风险
同步保存训练线程执行训练线程等待关键路径停顿长

两个 Future 代表两个不同的完成条件：现代异步保存返回的响应可以区分 staging 完成和 upload 完成。训练参数在 staging 完成之前不能被下一次更新污染；下一次异步保存启动之前，通常还应等待前一次 upload 完成，避免无限堆积检查点请求。

异步并不意味着没有成本。PyTorch 文档明确指出，CPU staging 缓冲区会带来额外内存占用，量级与每个 rank 的检查点大小和 rank 数相关；Pinned Memory 还会占用有限的 page-locked memory。官方教程也建议大多数场景限制为一次只有一个未完成的异步保存请求。

4.3 CheckFreq 的策略层：测量、设频率、再反馈调整

CheckFreq 不使用对所有模型都相同的固定保存间隔。它在线测量 iteration 时间、参数快照成本、存储写入成本、检查点大小与 GPU 剩余显存，选择初始频率；运行过程中再根据实际观察到的 overhead 自适应调整。如果其他任务争抢存储带宽，原本每 14 个 iteration 保存一次可能突然产生 35% 的额外开销；论文展示了反馈调节如何把它控制回 5%。

论文还把数据迭代器状态纳入恢复协议。它报告在所测试的模型和硬件上，检查点频率比 epoch 级保存高 83–278 倍，同时把运行时开销控制在不超过 3.5%。例如论文 Table 6 中，BERT 在单 V100 设置下的平均恢复时间从 4920 秒降到 85 秒。这些是 2021 年论文特定实验配置的结果，不应直接当作现代 LLM 集群的性能承诺。

05 · 分布式训练：每张 GPU 保存什么？

当模型状态大于单卡显存，训练框架会把参数、梯度和优化器状态分布到多个 rank。此时检查点不是一份单文件，而是一组具有明确分片关系的状态文件。

5.2 PyTorch Distributed Checkpoint：并行保存与重新分片

PyTorch DCP 支持多个 rank 并行保存和加载。它与 torch.save 的一个重要区别是：一个分布式检查点通常由多个文件组成，每个 rank 至少贡献一个文件；加载时可以根据目标模型预先分配的 state_dict 和分片信息执行 resharding。

这意味着：检查点的逻辑结构不应被误认为固定的物理文件布局。保存时使用 64 个 rank，恢复时使用 32 个 rank，并不一定意味着必须先拼出一个巨大的单文件再重新切分。支持 resharding 的检查点格式可以直接把源分片映射到目标布局。

5.3 Megatron Core：速度与可迁移性之间的取舍

Megatron Core 的分布式检查点文档明确区分两类 Distributed Optimizer 格式：

  • dp_reshardable：保存与加载速度较快，但不支持任意改变 model parallelism；适合训练拓扑保持稳定的常规任务。
  • fully_reshardable：支持更灵活的并行配置变化，但保存和加载更慢；适合需要改变 TP/PP/DP 等并行布局的迁移场景。

工程上并不一定要让每一次保存都付出完全可重分片的成本。可以在日常训练中使用更快的格式，在计划改变并行配置时执行一次可迁移格式的保存与转换。格式选择应当由恢复目标驱动，而不是只看保存速度。

5.4 DeepSpeed ZeRO：训练状态与发布权重不是同一个产物

DeepSpeed 提供 ZeRO-2 / ZeRO-3 checkpoint 到 FP32 consolidated state_dict 的转换工具。这个转换适合把分片训练状态整理成可供普通 PyTorch 或模型发布流程使用的权重；但它可能需要大量 CPU 内存。DeepSpeed 文档还指出 Universal Checkpoints 用于跨 GPU 数量和并行布局恢复，但其文档状态仍标注为 under development。

重要区别：可用于推理的 consolidated model weights，不一定包含恢复训练所需的 optimizer、scheduler、RNG 与数据状态。发布模型和续训检查点应当作为两个不同的交付目标管理。

06 · 正确性：文件写完不等于检查点可恢复

分布式 checkpoint 可能由几十甚至数百个文件组成。只要某个 rank 的分片丢失、元数据与数据版本不匹配，或者最新指针指向了一个尚未完成的目录，整个检查点就可能无法恢复。

6.1 推荐的提交协议

  1. 创建唯一版本目录：例如 step-00128000.tmp，不要直接覆盖上一份可恢复检查点。
  2. 各 rank 写入自己的 shard：记录 shard ID、shape、dtype、文件大小和校验摘要。
  3. 协调所有 rank：确认每个参与 rank 已完成本轮快照与写入；任何一个 rank 失败都不能提交成功状态。
  4. 写入 manifest：记录全局 step、训练配置指纹、并行布局、格式版本、分片清单与必要元数据。
  5. 完成持久化确认：在本地 POSIX 文件系统上，需要正确处理 flush / fsync / rename 等语义；对象存储则应使用适合其一致性模型的完成标记或条件更新。
  6. 最后更新 latest：只有 manifest 和所有必要分片确认有效后，才让恢复流程看见这个新版本。

6.2 为什么不能原地覆盖 latest checkpoint？

假设原来的 latest 是 step 1000。训练开始覆盖它，写到一半机器突然断电。此时 step 900 可能已经被清理，step 1000 又已经损坏，训练就可能退回到更早的备份，甚至完全无法恢复。

更稳健的做法是保留旧版本，完整写入新版本，验证成功后再切换指针，并按照保留策略清理过期版本。CheckFreq 论文也采用写新文件、持久化确认和限制磁盘上检查点数量的方式来控制损坏风险与空间占用。

文件存在、大小非零、甚至能够被 torch.load 读取，都不能单独证明这是一个语义一致的训练快照。恢复验证必须包含模型/优化器状态、分片映射、训练进度和数据状态。

6.3 恢复流程也需要成为正式协议

可靠的恢复流程应当是：读取最后一个已提交 manifest → 校验格式与配置兼容性 → 初始化目标分布式布局 → 加载并重新映射分片 → 恢复 optimizer / scheduler / RNG / sampler → 验证 global step → 继续训练。任何转换、版本升级或并行布局变化都应当有单独的兼容性测试。

07 · 存储、带宽与检查点体积

当模型达到几十亿或数百亿参数时，检查点写入很容易成为 I/O 密集型任务。先用最简单的估算理解数量级：

CHECKPOINT WRITE LOWER-BOUND
Twrite≥checkpoint byteseffective bandwidth

这是理想化的吞吐下界。真实写入还受元数据、同步、并行文件系统、对象存储请求数、竞争与序列化影响。

例如 1 TB 检查点在有效吞吐 20 GB/s 下，理论写入至少需要约 50 秒。这个时间尚未包括快照复制、文件创建、元数据收集、校验、网络拥塞和恢复时的读取。

7.1 模型参数并不是完整训练检查点的全部体积

70B 参数模型若以 BF16 保存一份参数，单是权重就约为 140 GB（按十进制 GB 估算）。如果 Adam 的两个 moment 使用 FP32，两个状态张量合计还可能约为 560 GB；若训练实现另外维护 FP32 master weights，体积还会继续增加。实际数字取决于优化器、精度策略、分片方式和 checkpoint schema，不能简单用一个固定的“每参数字节数”套所有系统。

7.2 典型的优化方向

并行分片写入

让多个 rank 同时写自己的 shard，避免单进程串行聚合成为瓶颈。

内存 staging

使用 CPU / pinned memory / shared memory 承接快照，但必须测量内存占用和 D2H 阻塞。

分层存储

先落到本地 NVMe，再异步复制到共享文件系统或对象存储；要明确本地副本何时算作可恢复。

减少元数据工作

复用稳定的 shard metadata 和 writer，降低重复规划与文件管理成本。

保留策略

保留最近若干份、关键里程碑和必要的周期性备份；清理必须发生在新版本提交之后。

格式与压缩

在写入时间、文件数量、恢复时间、CPU 消耗与格式兼容性之间做实测取舍。

增量检查点和压缩有时能降低存储量，但对持续变化的 optimizer states 来说，增量链可能让恢复过程变复杂，也可能产生额外 CPU 和 I/O 开销。不要为了减少字节数而牺牲可验证的恢复路径。

PyTorch 对 Activation Checkpointing 的定义是以额外计算换取更低的激活内存：前向阶段不保留某些中间张量，在反向传播需要它们时重新执行对应计算。它不会自动为你提供训练任务的持久化恢复能力。

一个实际训练系统可能同时使用两者：Activation Checkpointing 降低每一步训练的显存占用；Training Checkpointing 则把整个训练状态保存到持久存储。不要因为二者名字相同，就把它们的成本模型和实现方案混为一谈。

观察三个方向：

  • 检查点成本 C 增大，推荐间隔变长；如果硬件更慢或状态更大，频繁保存就会更昂贵。

10 · 用代码验证检查点策略

下面的最小实现只依赖 Python 标准库，负责计算理论间隔、估算开销、平均重做时间和理想写入下界。它是一个教学模型，不是 PyTorch DCP 或 Megatron 的生产级保存实现。

from math import sqrt

def young_daly_interval(checkpoint_cost_s, mtbf_s):
    """First-order optimum interval, in seconds."""
    if checkpoint_cost_s <= 0 or mtbf_s <= 0:
        raise ValueError("cost and MTBF must be positive")
    return sqrt(2.0 * checkpoint_cost_s * mtbf_s)

def expected_overhead_fraction(checkpoint_cost_s, interval_s, mtbf_s):
    """Approximate checkpoint + rework overhead fraction."""
    if min(checkpoint_cost_s, interval_s, mtbf_s) <= 0:
        raise ValueError("all inputs must be positive")
    return checkpoint_cost_s / interval_s + interval_s / (2.0 * mtbf_s)

def expected_lost_work_s(interval_s):
    if interval_s <= 0:
        raise ValueError("interval must be positive")
    return interval_s / 2.0

把成本、故障间隔和保存间隔分别作为输入，测试函数是否满足最优性和单调性。完整的可执行文件与 pytest 测试包含在本专题配套代码中。

正确的验证方式：首先验证公式和单位，再用一个极小的训练状态对象验证 save → mutate → load 是否恢复到保存时的状态。分布式系统还需要在不同 world size、rank 故障和部分 shard 丢失时单独测试恢复协议。

按训练场景选择策略

  • 短时、低故障风险的小规模实验：简单同步保存可能足够；优先保证状态完整和恢复脚本可运行。
  • 长时间运行、存储吞吐较高的训练：从 Young–Daly 得到初始间隔，再根据真实保存时间和故障记录修正。
  • 超大模型、分片状态、多机多卡：优先使用分布式 checkpoint API，避免单 rank 聚合所有状态，并明确 resharding 目标。
  • 抢占式实例或高故障率集群：需要更频繁的细粒度保存、可靠的数据迭代器状态和可验证的异步提交协议。
  • 需要频繁改变训练拓扑：将“日常保存速度”和“跨拓扑可恢复性”作为两个不同目标，选择合适的分片格式。

12 · 总结：从保存文件到恢复训练系统

Checkpoint Optimization 不是单纯提高磁盘写入速度，而是设计一条从训练状态捕获到故障恢复的完整链路。

  • 保存什么：保存足以决定下一步训练行为的一致状态，而不只是模型参数。
  • 何时保存：Young–Daly 提供初始间隔；CheckFreq 展示如何在线测量并自适应调整。
  • 怎样保存：把一致快照与后台持久化分离，合理重叠计算和 I/O，但不破坏状态一致性。
  • 如何扩展：通过分布式分片、元数据和 resharding 支持大模型训练与拓扑变化。
  • 如何证明正确：使用完整提交协议、恢复测试和故障注入，而不是只检查文件是否存在。
最终的工程判断：最好的 checkpoint 方案，不是保存得最快或最频繁的方案，而是在可接受的训练开销、存储预算和故障风险下，能够可靠恢复到一个语义一致训练状态的方案。
